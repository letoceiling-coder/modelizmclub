# Переход на боевой ВТБ

Составлено 08.09.2026 по коду и по фактическому `.env` прода. **Ничего из
этого не выполнено** — это план перехода, а не отчёт о нём.

Боевыми деньгами ВТБ не проверялся ни разу. Всё, что проверено, проверено
на кошельке площадки и на тестовых контурах банка.

## 0. Где мы сейчас

Три независимые настройки, их легко перепутать:

| Что | Ключ | Сейчас на проде | Где меняется |
| --- | --- | --- | --- |
| Эквайринг подписок и пополнений | `BILLING_PROVIDER` | **`stub`** | `.env` + `config:cache` |
| Где ждут деньги безопасной сделки | `safe_deal.escrow_provider` | `vtb` | админка → Монетизация |
| Как списывается карта в сделке | `SAFE_DEAL_VTB_CAPTURE_MODE` | `one_stage` | `.env` |

`BILLING_PROVIDER=stub` — это не описка и не наследие: сейчас подписки и
пополнения кошелька оформляются через внутреннюю страницу
`/pay/stub/{uuid}` с имитацией «оплачено / нет средств / карта отклонена».
Денег никто не платит, доступ выдаётся. **До запуска это обязано стать
`vtb`.**

Все три адреса ВТБ — тестовые:

```
VTB_ACQUIRING_API_URL = https://vtb.rbsuat.com/payment/rest     (RBS UAT)
VTB_PAYOUT_OAUTH_URL  = https://epa-ift-sbp.vtb.ru/passport/... (песочница)
VTB_PAYOUT_API_URL    = https://test3.api.vtb.ru:8443/...       (тест)
```

Боевые, из `config/billing.php`:

```
https://platezh.vtb24.ru/payment/rest/
https://open.api.vtb.ru/passport/oauth2/token
```

## 1. Что меняется в настройках площадки

Всё живёт в `backend/.env`. Файл читает только root — см. правило про
`config:cache` в конце.

### Эквайринг (приём денег)

| Ключ | Было | Станет | Откуда берётся |
| --- | --- | --- | --- |
| `BILLING_PROVIDER` | `stub` | `vtb` | наше решение |
| `VTB_ACQUIRING_ENABLED` | `true` | `true` | — |
| `VTB_ACQUIRING_API_URL` | `vtb.rbsuat.com` | `https://platezh.vtb24.ru/payment/rest` | банк |
| `VTB_ACQUIRING_USERNAME` | тестовый | боевой `…-api` | банк, отдельным письмом |
| `VTB_ACQUIRING_PASSWORD` | тестовый | боевой | банк |
| `VTB_ACQUIRING_TOKEN` | пусто | пусто или боевой | если банк выдаёт токен вместо пары логин/пароль — тогда логин и пароль не заполнять, клиент отдаёт приоритет токену (`VtbAcquiringClient:108`) |
| `VTB_ACQUIRING_CURRENCY` | `643` | `643` | ISO 4217, рубли |

### Выплаты продавцам (ОЭ, отдельная интеграция)

| Ключ | Станет | Примечание |
| --- | --- | --- |
| `VTB_PAYOUT_ENABLED` | `true` | |
| `VTB_PAYOUT_OAUTH_URL` | `https://open.api.vtb.ru/passport/oauth2/token` | |
| `VTB_PAYOUT_API_URL` | боевой из договора | |
| `VTB_PAYOUT_CLIENT_ID` / `_SECRET` | боевые | OAuth-пара, отдельная от эквайринга |
| `VTB_PAYOUT_MERCHANT_AUTHORIZATION` | боевой | |
| `VTB_PAYOUT_SOURCE_SYSTEM_ID` | согласовать с банком | сейчас `modelizmclub` |

Каналы выплат: СБП по телефону (`sbp_phone` + `sbp_bank_id` + ФИО) и
перевод на карту (A2C). Клиенты — `VtbSbpPayoutClient`, `VtbA2cPayoutClient`,
токен берёт `VtbPayoutOAuthClient`.

### Безопасная сделка

| Ключ | Значение | Почему |
| --- | --- | --- |
| `SAFE_DEAL_ESCROW_PROVIDER` | `vtb` | окружение; поверх него сильнее строка в админке |
| `SAFE_DEAL_VTB_CAPTURE_MODE` | **решить: `two_stage` или оставить `one_stage`** | см. ниже |
| `SAFE_DEAL_PLATFORM_FEE_PERCENT` | `5` | удерживается из выплаты продавцу |
| `SAFE_DEAL_AUTO_RELEASE_DAYS` | `7` | автоперевод продавцу после доставки |
| `SAFE_DEAL_HOLD_DAYS` | `14` | окно на спор |
| `SAFE_DEAL_CHECKOUT_TTL_MINUTES` | `30` | бронь лота под неоплаченную сделку |

**`one_stage` против `two_stage` — это вопрос к банку, а не к нам.**
`two_stage` (`registerPreAuth.do` → `deposit.do` / `reverse.do`) держит
деньги на карте покупателя до подтверждения получения; для него банк должен
разрешить мерчанту предавторизацию. `one_stage` (`register.do` → `refund.do`)
списывает сразу на счёт площадки, и возврат идёт обратной операцией. Сейчас
стоит `one_stage`.

Тексты чекаута написаны под `two_stage`: «банк удержит сумму на вашей
карте», «банк вернёт деньги на карту». При `one_stage` они неточны — либо
получаем предавторизацию, либо правим тексты.

Отдельно: `VTB_CALLBACK_TOKEN` в `.env` есть, а в коде не читается ни разу.
Вебхук намеренно не доверяет телу запроса (берёт `orderId` и переспрашивает
статус у банка). Ключ либо убрать, либо задействовать осознанно.

## 2. Что настраивается на стороне банка

### Callback-адреса

Регистрация заказа передаёт `dynamicCallbackUrl` в самом запросе
(`SafeDealSettlementService::openHold`), но ВТБ по умолчанию принимает
динамический callback только если это разрешено для мерчанта. Просить у
банка:

| Назначение | URL | Метод |
| --- | --- | --- |
| Подписки и пополнения | `https://api.modelizmclub.ru/api/v1/payments/webhooks/vtb` | GET и POST |
| Безопасная сделка (приём) | `https://api.modelizmclub.ru/api/v1/safe-deals/webhooks/vtb` | GET и POST |
| Выплаты (ОЭ) | `https://api.modelizmclub.ru/api/v1/safe-deals/webhooks/vtb-payout` | POST |

Все три вне авторизации — так и должно быть. Первые два принимают и GET, и
POST: RBS шлёт по-разному в зависимости от настройки мерчанта.

Четвёртый вебхук — `…/safe-deals/webhooks/delivery` — это СДЭК, к ВТБ
отношения не имеет.

### Белый список IP

Наш исходящий адрес один: **31.207.75.124** (сам сервер, запросы к
`platezh.vtb24.ru` и `open.api.vtb.ru` идут напрямую, без прокси).

Входящие — попросить у банка список адресов, с которых приходят callback и
которые ходят в ОЭ. Сейчас вебхуки открыты всему интернету; после получения
списка закрыть их на уровне nginx (`allow`/`deny` внутри
`location /api/v1/payments/webhooks/` и `/api/v1/safe-deals/webhooks/`).
Это не критично для приёма — подделка callback ничего не даёт, статус всё
равно перечитывается у банка, — но лишний шум убирает.

### Сертификаты

- **Эквайринг** — обычный REST по HTTPS, клиентские сертификаты не нужны,
  хватает пары логин/пароль (или токена).
- **ОЭ (выплаты)** — здесь возможен mTLS. В коде клиентские сертификаты
  нигде не настраиваются: `VtbPayoutOAuthClient` и клиенты выплат ходят
  обычным `Http::`. **Если банк требует mTLS — это доработка, а не
  настройка.** Уточнить до перехода: нужен ли клиентский сертификат,
  в каком формате, и с каким сроком.
- Наш сертификат на `api.modelizmclub.ru` должен быть валиден и с полной
  цепочкой: банк проверяет её при обращении к callback.

### Что ещё спросить у банка

- Разрешена ли предавторизация (см. `two_stage` выше).
- Лимиты: максимальная сумма одной операции и суточный оборот.
- Порядок возвратов: полный и частичный, сроки зачисления.
- Реквизиты для сверки: где смотреть выписку, как выгружать реестр.
- Чек по 54-ФЗ: обязан ли мерчант передавать фискальные данные. В коде
  фискализация есть только в устаревшем YooKassa-блоке; для ВТБ её нет.
  **Если чек обязателен — это доработка.**

## 3. Порядок перехода

Ночью или в окно с наименьшим трафиком.

1. Свежий дамп: `deploy/scripts/backup-db.sh`.
2. Записать текущие значения ключей из §1 — понадобятся для отката.
3. Правка `.env` **от root**.
4. `cd /var/www/modelizmclub/backend && php artisan config:cache` **от root**,
   затем `chown www-data:www-data bootstrap/cache/config.php && chmod 644`,
   затем `systemctl reload php8.3-fpm`.
   `config:clear` от `www-data` не запускать никогда: `.env` доступен только
   root, кеш соберётся пустым и весь API уйдёт в sqlite (лежало 6 минут
   07.09).
5. Проверка, что провайдер сменился:
   `grep -ao "'provider' => '[a-z]*'" bootstrap/cache/config.php`
   и `curl -s https://api.modelizmclub.ru/api/v1/plans` — должен отвечать 200.
6. `deploy/scripts/smoke-check.sh`.

## 4. Что проверяется первым платежом

Первый платёж — своей картой, на минимальную сумму. Не тестовой картой:
боевой контур тестовые карты не принимает.

### 4.1. Подписка (самое простое, деньги идут только в одну сторону)

1. Тестовой учёткой купить самый дешёвый тариф.
2. Убедиться, что редирект уходит на `platezh.vtb24.ru`, а не на
   `/pay/stub/...` и не на `rbsuat`.
3. Оплатить. Пройти 3-D Secure.
4. После возврата: подписка активна, `payments` содержит строку с
   `provider = vtb` и `provider_payment_id`.
5. В личном кабинете банка — операция на ту же сумму.
6. **Проверить, что вебхук дошёл**: `safe_deal_gateway_events` для сделок,
   а для подписки — `payments.status` без ручного `POST payments/{uuid}/sync`.
   Если статус меняется только после `sync` — callback не настроен, вернуться
   к §2.
7. Возврат: отменить подписку и убедиться, что деньги вернулись.

### 4.2. Безопасная сделка, приём

Понадобятся две учётки и настоящий лот на маленькую сумму.

1. Покупатель создаёт сделку → редирект на боевую платёжную форму.
2. Оплата картой.
3. Сделка становится `paid`. При `two_stage` — на карте холд, деньги не
   списаны; при `one_stage` — списание.
4. `safe_deal_incoming_payments`: `status`, `rbs_order_id`, `capture_mode`.
5. `safe_deal_gateway_events` — есть запись ответа банка.

### 4.3. Безопасная сделка, отмена (возврат покупателю)

1. Отменить ту же сделку до отправки.
2. `two_stage` → `reverse.do`, холд снят в тот же день.
3. `one_stage` → `refund.do`, деньги возвращаются по срокам банка.
4. Проверить выписку.

### 4.4. Безопасная сделка, выплата продавцу (ОЭ)

Самое рискованное: тут площадка отдаёт деньги наружу.

1. Продавец заполняет реквизиты СБП (телефон + банк + ФИО).
2. Довести сделку до подтверждения получения.
3. `safe_deal_payouts`: `created → processing → approved → confirmed → paid`.
4. Деньги пришли продавцу на телефон/карту.
5. Отдельно проверить A2C (перевод на карту) — это другой клиент.
6. Проверить, что комиссия 5% осталась на площадке: выплата = сумма − 5%.

### 4.5. Что смотреть в логах

```
tail -f /var/www/modelizmclub/backend/storage/logs/laravel.log | grep -i vtb
```

и таблицы `safe_deal_gateway_events`, `safe_deal_incoming_payments`,
`safe_deal_payouts`, `payments`.

## 5. Откат

Если первый же платёж не прошёл или деньги зависли:

1. `BILLING_PROVIDER=stub` и `safe_deal.escrow_provider = wallet`
   (последнее — из админки, мгновенно, без деплоя).
2. `config:cache` от root, reload php-fpm.
3. Уже открытые сделки идут по тому провайдеру, с которым созданы —
   переключение их не ломает, но и не чинит. Зависшие разбирать руками
   через `POST payments/{uuid}/sync` и раздел «Монетизация» в админке
   («Выплатить» / «Вернуть» у каждой сделки в холде).
