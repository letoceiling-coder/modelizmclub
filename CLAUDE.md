# modelizmclub

## Анимации появления и серверная разметка

**Не задавайте `initial` компонентам первого экрана.**

framer-motion записывает проп `initial` инлайн-стилем прямо в серверный HTML.
Содержимое приезжает с сервера готовым — и невидимым до конца гидрации.
Пользователь смотрит на пустое место, браузер не считает элемент отрисованным,
LCP уезжает на время загрузки и разбора бандла.

Замерено на проде 05.09 при 1,6 Мбит/с и 4× CPU:

| Страница | Узел | В DOM | Видно | Разрыв |
| --- | --- | --- | --- | --- |
| `/feed` | карточка поста | 2,5 с | 6,2 с | **3,7 с** |
| `/profile` | содержимое вкладки | 1,7 с | 4,6 с | **2,9 с** |
| `/feed` | баннер (до починки) | 3,1 с | 6,8 с | **3,7 с** |

Во всех трёх случаях данные пришли вовремя. Ждали не их.

### Как надо

Для появления при монтировании — `<Appear>` из `@/components/ui/Appear`.
Он не задаёт начальное состояние на первом рендере (ни на сервере, ни при
гидрации) и анимирует только то, что смонтировано позже: переключение вкладки,
догрузку страницы ленты, ответ на действие.

```tsx
// было: прячет карточку до гидрации
<motion.div initial={{ opacity: 0, y: 8 }} animate={{ opacity: 1, y: 0 }}>

// стало
<Appear>
```

Для смены содержимого по ключу — `<ReducedMotionSwitch>`; он по умолчанию не
анимирует первый отрисованный кадр. Ставьте `animateOnMount` только если
уверены, что блока в серверной разметке нет.

### Когда `initial` уместен

- **Блоки ниже сгиба с `whileInView`.** Они прячут то, чего пользователь ещё
  не видит. Вреда нет, проверять не нужно.
- **Диалоги, меню, тосты, шторки.** Их вообще нет в первом рендере — они
  появляются по действию.

### Как проверить

```bash
curl -s https://modelizmclub.ru/feed | grep -ac 'opacity:0'
```

`-a` обязателен. Роутер сериализует идентификаторы совпадений в разметку
вместе с нулевыми байтами (`"__root__\0"`, `"\0feed\0feed"`), grep считает
такой ответ двоичным и молча не печатает ничего. Пустая строка выглядит как
ноль, но означает, что проверка не выполнялась. Найдено 06.09.

Ноль на первом экране. Если больше — найдите узел и посмотрите, виден ли он
без JS. Разрыв между «пришло в DOM» и «стало видно» измеряется наблюдателем
`largest-contentful-paint` и опросом `getComputedStyle(el).opacity`.

## После мержа возвращайтесь на develop

`git merge` оставляет вас на той ветке, в которую влили. Дальше рука сама
делает `git commit` — и коммит уходит в `master`, минуя ветку.

Так уже дважды случилось: 04.09 два коммита и 05.09 `67d02c9` (метаданные
видео) и `7b26e9d` (preconnect). Ничего не потерялось — они запушены и
выкачены, — но в `feat/feed-card-density` их нет, а `develop` отстал от
`master` на три коммита и следующая ветка ушла бы от неполной базы.

Мерж заканчивается возвратом, а не остаётся последним действием:

```bash
git checkout master && git merge --no-ff feat/… && git push origin master
git checkout develop && git merge --ff-only master && git push origin develop
```

Если правка нашлась уже после мержа — новая ветка от `develop`, даже на
одну строку. Проверка перед любым коммитом: `git rev-parse --abbrev-ref HEAD`
не должен отвечать `master`.

## Параллельные сессии — каждая в своём worktree

Общее рабочее дерево на две сессии не делится. 08.09 это стоило двух
испорченных коммитов: `git add -A` в докоммите дважды смёл незакоммиченную
работу соседней сессии — сначала воскресший `DeliveryChoiceSheet.tsx`, потом
восемь файлов страницы `/post/{uuid}`. Оба раза чужой незаконченный код уехал
в `master`, второй раз — вместе с красными воротами, которые полдня никто не
видел.

Страдают обе стороны, и вторую легко не заметить.

**Кто смёл** — уносит в свой коммит то, чего не писал: непроверенный код под
своим именем и своим сообщением. `fb05263` называется «инвентаризация ключей
ВТБ» и наполовину состоит из страницы записи.

**Кого смели** — теряет авторство. Работа уже в `master`, но не там, где её
будут искать: ветка `feature/post-page` осталась пустой на базе, `git log
--follow` по файлу выводит на чужой коммит про платежи. Через полгода это
выглядит не следом аварии, а загадкой; понадобилась отдельная запись в
`docs/known-issues.md`, чтобы её распутать.

### Как заводить worktree

```bash
bash deploy/scripts/worktree.sh new fix/<задача>   # дерево, ветка, зависимости
bash deploy/scripts/worktree.sh list               # кто ещё работает
bash deploy/scripts/worktree.sh done fix/<задача>  # убрать дерево и слитую ветку
```

Одна команда вместо четырёх — и это не про удобство. Правило существовало и
08.09, но стоило `worktree add`, `bun install`, `composer install`, а потом
не забыть убрать дерево и ветку. Три раза за день оказалось проще не заводить
дерево вовсе; чем это кончилось, написано выше.

База — `origin/master`, а не текущий HEAD: ветвиться от чужой недоделанной
работы незачем.

Руками то же самое:

```bash
git worktree add ../MODELISM-<задача> -b <ветка> origin/master
cd ../MODELISM-<задача> && (cd frontend && bun install --frozen-lockfile)
# …работа, коммиты, мерж…
git worktree remove ../MODELISM-<задача>        # с незакоммиченным — --force
git worktree prune                              # если каталог удалили руками
git branch -d <ветка>                           # ветка сама не исчезает
```

Отдельное дерево — отдельный чекаут: соседняя сессия не видит ваших правок,
вы не видите её. `.git` общий, ветки и коммиты видны обеим.

Проверить, кто ещё работает: `git worktree list`. Если в основном дереве
лежат чужие незакоммиченные правки — не коммитить вообще, а завести своё
дерево.

### Своё дерево — своя тестовая база

`phpunit.xml` называет базу `modelizmclub_test`, и до 10.09 `TestCase`
требовал ровно это имя. Значит два прогона из двух деревьев делили одну
базу и роняли друг другу схему на `migrate:fresh`. Выглядело это не как
гонка, а как поломка кода: `relation "migrations" does not exist`,
`relation "users" already exists`, `duplicate key value violates unique
constraint "pg_type_typname_nsp_index"`.

Теперь проверка смотрит на префикс, и имя задаётся переменной. Рецепт
печатает `worktree.sh new` при создании дерева:

```bash
DB_NAME=modelizmclub_test_<дерево> bash deploy/scripts/setup-test-db.sh
DB_DATABASE=modelizmclub_test_<дерево> php artisan test
```

Переменная оболочки перебивает `phpunit.xml` — проверено; `<env>` там без
`force` и существующее значение не трогает. Защита от прогона по боевой
базе на месте: `modelizmclub` под префикс `modelizmclub_test` не подходит.

Если прогон всё же столкнулся с чужим: гасить надо по `phpunit`, а не по
`artisan test` — работает именно он, и `pkill -f "artisan test"` его не
трогает.

### `git add -A` запрещён

Всегда. Только явные пути:

```bash
git add frontend/src/routes/feed.tsx frontend/src/lib/routes.ts   # так
git add -A                                                         # нельзя
git add .                                                          # нельзя
```

Причина не в аккуратности, а в том, что `-A` захватывает всё, включая то,
чего вы не писали: чужие правки, финдеровские дубли, случайные файлы.
Три раза за один день — этого достаточно, чтобы считать команду непригодной.

### Перед коммитом смотреть, что уходит

`git status` перед каждым коммитом — целиком, а не только то, что уже
добавлено. Если там есть изменения в файлах, не относящихся к вашей задаче,
коммит **останавливается**: сначала выяснить, чьи они, и только потом
продолжать. Не «закоммичу своё, а с этим разберутся» — именно так чужая
работа и уезжает под чужим именем.

### Переключать ветки в общем дереве нельзя, пока рядом кто-то работает

`git checkout` и `git checkout -b` уносят несохранённые правки с собой:
git молча переносит их на новую ветку, конфликта нет, сообщения нет. Если
правки чужие, следующий `git add` кладёт их в вашу историю.

Перед любым переключением: `git status` пуст или все правки ваши. Иначе —
не переключаться, а завести своё дерево (см. выше). Это относится и к
`git checkout -b` от текущего коммита: HEAD не двигается, но правки уходят.

### Что из этого ловят хуки, а что нет

`deploy/scripts/install-git-hooks.sh` ставит `pre-commit` и `post-checkout`.
Проверено опытами 08.09 в отдельном дереве — четыре правила выше хук
закрывает по-разному, и разницу надо знать, чтобы не полагаться на него там,
где он бессилен.

| Правило | Хук | Как именно |
| --- | --- | --- |
| Своё дерево на задачу | **запрещает** | обычный коммит из общего дерева не проходит, если рядом заведено дерево с веткой |
| `git add -A` запрещён | **не ловит напрямую** | точки входа «до `git add`» у git нет — но вред от него случается только при коммите из общего дерева, а это запрещено строкой выше |
| Смотреть, что рядом | видит | `pre-commit` печатает «рядом осталось» — незакоммиченное и неотслеживаемое, что в коммит не идёт |
| Не переключать ветки | видит после | `post-checkout` называет перенесённые файлы и ветку; запретить нельзя — хука «до checkout» у git нет |
| Документация вместе с кодом | **запрещает** | оба смёта 08.09 были докоммитами, утащившими фронтенд |
| Посторонние файлы в исходниках | **запрещает** | `check-workspace.sh`: финдеровские дубли и неотслеживаемое |

Главный запрет — первый, и он появился после того, как печати оказалось мало:
оба смёта 08.09 случились при списке соседних деревьев на экране.

**Общее дерево при живой параллельной работе — только для слияний.** Мержи
проверка пропускает: слияние без конфликта до `pre-commit` не доходит вовсе
(у него свой хук `pre-merge-commit`), а слияние с конфликтом завершается
обычным `git commit`, и на этот случай проверка молчит при живом
`MERGE_HEAD`. То есть `git checkout master && git merge --no-ff` из общего
дерева работает как работал.

Соседом считается дерево **с веткой**. Временные деревья с отсоединённым
HEAD заводит оснастка, они есть всегда, и считать их значило бы запретить
коммиты из общего дерева навсегда — а запрет, срабатывающий всегда, за
неделю превращается в привычку писать `--no-verify`.

Переключение веток остаётся единственным, что нельзя запретить до действия:
хука «до checkout» у git нет. Но и оно теперь опаснее для того, кто
переключает, чем для соседа: коммитить в общем дереве всё равно не дадут.

Хуки не приезжают с `git clone`, установщик запускается руками один раз на
машину. Осознанный обход — `git commit --no-verify`.

## Проверять до выкатки, а не после

07.09 на прод ушли три регрессии и один простой API. Все четыре нашлись при
моей же проверке, но **после** выкатки. Значит, какое-то время ими пользовались
живые люди, и повезло только в том, что первым посмотрел я.

| Что | Отчего |
| --- | --- |
| Окно верификации поверх каждой страницы | закрыл `verified` всю группу Billing, включая чтения; `fetchSession` стал получать 403 с кодом `phone_not_verified`, а по этому коду окно открывается глобально |
| Обнулённые счётчики комментариев | `'App\\Models\\Post'` в SQL схлопнулось до `App\Models\Post`, условие не совпало ни с одной строкой, счётчики обновились в ноль |
| Дубль записи в шторке комментариев | вывод «пропс нигде не отрисовывается» по фрагменту файла |
| Шесть минут простоя API | `config:clear` от `www-data` при `.env` с правами root |

Правила отсюда.

**1. Правка доступа, прав или данных проверяется на стенде под всеми
затронутыми состояниями до прода.** Затронутые состояния — не «вошёл и не
вошёл», а весь список ступеней, которых касается правка: гость,
зарегистрированный, с подтверждённым телефоном, подписчик, staff. Для
маршрута — ещё и оба входа: прямая загрузка и переход внутри приложения; они
идут по разным веткам, и 07.09 расхождение между ними держалось незамеченным
именно поэтому.

Если изолированного стенда нет (`dev.modelizmclub.ru` сейчас совпадает с
продом), правка не выкатывается, а откладывается с объяснением. Это уже
сработало: `fix/route-access-auth-tier` пролежала невыкаченной сутки и вышла
только после разбора последствий для десяти маршрутов.

**2. Массовое изменение данных сначала с `--dry-run`, и выборка проверяется
независимым запросом.** Пересчёт счётчиков, миграция значений, любой `UPDATE`
без `where id = ?`. Считать затронутые строки тем же условием, что стоит в
правке, бессмысленно: если условие сломано, сломаны обе половины одинаково.
Проверять надо с другой стороны — по факту в данных. С теми счётчиками
`select count(*) from comments where post_id = …` показал бы, что записей нет,
за секунду до того, как они обнулились.

**3. Команды, трогающие кеш конфигурации, на проде не запускаются.** Чтобы
php-fpm увидел новый или изменённый PHP-класс, достаточно
`systemctl reload php8.3-fpm`. `config:clear` и `config:cache` нужны только
при правке `config/` или `.env` — и тогда см. раздел про доступ к `.env` ниже.

**4. Отрицательное утверждение о коде требует полного чтения** — отдельным
разделом ниже.

Порядок один и тот же: сначала полный проход, потом починка. Исключение —
P0: чинится сразу, отдельным релизом, с проверкой на проде сразу после.

## Локальные ворота — не CI. Смотреть надо оба

Локальный прогон говорит про рабочее дерево, CI — про то, что легло в
`master`. Это разные утверждения, и расходятся они предсказуемо.

09.09 я дважды выкатил на прод коммит, у которого CI был красным, и оба
раза отчитался «ворота зелёные». Локально так и было: `tsc` ноль, eslint
ноль ошибок, тесты зелёные. Красным был шаг, которого локально нет вовсе.

| Коммит | Что упало |
| --- | --- |
| `a9d69c9` — релиз 1 иерархии направлений | `Schema baseline is current` |
| `6b0bcac` — кошелёк и платежи | `Schema baseline is current` |

Два красных прогона из тридцати, и оба — один и тот же шаг. Механизм тоже
один: ветка добавляет миграции, эталон схемы в
`backend/database/schema/objects.txt` остаётся прежним, и в момент мержа
CI краснеет по построению. Я потом пересобирал эталон следующим коммитом
— то есть чинил через четыре минуты то, что можно было не ломать.

**Правило 1. Ветка с миграциями пересобирает эталон схемы в себе, а не
следующим коммитом.**

```bash
bash deploy/scripts/schema-drift.sh --update-baseline
git add backend/database/schema/objects.txt
```

Тогда мерж зелёный сразу, и отдельная ветка `chore/schema-baseline-…`
не нужна.

**Правило 2. Перед выкаткой посмотреть CI именно того коммита, который
выкатываете.** Не «последний прогон на master», не «у меня локально
зелено» — прогон по этому SHA:

```bash
bash deploy/scripts/check-ci-status.sh $(git rev-parse master)
```

Ответов три, и путать их нельзя: `0` зелёный, `1` красный, `2` —
**неизвестно**. Неизвестно бывает, когда прогон ещё идёт, ещё не
начинался или спросить не удалось. Это не «всё хорошо»: подождите или
проверьте вручную.

Скрипт появился вместо однострочки, которая здесь стояла сначала. Та
падала с трассировкой Python, когда GitHub отвечал «rate limit exceeded»:
`gh` на машине не авторизован, а без токена дают 60 запросов в час, и
кончаются они быстрее, чем кажется. Трассировка читается как поломка
инструмента, а не как «проверить нельзя», — то есть подталкивает выкатить
не проверив. Ровно наоборот тому, ради чего проверка заводилась.

`GH_TOKEN` в окружении поднимает лимит; без него всё работает, пока лимит
цел.

Выкатка при красном CI — это то, что заказчик просил подтверждать
отдельно. Молча так делать нельзя, даже когда причина известна и кажется
безобидной.

## Доступ к .env на проде

`backend/.env` имеет права `-rw------- root root`, а php-fpm работает от
`www-data` и прочитать файл не может. Приложение живёт исключительно за счёт
`bootstrap/cache/config.php`, собранного когда-то от root. Любая чистка кеша
— и все `env()` возвращают null: `DB_CONNECTION` уходит в умолчание `sqlite`,
весь API отдаёт 500. Так прод и лежал шесть минут 07.09.

Прав это не защищает. В том же каталоге `bootstrap/cache/config.php` лежит с
правами 644 — читает любой пользователь сервера, — и внутри него тот же
пароль базы открытым текстом. То есть 600 у `.env` не закрывает секрет, а
только создаёт ловушку.

Правильное состояние:

```bash
chown root:www-data backend/.env && chmod 640 backend/.env
chmod 640 backend/bootstrap/cache/config.php
```

После этого чистка кеша безопасна: Laravel прочитает `.env` напрямую.

Права выставлены на проде 08.09; учение подтвердило починку:
`config:clear` и `config:cache` от `www-data` при опросе API раз в 250 мс
дали 23 запроса и 23 ответа 200, а собранный кеш содержит `pgsql`, `redis`,
`reverb` — то есть `.env` прочитан.

`config:cache` создаёт файл с умолчательными 644, поэтому во всех скриптах,
которые её вызывают, сразу после стоит `chmod 640`: иначе следующая выкатка
молча отменяет починку.

Эта строка два месяца была не описанием, а пожеланием. Написали её 08.09;
пересчёт 10.09 показал, что из четырнадцати вызовов `chmod` стоял в
четырёх, а десять скриптов — включая `server-setup.sh`, `finish-setup.sh`
и `deploy-neeklo.sh` — тихо возвращали кешу 644 вместе с паролем базы
внутри. Заметить это можно было только пересчётом руками, потому что
ничто не смотрело.

Теперь смотрит `deploy/scripts/check-config-cache-chmod.sh`: у каждого
вызова в репозитории должен стоять `chmod` рядом, иначе ворота CI не
проходят. Правило, за которым никто не следит, — не правило, а запись о
намерении.

`deploy/scripts/check-config-access.sh` проверяет оба условия и вызывается из
`smoke-check.sh` после каждой выкатки — предупреждением, не приговором.

## Возраст строки в чистом SQL врёт на три часа

`APP_TIMEZONE=Europe/Moscow`, а Postgres на сервере живёт в `Etc/UTC`. Колонки
времени объявлены `timestamp without time zone` — 130 таблиц из 130. Laravel
пишет в них московское время, а `now()` в psql отдаёт UTC. Сравнивать одно с
другим нельзя.

Выглядит это не как ошибка часового пояса, а как невозможное значение:

```sql
select round(extract(epoch from now() - created_at) / 60) from safe_deals where id = 35;
-- -153, то есть сделка «создана через два с половиной часа»
```

Приложение внутри себя согласовано: `now()` в PHP тоже московский, и
`expireStaleCheckouts` со своим TTL работает верно. Врёт именно ручной запрос
— и врёт правдоподобно, если разница окажется меньше суток.

08.09 я на этом чуть не выписал несуществующий дефект: по SQL выходило, что
сторож не гасит брошенный чекаут, а на деле сделке было 27 минут при TTL 30.
Настоящая причина простоя была другая (замок `withoutOverlapping` на сутки),
и три лишних часа в расчёте её маскировали.

**Как проверять возраст.** Через приложение — оно единственное знает, в каком
поясе писало:

```bash
php artisan tinker --execute='echo now()->diffInMinutes(\App\Models\SafeDeal::find(35)->created_at, true);'
```

Если нужен именно SQL — приводить `now()` к московскому стенному времени
**одним** преобразованием:

```sql
select round(extract(epoch from (now() at time zone 'Europe/Moscow') - created_at) / 60)
from safe_deals where id = 35;
-- 60, то есть час — столько же, сколько показывает приложение
```

`at time zone 'Europe/Moscow'` над `timestamptz` возвращает стенные часы
Москвы уже без пояса — ровно в том виде, в каком лежит `created_at`. Второе
преобразование подряд (`at time zone 'UTC' at time zone 'Europe/Moscow'`)
уводит в другую сторону и делает хуже: на той же строке даёт −300 вместо 60.
Проверено на боевой базе 08.09.

Ту же поправку держать в уме, читая любые даты глазами: `created_at` в выводе
psql — московское время, `now()` в соседней колонке того же запроса — UTC.

## Замер в браузере ловит не тот узел

Две ловушки, каждая стоила ложного дефекта в аудите 10.09. Обе выглядят
одинаково: селектор находит узел, замер выполняется, число получается — и
относится к чему-то другому.

### Куки-баннер — тоже `role="dialog"`

Проверка просмотрщика записи показала «ноль крестиков» и «Escape не
закрывает». Оба вывода относились к баннеру согласия: он висит на каждой
странице, объявлен `role="dialog"`, и `document.querySelector('[role="dialog"]')`
возвращает **его**, а не открытое окно.

С закрытым баннером тот же замер даёт один крестик 32×32 и Escape,
который закрывает. То есть дефекта не было вовсе.

```js
// так — первым найдётся баннер
document.querySelector('[role="dialog"]')

// так — окно, открытое последним
[...document.querySelectorAll('[role="dialog"]')].at(-1)

// а надёжнее — сперва убрать баннер и убедиться, что диалогов ноль
[...document.querySelectorAll('button')]
  .find((b) => /^Принять$/.test(b.textContent.trim()))?.click();
```

### Селектор по всей странице ловит боковую колонку

Проверка «адрес следует за выбранным диалогом» в мессенджере показала, что
адрес не меняется. На деле селектор — «элемент с текстом длиннее двадцати
символов и временем внутри» — попал в блок подписки в правой колонке
(«Год · активна до 06.09.2027») и увёл страницу на `/subscription`.

Список диалогов лежит в `main`; боковые колонки, шапка и нижняя навигация
— снаружи. Замер, ограниченный `main`, сразу нашёл девятнадцать строк и
подтвердил, что адрес меняется на `?chat=…`.

```js
const main = document.querySelector('main') ?? document.body;
[...main.querySelectorAll('button, a, [role="button"]')]
```

### Скрытая вкладка останавливает наблюдателей

Проверка догрузки комментариев показала, что сторож под списком есть,
прокрутка доходит до конца, а следующая страница не приезжает и запрос не
уходит вовсе. Похоже на сломанный `IntersectionObserver` — и объяснение
находилось само: у наблюдателя корнем стоит прокручиваемый контейнер, а
такие корни легко задать не тем узлом.

Дело было не в этом. Панель браузера была спрятана, то есть страница
считалась невидимой:

```js
document.visibilityState  // "hidden"
```

В такой вкладке браузер не крутит кадры, а `IntersectionObserver` отдаёт
колбэки по кадрам — и не отдаёт даже первый, обязательный. Замер сообщал не
«не сработало», а «не измерялось», и выглядели эти два ответа одинаково.

Проверяется одной строкой; если `false` — измерять нечего, надо открыть
вкладку или взять браузер, у которого страница видима:

```js
await new Promise(r => { const t = setTimeout(() => r(false), 1000);
  requestAnimationFrame(() => { clearTimeout(t); r(true) }) })
```

Под это правило попадает всё, что живёт кадрами: `IntersectionObserver`,
`ResizeObserver`, `requestAnimationFrame`, анимации, ленивая подгрузка,
автопрокрутка, замеры LCP и CLS. Геометрия — `getBoundingClientRect`,
`getComputedStyle` — считается и в скрытой вкладке, поэтому размеры,
отступы и цвета в ней мерить можно, а поведение нельзя.

**Общее правило.** Прежде чем записывать отсутствие — крестика, изменения
адреса, кнопки, догрузки, — напечатайте, что именно нашёл селектор: тег,
подпись, координаты. А если отсутствует не узел, а событие, — сначала
докажите, что инструмент вообще работает: поставьте свой наблюдатель на тот
же узел и убедитесь, что он отвечает. Ложный дефект от настоящего
отличается тем, что у ложного находка не та, а не пустая. Ср. «Отрицательное
утверждение о коде требует полного чтения» ниже: там то же правило для кода,
здесь — для экрана.

## Отрицательное утверждение о коде требует полного чтения

Сказать «этого в коде нет» можно, только прочитав функцию или компонент
целиком. Найти что-то можно по `grep` — этого достаточно, находка сама себя
доказывает. Не найти — нельзя: `grep` по куску файла и чтение фрагмента
доказывают лишь то, что вы смотрели не туда.

Два дубля 07.09 родились именно так.

`CommentsSheet` принимает пропс `preview`. Я посмотрел разметку диалога
ниже по файлу, не нашёл там его отрисовки и написал в коммите «пропс нигде
не отрисовывается». Он рисовался в `header()` на 41-й строке, выше того
места, куда я смотрел. Добавленный второй показ дал на проде запись дважды —
до заголовка и после.

Там же: `cancelSubscription` в `lib/api/payment.ts` действительно никем не
вызывается, и я чуть не отчитался, что подписку нельзя отменить. Настоящая
функция называется `cancelMySubscription`, живёт в `SubscriptionBlock` и
смонтирована на своей странице профиля. Отличие в одном слове имени.

Практически: перед «нет такого» — `sed -n '1,$p'` по файлу или чтение всей
функции; поиск по корню слова, а не по полному имени (`cancel.*ubscription`,
а не `cancelSubscription`); и проверка на живой странице, если утверждение
касается поведения.
