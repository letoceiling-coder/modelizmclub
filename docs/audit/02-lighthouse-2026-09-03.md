## Три проверявшиеся гипотезы

### «~20 API-запросов при открытии главной» — не подтвердилась

Всего на главной **20 сетевых запросов**, но к API из них **6**, и пять из
шести — это картинки, отдаваемые через `/api/v1/media/<uuid>`:

| Статус | Размер | URL |
|---|---:|---|
| 200 | 65 КБ | `/api/v1/media/9fd5796f-…` |
| 200 | **707 КБ** | `/api/v1/media/a5b740ba-…` |
| 200 | **702 КБ** | `/api/v1/media/b3958976-…` |
| 200 | 157 КБ | `/api/v1/media/dd6f4255-…` |
| 200 | **519 КБ** | `/api/v1/media/41d83c8d-…` |
| 200 | 1.1 КБ | `/api/v1/plans` |

Настоящий data-запрос ровно один — `/api/v1/plans`. Проблема главной не в
количестве запросов, а в их весе: **4902 КБ** на загрузку.

### «herovideo.mp4 даёт ERR_ABORTED на range-запросах» — подтвердилась, причина найдена

На главной видео **не запрашивается вообще** (0 запросов) — в текущей вёрстке
его нет. Но сам файл отдаётся сломанно:

```
GET /videos/herovideo.mp4
  HTTP/2 200
  content-type: video/mp4
  content-length: 6005880
  accept-ranges: bytes          ← заявлено

GET /videos/herovideo.mp4  (Range: bytes=0-1023)
  HTTP/2 200                    ← должно быть 206 Partial Content
  content-length: 6005880       ← отдан весь файл целиком
  (Content-Range отсутствует)
```

Сервер **объявляет поддержку range-запросов, но не выполняет их**. Браузер
просит первый килобайт для метаданных, получает в ответ 6 МБ, обрывает
соединение — это и есть `net::ERR_ABORTED`. По той же причине невозможна
перемотка и возникают рывки: плеер не может запросить произвольную позицию.

Дополнительно: у видео **нет `Cache-Control`** — оно перекачивается при каждом
заходе. Рядом лежит `herovideo.webm` (2.2 МБ против 6.0 МБ), который не
используется.

> Путь `/herovideo.mp4` (из корня репозитория) отдаёт **404** — рабочий адрес
> `/videos/herovideo.mp4`. В коде фронта видео упоминается только как
> placeholder в админке (`components/admin/LandingBlocksAdminCard.tsx:256`),
> то есть подставляется контент-менеджером через настройку блока лендинга.

### Статика отдаётся без сжатия — не проверялось, но найдено

```
GET /assets/index-DEBqgwyG.js   (Accept-Encoding: gzip, br)
  content-length: 2320098       ← 2.27 МБ
  (content-encoding отсутствует)
```

Тот же чанк под gzip — **668 КБ** (замерено локально, см. `01-baseline.md`).
CSS так же: 161 813 байт без сжатия. То есть на каждой загрузке главной
пересылается **примерно 1.6 МБ лишнего трафика** только по JS.

Это самая дешёвая из всех возможных оптимизаций: `gzip on` / `brotli on` в
nginx, ноль изменений в коде.

## Что видно из цифр

**LCP 14–19 с на всех страницах, кроме главной.** Главная отдаёт LCP за 2.8 с,
остальные — за 14–19 с при том же FCP 2.5–3.9 с. Разрыв между FCP и LCP в
10+ секунд означает, что первый экран рисуется быстро, а главный элемент
дорисовывается после того, как отработает JS и придут данные. Это поведение
клиентского рендера поверх SSR-оболочки.

**`/profile` — TBT 1400 мс.** На порядок больше любой другой страницы. Главный
поток заблокирован больше секунды.

**CLS 0.226 на `/feed`** при 0.09 на десктопе — вдвое хуже цели. На
`/subscription` 0.133.

**`index-*.js` весом 2268 КБ висит на каждой странице** — это первый по весу
ресурс везде, кроме страниц с крупными картинками.

## Ограничения замера

- Один прогон на страницу, без усреднения. Lighthouse на мобильном профиле
  даёт разброс 5–10 пунктов Performance между прогонами; для отслеживания
  динамики нужно 3–5 прогонов и медиана.
- Замер с локальной машины, канал и география влияют на абсолютные значения.
  Сравнимы между собой цифры внутри одной таблицы, а не с внешними бенчмарками.
- Страницы под авторизацией измерены как их видит гость.
