# A. Резюме

## Реальное состояние

Фронтенд **функционально широкий и структурно незавершённый**. 76 маршрутов,
244 компонента, 95 тысяч строк — покрыты все три продукта: соцсеть,
маркетплейс, монетизация. Но собран он как набор страниц, а не как система:
у каждой страницы своя загрузка данных, своя проверка прав, свои отступы,
свой формат даты. Отсюда главный симптом, который видит заказчик, —
«блоки есть, страница не собрана» — и главная причина реестра дефектов §6:
пятнадцать разных багов оказываются одной ошибкой, повторённой в пятнадцати
местах.

Ни одна мобильная страница, кроме главной, не проходит по LCP. Сборка из
чистого чекаута не собирается. Тестов на фронте нет.

## Три структурные проблемы

**1. Права проверяются нигде и везде.** Четыре параллельных механизма
доступа на фронте (факт ③), ни один не работает на SSR (①), а бэкенд
проверяет владение объектом одной policy на 279 изменяющих маршрутов (②).
Итог: гость получает paywall вместо окна входа, авторизованный —
«Не удалось отправить комментарий» вместо «Подтвердите номер». Это не
пятнадцать багов, это одна отсутствующая точка принятия решения.

**2. Данные загружаются императивно.** 335 `useEffect` против 28
`useQuery`, самописный store на 880 строк, три источника правды о сессии,
ручные `syncFavoritesFromServer()`/`syncDialogsFromServer()` (④). Каждая
страница грузит своё, кэша между страницами нет, перерисовывается всё.
Это причина и LCP 18.9 с на `/feed`, и рассинхрона «лайкнул — счётчик не
изменился — обновил — изменился».

**3. Дизайн-системы нет.** 2254 захардкоженных px, 81 из 83 картинок без
размеров, три разных карточки поста, три разных шапки, дата в ISO-формате
в сообществах (⑥). Мобильная адаптация невозможна, пока отступы —
абсолютные пиксели.

Плюс одно инфраструктурное: сжатие выключено (⑤). Одна строка nginx даёт
больше, чем любая оптимизация кода.

# C. Системные решения

## S1. Единый шлюз доступа

**Закрывает:** A1, A2, A8, A9, A10 (фронтовая часть), B1, B2, §6.4 «без SMS —
единое окно», §6.5 «/deals для гостя», §4 целиком. Из реестра §6 — **11
пунктов**.

### Что заменяет

`lib/auth/` (7 гвардов), `components/access/` (7 файлов, 639 строк,
`GuestAccessProvider` в 41 файле, `GuestGuardLink` в 12), `lib/access/`
(2 файла), `lib/feed-guest-access/` (3 файла, 375 строк). После миграции
остаётся один модуль `lib/gate/`.

### Модель

Четыре уровня, строго упорядоченные: `guest < registered < verified < subscriber`.
Уровень пользователя вычисляется из одного источника — `useSession()` (S5):

```
level(session) =
  !session.user                → guest
  !session.user.phoneVerified  → registered
  !session.subscription.active → verified
  иначе                        → subscriber
```

Проверка — сравнение чисел. Причина отказа — **первый** непройденный шаг в
порядке `registered → verified → subscriber`. Ровно одна. Это и есть
формализация правила §4 «одно действие → одна проверка → одна причина».

### Публичный API

**Хук** `useGate()` возвращает одну функцию:

```
require(level, action, options?) → Promise<void>
```

- `level` — требуемый уровень;
- `action` — функция, которую надо выполнить, если доступ есть (обычно
  вызов мутации);
- `options.intent` — сериализуемое описание намерения для возврата после
  входа: `{ key: 'post.like', params: { postId } }`;
- `options.returnTo` — маршрут для возврата (по умолчанию текущий).

Поведение: если `level(session) >= level` — вызывает `action()` и всё. Иначе
сохраняет intent в `sessionStorage['gate.intent']`, открывает **одно** окно,
соответствующее первому непройденному шагу, и завершается без вызова
`action()`. После успешного входа/верификации/оплаты хост окон читает intent,
повторяет `require()` с тем же `level` и `action` — если теперь проходит,
действие выполняется, intent очищается.

**Компонент** `<Gated level action>`: обёртка над кликабельным элементом —
перехватывает `onClick` и прогоняет через `require`. Для ссылок —
`<GatedLink to level>`: при недостатке прав открывает окно вместо перехода,
intent = `{ key: 'navigate', params: { to } }`.

**Хост окон** `<GateHost/>` — монтируется один раз в `__root.tsx`. Держит
состояние «какое окно открыто» и три диалога:

| Окно | Когда | Содержимое | Успех |
|---|---|---|---|
| `AuthDialog` | нужен `registered` | «Войти или зарегистрироваться», вход по email/телефону/OAuth **внутри окна**, без перехода на `/login` | сессия обновилась → resume |
| `VerifyPhoneDialog` | нужен `verified` | «Подтвердите номер телефона, чтобы получить доступ к этой функции» + кнопка «Подтвердить номер» → форма SMS в том же окне | `phoneVerified` → resume |
| `PaywallDialog` | нужен `subscriber` | «Нужна подписка. Оформите подписку, чтобы пользоваться этой функцией» + кнопка → `/subscription` с `returnTo` | после оплаты страница подписки читает intent и возвращает |

На < 768 px все три — `Sheet side="bottom"`.

### Гварды маршрутов

Остаются как тонкая обёртка: `routeGuard(level)` в `beforeLoad` → тот же
`require(level, () => {}, { intent: navigate })`. Для страниц, которые целиком
за уровнем (`/messenger`, `/settings/*`), гвард нужен, чтобы не рисовать
пустую страницу. Для read-only страниц с действиями (`/ads/$id`,
`/communities/$id`) гварда **нет**, действия — через `<Gated>`.

### SSR (факт ①)

**Чинить не нужно, нужно перестать называть это утечкой.** Sanctum-токен
живёт в клиенте, SSR его не имеет и не может получить приватные данные.
Что «утекает» на SSR — оболочка страницы без данных. Правильное поведение:

- публичные страницы — полный SSR с данными (это и нужно для LCP);
- персональные страницы — SSR отдаёт скелет, `beforeLoad` на сервере
  **не редиректит** (не может знать), клиент после гидратации применяет
  гвард. Скелет не содержит ничего личного.

### Фронт — поле `can`

Да, отдавать. Формат — объект булевых флагов в каждом Resource сущности с
policy:

```
{ "id": ..., "can": { "edit": true, "delete": false, "comment": true, "react": true } }
```

Правила: ключ отсутствует = `false` · только действия, для которых есть
policy · вычисляется через `$user?->can('update', $this)` в `toArray()` ·
для гостя — все `false`.

Фронт: `<Gated level>` сначала проверяет уровень (S1), затем — если
сущность передана — `entity.can[action]`. Уровень отвечает за «войдите /
подтвердите / оформите», `can` — за «это не ваш комментарий». Два разных
отказа с двумя разными окнами: второй — просто скрытие кнопки, окно не нужно.

Это убирает «Не удалось отправить комментарий»: кнопка либо есть и
работает, либо её нет.
