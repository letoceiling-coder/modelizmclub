# Перенос репозитория к владельцу

> **Дата:** 03.10.2026
> **Откуда:** `letoceiling-coder/modelizmclub`
> **Куда:** `Neeklo1606/modelizmclub`
> **Способ:** зеркальная копия (`git clone --mirror` + `git push --mirror`)

Код и история перенесены полностью, потерь нет. Не перенеслось то, что не
живёт в репозитории: задачи, пулл-реквесты, история сборок, настройки. Это
свойство способа, а не ошибка: передача владения сохранила бы и их, но
зависела от прежнего разработчика.

## Почему копия, а не передача владения

Передача владения — лучший способ, и просить о ней стоило. Копия выбрана
потому, что ждать было нельзя: доступ к исходному репозиторию держался на
чужом ключе, и в день его отзыва способов не осталось бы вовсе.

Важная деталь, которая в этот день выяснилась: **у владельца доступа к
исходному репозиторию не было**. Токен учётной записи `Neeklo1606` не видел
его совсем — `gh repo view` отвечал «Could not resolve to a Repository».
Прочитать удалось только SSH-ключом, лежащим на машине владельца, но
зарегистрированным на учётной записи ушедшего разработчика:

```
$ ssh -T git@github.com
Hi letoceiling-coder!
```

То есть перенос был возможен ровно до отзыва этого ключа.

## Чем доказана полнота

Сверка двух независимых свежих копий, а не вывод команды переноса.

| Что сверялось | Старый | Новый |
| --- | --- | --- |
| Коммитов во всей истории | 2045 | 2047 |
| Ветки | 132 | 133 |
| Теги | 34 | 34 |
| SHA всех 200 ссылок | — | расхождений нет |
| `git fsck` | — | без ошибок |
| Git LFS | не используется | — |

Два лишних коммита в новом — правка адресов (`9b7f3b5a`) и служебный слепок
пулл-реквеста, который GitHub делает сам.

Проверка, которую можно повторить:

```bash
git clone --mirror github-letoceiling:letoceiling-coder/modelizmclub.git old.git
git clone --mirror git@github.com:Neeklo1606/modelizmclub.git new.git
comm -23 <(git -C old.git rev-list --all | sort) <(git -C new.git rev-list --all | sort)
```

Пустой вывод означает, что ни один коммит не пропал. Вывод был пустым.

**`refs/pull` удаляются до заливки.** В зеркальной копии они есть (их отдаёт
GitHub), а принимать их GitHub отказывается. Без удаления заливка падает
шестью отказами подряд:

```bash
git for-each-ref --format='delete %(refname)' refs/pull | git update-ref --stdin
```

**Заливка идёт по SSH, а не по HTTPS.** Токен `gh` без права `workflow` не
принимает ни один коммит, трогающий `.github/workflows/`, — а таких в истории
большинство: из 132 веток доехали 32, тегов ноль. По SSH этого ограничения
нет. Право `workflow` можно и выдать (`gh auth refresh -s workflow`), но SSH
проще и не требует ничего менять.

| Пулл-реквесты (было не меньше 6) | только передачей владения |

по SSH даёт код, но не интерфейс.

## Адреса в репозитории

Адрес стоял в одиннадцати местах восьми файлов. Все переведены коммитом
`9b7f3b5a`.

Опасен был один. `deploy/scripts/check-ci-status.sh` — та проверка, на которой
стоит правило «не выкатывать при красном CI», — по умолчанию спрашивала
состояние сборки у репозитория, которого владельцу не видно, и отвечала бы
`Not Found`, то есть кодом 2 «выяснить не удалось». Проверка против выкатки
вслепую отвечала бы «не знаю» всегда и по одной причине, а такой ответ легко
прочитать как «можно».

Намеренно не тронуто `docs/qa/modelizm-baseline.md:12` — там
`letoceiling-coder` стоит в графе «Автор» коммита `5ce68e3`. Это атрибуция,
а не адрес; переписать её значило бы подделать запись о том, кто что сделал.

## Два ключа на одной машине

До переноса `~/.ssh/config` отдавал `github.com` ключ `id_ed25519`. В его
открытой части стоит адрес владельца, но зарегистрирован он на учётной
записи ушедшего разработчика. Ключ с вашим адресом в комментарии не значит
«ваш ключ» — проверять надо ответом сервера, а не содержимым файла.

Теперь так:

| Адрес | Учётная запись |
| --- | --- |
| `git@github.com:…` | `Neeklo1606` |
| `github-neeklo:…` | `Neeklo1606` |
| `github-letoceiling:…` | `letoceiling-coder` (пока ключ действует) |

`IdentitiesOnly yes` обязателен в обоих разделах: без него ssh предлагает все
ключи подряд, и учётная запись определяется тем, который подошёл первым.

## Что осталось за пределами репозитория

**Сервер.** Выкатка делает `git fetch origin` в `/var/www/modelizmclub`, и
`origin` там надо перевести на новый адрес, а на сервер добавить ключ с
доступом к нему. Пока действует ключ прежнего разработчика, выкатка
работает; после отзыва — встанет.

```bash
cd /var/www/modelizmclub && git remote -v     # посмотреть
git remote set-url origin git@github.com:Neeklo1606/modelizmclub.git
```

**Защита ветки `master` недоступна.** На бесплатной учётной записи приватный
репозиторий защитить нельзя — ни прежним механизмом, ни rulesets:

> Upgrade to GitHub Pro or make this repository public to enable this feature.

Публичным делать нельзя: в репозитории опись доступов и разбор денежных
контуров. Остаётся GitHub Pro. До тех пор правило «коммит не уходит в
`master` напрямую» держится только на дисциплине, а случаи, когда оно не
удержалось, уже есть — см. `CLAUDE.md`.

**Dependabot** включён 03.10 (оповещения и автоматические заплатки
безопасности). Расписание — в `.github/dependabot.yml`: понедельник, не
больше пяти PR на экосистему.

## Побочная находка: красные ворота

Первый же прогон CI на новом репозитории оказался красным, и это **не
следствие переноса**: падающий коммит `5966e2d9` лежит в обоих
репозиториях с одинаковым SHA.

Причина разобрана отдельно и починена в `fix/ci-build-heap`: предел кучи для
сборки фронтенда стоял у боевой выкатки (4096) и не стоял в воротах вовсе.
Прод собирался, ворота падали, и увидеть расхождение мог только тот, кто
смотрит в оба места сразу.

Подробности — в том коммите; здесь важно другое: **первый прогон CI на новом
репозитории — это первый прогон вообще.** История сборок не переносится, и
«на старом было зелено» проверить нельзя. Любой отказ в первые дни надо
разбирать от начала, а не списывать на перенос.
