# МоДелизМ — FRONT-FINAL-RUN: финальная доводка интерфейса

Версия 1.0 от 05.10.2026. Исполнитель: Claude Code. Проект: modelizmclub.ru.

Этот файл — очередь промптов по техническому заданию «МоДелизМ Club: финальная доводка лендинга и интерфейса» (далее ТЗ, файл `modelizm_frontend_finalization_claude_code.md`). Агент читает его целиком и выполняет промпты раздела 4 по порядку. Работа идёт на локальном стенде, без сервера и без выкатки. Сайт обновляется только в разделе 5, с участием владельца.

---

## 0. Как запустить (для Никиты)

1. Положи в репозиторий, в папку `docs/frontend-finalization/`, два файла: этот и файл ТЗ.
2. Если есть скриншоты, по которым писалось ТЗ, положи их в `docs/frontend-finalization/screens-owner/`. Без них агент восстановит картину по описанию, но со скриншотами точнее.
3. Просмотри раздел 2 «Решения». Исправь строку, если решение записано не так.
4. Закрой остальные сессии Claude Code в этом репозитории. Ноутбук на зарядке, во второй вкладке терминала `caffeinate -i`.
5. В корне репозитория: `claude --permission-mode auto`. Вставь стартовый промпт.

Объём работы больше одной сессии. Агент работает пять часов, сохраняет место остановки и выводит итог. Следующую сессию запускаешь тем же стартовым промптом — он продолжит сам.

### Стартовый промпт

```text
Ты выполняешь финальную доводку интерфейса modelizmclub.ru.

1. Найди и прочитай целиком два файла: FRONT-FINAL-RUN.md и
   modelizm_frontend_finalization_claude_code.md (ТЗ). Ищи по имени,
   исключая node_modules и vendor.
2. Если существует docs/frontend-finalization/STATE.md — продолжай с первого
   промпта без финального статуса. Если нет — начни с промпта 00.
3. Выполняй промпты раздела 4 по порядку, соблюдая разделы 1–3.
   Перед каждым промптом перечитывай раздел 3 и STATE.md.
4. Меня нет. Вопросов не задавай. Всё, что требует моего решения,
   записывай в docs/frontend-finalization/MORNING.md и иди дальше.
5. Границы: к серверу не подключаться; прод — только GET-запросы гостя;
   не выкатывать; в master и develop не сливать и не пушить; реальных
   платежей, SMS и звонков нет; данные живых пользователей не трогать.
6. Разрешаю: ветки front-final/* и их пуш в origin; один pull request
   в develop без слияния.
7. Через пять часов от начала сессии заверши текущий шаг, обнови STATE.md
   и MORNING.md, запушь и выведи MORNING.md в чат.
```

## 3. Правила

Действуют в каждом промпте. Правила раздела 2 файла `NIGHT-RUN.md` и `CLAUDE.md` тоже действуют; при расхождении побеждает `CLAUDE.md`.

### 3.1. Что это за работа

Доводка существующего интерфейса. Не новый продукт, не переписывание, не новая дизайн-система. Сначала сломанные сценарии, потом композиция, потом анимации. «Премиально» означает аккуратную композицию, читаемость и предсказуемое поведение.

### 3.2. Факты и гипотезы

1. ТЗ написано по скриншотам и тексту главной. Его наблюдения V01–V22 — это то, что видно на картинке, а не причина и не диагноз. Каждое сначала воспроизведи.
2. Не воспроизвелось — статус «не воспроизведено» с доказательством, ничего не чинить.
3. Вывод «этого нет» — только после проверки вторым способом. Перед выводом «пусто» прочитай ответ API целиком. Ищи по корню имени, а не по полной строке.
4. Не строй второе, если есть первое: перед новым компонентом, настройкой или страницей найди существующие.
5. Проверка, которая не краснеет при откате правки, проверкой не считается.

### 3.3. Стенд

1. Вся проверка — на полном локальном стенде: база из миграций и семян, бэкенд, очередь, вебсокет, фронтенд. SMS и письма — в журнал, банк — заглушка.
2. Перед каждым замером убедись, что на порту отвечает именно этот стенд, и что адрес API собран с `/api/v1`. Ошибки CORS локального стенда к боевому API дефектом сайта не являются.
3. Рабочее дерево создаётся штатным скриптом проекта, как требует `CLAUDE.md`.
4. Проверка на эмуляции не равна проверке на устройстве. Клавиатура iOS и Android, адресная строка, безопасные зоны на настоящем телефоне — статус `BLOCKED: проверяет владелец`, а не `PASS`.

### 3.4. Код

1. Переиспользовать существующие Button, Input, Tabs, Dialog, Sheet, PostCard, ListingCard, Avatar, EmptyState. Недостающий вариант добавлять в сам компонент.
2. Горизонтальное переполнение чинить в компоненте-причине. Глобальный `overflow-x: hidden` ремонтом не считается.
3. Нельзя: пустой обработчик, `href="#"`, кнопка внутри ссылки, `onClick` на `div` без клавиатурной семантики, сообщение об успехе без ответа сервера, хаотичные `z-index`.
4. Серверное состояние живёт в слое запросов, локальное — в компоненте. Не заводить вторую копию списка.
5. `useEffect` сам по себе не дефект. Переводить на слой запросов только затронутые чтения.
6. Не менять права доступа на сервере, правила дружбы, тарифы, денежные потоки и дерево категорий сверх решений раздела 2.
7. Не добавлять новые библиотеки ради анимаций. Не обновлять мажорные версии.
8. Код и документы — отдельными коммитами.

### 3.5. Git и гейт

1. Интеграционная ветка `RUN_BRANCH` от `origin/BASE_BRANCH`. Каждая волна — своя ветка `front-final/NN-имя` от неё.
2. Гейт зелёный — слияние в `RUN_BRANCH` через `--no-ff`, пуш. Красный после `MAX_ATTEMPTS` — ветку запушить, не сливать, статус `FAIL`.
3. Общий гейт: команды из `CLAUDE.md` и CI; ни одного нового красного теста, ни одной новой ошибки линтера и типов относительно базы; обход всех маршрутов — ноль исключений, ноль горизонтальной прокрутки на 320, 360 и 390, ровно один `<main>` и один `<h1>` на странице.
4. `RUN_BRANCH` всегда зелёная. Регрессия, не починенная за `MAX_ATTEMPTS`, — отмена слияния волны.

### 3.6. Журнал

В `docs/frontend-finalization/`:

- `STATE.md` — очередь, статусы, ветки, коммиты, остаток.
- `baseline.md` — окружение, коммит, команды, старые проблемы.
- `screens.md` — маршруты, роли, ширины, состояния.
- `actions.csv` — реестр всех интерактивных действий по форме ТЗ 4.2.
- `defects.md` — шаги воспроизведения, важность, причина, правка, тест.
- `decisions.md` — решения D1–D11 и найденные расхождения.
- `qa.md` — фактические результаты со ссылками на доказательства.
- `MORNING.md` — для владельца, простым языком.

Статусы действия и проверки: `passed`, `failed`, `blocked`, `not-tested`. В отчётах различать: сделано, протестировано, прошло, заблокировано. «Код написан» не равно «работает». Каждое доказательство привязано к коммиту и ширине экрана. Снимки «до» и «после» — по стандарту репозитория, без учётных данных и личных данных.

### 3.7. Сначала телефон

Каждая правка проектируется и проверяется от 360 px, затем 320, затем остальные ширины. Зона нажатия — 44×44 CSS px как внутренняя норма проекта. Поля ввода на телефоне — не меньше 16 px. Масштабирование страницы не запрещать.

### Промпт 02 — Мессенджер [МЕНЯЕТ КОД]

```text

Два человека переписываются через настоящий API стенда; вёрстка устойчива
на телефоне; сообщение не теряется и не дублируется.

ОСНОВАНИЕ
ТЗ 3.7, 5.3 (M01–M14). Наблюдение V19. Решения D2, D3.

ШАГИ

   областей прокрутки или API. Запиши причину до правки.
2. Список диалогов: поиск с состояниями пусто/ошибка/загрузка; короткие
   вкладки; аватар 44–48 px; имя и последнее сообщение в сжимаемой зоне;
   справа короткое время и значок непрочитанного; даты «сегодня ЧЧ:ММ»,

   и переписка — отдельные состояния маршрута, «Назад» возвращает в тот же

   на уровне макета маршрута.
```

## 6. Когда работа считается законченной
