## 8. D4 — состав нижней панели (единственный подтверждённый дефект)

Воспроизведено на стенде, `/feed`, гостем, ширины 320 и 360.

D4 требует пять пунктов: **Лента, Сообщества, Сообщения, Объявления,
Профиль**, а Друзья — «в профиле и меню».

Фактически панель рисует пять пунктов, но состав другой:

| Ширина | Пункты | Колонки |
| :-- | :-- | :-- |
| 320 | Лента · Сообщения · Объявления · Профиль · **Друзья** | 5 × 64 px |
| 360 | Лента · Сообщения · Объявления · Профиль · **Друзья** | 5 × 72 px |

То есть: **«Сообщества» отсутствует**, **«Друзья» присутствует**. Пять
получилось по совпадению — один нужный пункт пропал, один ненужный встал.

Почему пропали «Сообщества»: `src/components/layout/BottomNav.tsx:35`
отсеивает пункт по признаку `communitiesEnabled`, а
`FeatureFlagsSeeder.php:13` задаёт `feature.communities_enabled = false`.
На стенде признак выключен. **На проде он может быть включён — и тогда
панель покажет шесть пунктов**, то есть разойдётся с D4 ещё и числом.

«Друзья» не отсеиваются никогда: в `ALL_ITEMS` шесть записей, и
единственный фильтр — на `/communities`. Прочитан весь компонент, не
фрагмент.

Что при этом в порядке и портить не надо:

- зона нажатия 64×60 px при 320 и 72×60 при 360 — внутренняя норма 44×44
  соблюдена с запасом;
- подписи не обрезаны ни на одной ширине (`scrollWidth == clientWidth` у
  всех пунктов), то есть требование «на 320 px подписи не сталкиваются»
  выполнено;
- слой берётся из шкалы (`z-[var(--z-sticky)]`), безопасная зона учтена
  один раз (`padding-bottom: var(--safe-bottom)`).

Правка — шаг 3 промпта 01, вместе со сторожевым тестом на пять пунктов,
который требует гейт того же промпта. **В этой сессии не делалась**, и
проверка «а есть ли Друзья в профиле и меню» выполнена — её итог меняет
состав правки.

### Условие, без которого правку делать нельзя

D4 переносит Друзей «в профиль и меню». На телефоне выполнено только
первое:

| Вход в Друзей | Где | Видно на телефоне (< 768 px) |
| :-- | :-- | :-- |
| Нижняя панель | `BottomNav.tsx:28` | да — это и предлагается убрать |
| Профиль (свой) | `ProfileView.tsx:632`, `href={isOwn ? "/friends" : undefined}` | да |
| Боковая колонка | `Sidebar.tsx:70` | **нет** |
| Меню аватара | — | **нет, пункта не существует** |

`Sidebar.tsx:418` показывает колонку классом `w-16 md:flex xl:hidden`, то
есть от 768 px и шире; `BottomNav` — наоборот, `md:hidden`. На телефоне
панель остаётся единственной навигацией.

Меню аватара прочитано целиком: Админка, Профиль, Мои объявления, Сделки,
Кошелёк, Подписка, Приглашения. **Друзей там нет.**

Значит, если просто убрать пункт из панели, на телефоне останется один
путь — через свой профиль, в два нажатия вместо одного, а «и меню» из D4
не будет выполнено вовсе.

**Поэтому правка состоит из двух частей, и вторая обязательна:** убрать
«Друзей» из `BottomNav` **и** вернуть раздел в меню. Счётчик входящих заявок
(`useIncomingFriendRequestCount`) нужно перенести вместе с пунктом, иначе
человек перестанет видеть заявки.

## 9. Маршруты с параметрами: два дефекта

Обход дополнен 10 маршрутами с настоящими идентификаторами из базы стенда,
4 ширины = 40 загрузок. **Горизонтальной прокрутки нет ни на одной,
исключений нет ни одного.** Два замечания подтвердились с выдержкой 3,2 с.

### 9.1. `/post/{uuid}` — ни одного заголовка

Страница записи отвечает 200, содержимое настоящее, `<main>` один — но
**ни `<h1>`, ни `<h2>` на странице нет вовсе**.

```
адрес=/post/00000000-0000-4000-8000-000000000101
окно=«Сборка P-51 Mustang 1:48 — МоДелизМ»
main=1  h1=[]  h2=[]
сверху: К ленте · Demo User · 28 мин назад · Авиация · Сборка P-51 Mustang 1:48
```

Название записи выводится и даже попадает в заголовок окна, но разметкой
заголовка не является. Воспроизводится на всех четырёх ширинах, то есть это
не выдержка замера, а состояние страницы.

Это нарушение гейта 3.5.3 («ровно один `<h1>` на странице») на одной из
самых посещаемых страниц, и одновременно вопрос доступности: по заголовкам
такую страницу не обойти.

Правка — волна F4 (единая карточка записи, ТЗ 3.3): название записи должно
быть `<h1>` страницы.

### 9.2. Страница 404 без ориентира `<main>`

```
адрес=/rules/consent → HTTP 404
main=0  h1=["404"]  h2=["Страница не найдена"]
```

Заголовок есть и текст понятный — а `<main>` нет. Гейт 3.5.3 требует ровно
один; служебные страницы под это требование попадают так же, как
остальные, и шаг 4 промпта 06 их отдельно называет.

### 9.3. Две мои ошибки в этой же проверке — не дефекты

Чтобы следующая сессия не занесла их в дефекты:

- **`/ads/1`** отвечает «Объявление не найдено». Числовой `id=1` из таблицы
  `listings` этому маршруту не подходит — нужен другой идентификатор.
  Проверка неубедительна, маршрут надо перепроверить с верным значением,
  а не считать сломанным.
- **`/rules/consent`** отвечает 404 закономерно: `consent` — слуг из
  `legal_pages`, и живёт он под `/legal/`, а не под `/rules/`. `/legal/rules`
  и `/legal/privacy` прошли обход без замечаний. Дефект здесь только тот,
  что описан в §9.2 — отсутствующий `<main>` у самой страницы 404.

## 10. Счётчик заявок в друзья пропал с телефона — исправлено

## 12. Вкладки при свайпе: не воспроизведено, но свойство добавлено

настоящем телефоне видна.

`ui/tabs`, вкладкам сущностей и вкладкам профиля. Прокрутку внутри ленты это
не меняет: после правки лента профиля прокручивается 0 → 296 из 557,
страница не двигается. Подтверждение самого симптома —
`BLOCKED: проверяет владелец`.

это не вкладки.

### 12.1. Два инструмента, которые мерили не то

Записано, чтобы следующая сессия не повторила и не завела ложный дефект.

**Мышиное протягивание не прокручивает контейнер.** Первый замер
протаскивал ленту мышью: у мессенджера прокрутка пошла, у профиля нет, и
профиль выглядел сломанным. На деле мышь вообще не прокручивает
`overflow-x-auto` — у мессенджера на жест отвечает своя обработка
(`drag-scroll-x` в `HorizontalScrollNav`), у профиля родное поведение,
которое отвечает на касание. Замер сравнивал разные механизмы.

**События касания, созданные в JS, не управляют родной прокруткой.** Второй
замер рассылал `TouchEvent` из `page.evaluate` — обе ленты не двинулись, и
теперь «сломанными» выглядели обе. Родная прокрутка идёт от настоящего
ввода, а не от событий, собранных в JS.

Годится только настоящий ввод: `Input.dispatchTouchEvent` через CDP. Прежде
чем записывать «не прокручивается», надо показать, что инструмент вообще
умеет прокручивать — на ленте, про которую это известно.

### 12.2. Вкладки профиля — не вкладки для доступности

На `/profile` при 360 весь перечень ролей на странице — `{"status": 1}`.

«Отзывы», «Сообщества», «Приглашённые», «Заблокированные») нет ни
`role="tablist"`, ни `role="tab"`: это кнопки в прокручиваемом `div`.
Клавиатурой и экранным диктором такая лента вкладками не читается.

Шаг 4 промпта 01 требует «один компонент» для вкладок. Профиль свою ленту
собирает сам, а не общим `ui/tabs`, который роли даёт. Это работа волны F1,

## 13. Переписку закрывает подписка, а не дружба — спорит с D2

Воспроизведено запросом и в интерфейсе.

D2: «„Написать“ проверяет дружбу, а не подписку. Подписчик пишет как
раньше.»

Фактически `app/Policies/ConversationPolicy.php`:

```php
public function create(User $user): bool
{
    return $this->isSubscriber($user);   // строка 28
}
```

и `send()` (строка 48) — тоже подписчик, кроме чата сделки.

Проба: А и Б — друзья, оба с подтверждённым телефоном, подписки нет.

```
POST /api/v1/conversations {"user_id":5}
→ 403 {"message":"Оформите подписку, чтобы начинать переписку.",
       "code":"subscription_required"}
```

То есть двое друзей без подписки переписываться не могут вовсе, а D2
говорит, что решать должна дружба.

**Не правил, и вот почему.** Это не вёрстка, а правило доступа, за которым
стоят деньги: подписка — то, за что платят. `CLAUDE.md` требует проверять
такие правки на стенде под всеми затронутыми состояниями, а менять их
вообще разрешено только «сверх решений раздела 2» — и формулировка D2
допускает два чтения: «так должно быть на сервере» и «так должна вести себя
кнопка „Написать“ в интерфейсе». Разница между ними — платная функция,
отданная бесплатно.

Вынесено владельцу в `MORNING.md` вопросом «да или нет».

Чтобы проверить сам мессенджер, А и Б на стенде получили подписку штатным
путём — выдачей администратора (`granted_by_admin_id`), как это делает
владелец в продукте. В остался без подписки: на нём проверяется отказ.

## 15. Правило переписки: сделано — `9cede1bb`

Расхождение из §13 закрыто решением владельца: переписку открывает дружба
ЛИБО подписка.

**Корень был не там, где казалось.** Клиент уже знал правило владельца: на
профиле «Написать» проверяет `is_friend` и открывает готовое окно
`FriendRequiredDialog` с текстом «Добавьте пользователя в друзья, чтобы
написать ему» — он лежал в проекте с тем самым заголовком, описанием и
кнопкой «Добавить», которые просил владелец. Сервер же требовал подписку
всегда. Друг без подписки проходил проверку клиента и получал 403, после
чего ему показывали окно подписки: просили заплатить за то, что по правилу
открыто.

| Что изменено | Где |
| :-- | :-- |
| Дружба ЛИБО подписка для `create` и `send` | `ConversationPolicy` |
| Получатель передаётся в политику | `StoreConversationController` |
| Код отказа пробрасывается любой, а не выбранный из списка | `AuthorizesSend` |
| Условие клиента приведено к серверному: дружба ЛИБО подписка | `ProfileView` |
| `friendship_required` открывает окно «Добавьте в друзья» | `ProfileView` |

**Трейт `AuthorizesSend` — отдельная находка.** Он пробрасывал наружу
только `subscription_required`, сравнивая код со строкой. Когда у политики
появился второй код, отказ по дружбе приехал клиенту пустым 403: окно не
открывалось, человек видел общий текст. Перечисление кодов в двух местах и
было той второй копией, которая расходится с первой; теперь решает только
политика.

**Дружбу спрашиваю у готового `FriendService::areFriends`.** Своего запроса
не завёл: он смотрит ту же таблицу, которую пишет при принятии заявки и
снимает при удалении из друзей. Поэтому «после удаления из друзей — отказ»
получается само, без отдельной проверки.

**Что не менялось:** участие в беседе, блокировки
(`UserService::assertCanInteract`), подтверждение телефона, чаты сделок.
Чаты направлений, сообществ и групп остались за подпиской: там собеседник не
один и взаимная дружба к ним не применима.

**Два существующих теста обновлены, а не откачены.** Они закрепляли код
`subscription_required` там, где теперь другая причина отказа. Сам отказ не
изменился — писать по-прежнему нельзя; изменилось то, что о нём сообщают, и
окно, которое от этого открывается.

**Семь проверок, каждая доказана откатом** (правило 3.2.5):

| Откат | Что краснеет |
| :-- | :-- |
| вернуть «только подписка» | друзья начинают, друзья отправляют, после удаления, заблокированный — **4** |
| отдать `create` всем | отказ не-другу — **1** |
| убрать подписчика из правила | «подписчик пишет не другу как раньше» — **1** |
| применить дружбу ко всем типам чатов | «подписка остаётся условием для чатов направлений» — **1** |

**Замеры в браузере** на 360 и 1280, учётки А (друг Б, без подписки), В (не
друг, без подписки), подписчик:

| Сценарий | 360 | 1280 |
| :-- | :-- | :-- |
| А → Б, друзья без подписки | переписка открылась | переписка открылась |
| А → В, не друзья без подписки | окно «Добавьте пользователя в друзья» | то же окно |
| подписчик → В, не друзья | переписка открылась | переписка открылась |

## 18. Поле ввода переписки — `1d7e8a4c`

Два требования ТЗ 3.7 и проверки M07, которых не было, **хотя намерение в
коде стояло**.

**Поле не росло.** У `textarea` были `rows={1}` и `maxHeight: 120`, но высоту
никто не считал: `maxHeight` оказался мёртвым намерением — поле оставалось в
одну строку и с первой же лишней прокручивалось внутри себя.

```
замер до правки, 360 и 1280: двенадцать строк текста → высота 24 px до и после
замер после правки:          24 → 120, дальше прокрутка внутри, за экран не выходит
```

Высота снимается с `scrollHeight` при сброшенной `height`: иначе
`scrollHeight` вернёт прежнюю высоту и поле не уменьшится, когда текст
стёрли.

**Enter отправлял во время композиции ввода.** Условие
`e.key === "Enter" && !e.shiftKey` истинно и посреди набора иероглифа: у
человека, набирающего китайский или японский, первое же подтверждение
символа отправляло недописанную строку. Добавлены `isComposing` и
`keyCode !== 229` — так о съеденном редактором ввода Enter сообщают браузеры,
где `isComposing` уже сброшен. Shift+Enter по-прежнему переносит строку.

Сторож на пять утверждений проверен откатом: снятие предела роста и снятие
проверки композиции валят по одному утверждению каждое.

## 7. Ложные находки этой сессии — и почему они возникли

Записано, чтобы следующая сессия не приняла их за дефекты и не «починила»
исправный код.

### 7.1. Семь страниц без `<h1>` и расхождение гидрации — моя сломанная база

Первый обход дал: пустой или отсутствующий `<h1>` на `/`, `/landing`,
`/how-to-use`, `/how-it-works`, `/payment`, `/refund`, `/rules/tariffs`;
расхождение гидрации React на `/landing` и `/channels`; по 3–6
исключений на страницу, одинаково в трёх прогонах подряд.

Выглядело убедительно: воспроизводимо, детерминированно, и расхождение
гидрации — ровно тот дефект, которому в `CLAUDE.md` отведён целый раздел.

Причина оказалась моя. Чтобы прогнать тесты так, как их гоняет CI, я
сменил пароль роли `modelizmclub` на `secret` — и не поправил
`backend/.env` стенда, где остался прежний. API начал отвечать 500 на
`select "value" from "system_settings" where "key" = 'branding.logo'`.
Сервер рисовал страницу без брендинга, браузер — с ним; отсюда и
расхождение гидрации, и пустой `<h1>` (его содержимое — название из
настроек брендинга).

После починки пароля и перезапуска API те же четыре страницы дают:

| Страница | `<h1>` | `pageerror` | `console.error` |
| :-- | :-- | --: | --: |
| `/` | «МоДелизМ» | **0** | **0** |
| `/channels` | «Каналы» | **0** | **0** |
| `/rules/tariffs` | «Тарифы и стоимость услуг» | **0** | **0** |
| `/how-to-use` | «Как пользоваться» | **0** | **0** |

Ни расхождения гидрации, ни пустых заголовков, ни единого исключения.

Урок для следующей сессии: **500 от API на стенде подделывает расхождение
гидрации**. Прежде чем искать причину в коде — проверить, что API отвечает
200. Один `curl` к `/api/v1/listings`.

### 7.2. `main=0` и `main=2` — снимок на середине перехода

Обход сообщил `main=0` на `/admin/design-system` и `main=2` на
`/settings` при 1280.

Ни то, ни другое не дефект. Гостя с `/admin/design-system` уводит на

`<main>` и один `<h1>` («Войти», «Профиль и аккаунт»).

Отсюда же: **счёт `<h1>` в обходе при выдержке 1,4 с недостоверен** —
заголовок части страниц дорисовывается позже. Любое попадание `h1=0`
проверяется отдельно с выдержкой не меньше 2,5 с, прежде чем попасть в
этот файл.

### 7.3. `opacity:0` на проде — измерения не было

Отозвано, разобрано в `baseline.md`. Короче: `curl -s` при отказе
соединения молчит, `grep` получает пустой ввод, `wc -l` отвечает 0, и ноль
читается как «скрытых узлов нет». Сеть к проду закрыта — измерения не было.

### 7.4. Два красных теста ВТБ — мой `.env`, не база

Первый прогон `php artisan test` с `backend/.env` стенда дал 2 падения в

Причина: CI гоняет `php artisan test --env=testing` с

С `--env=testing` оба теста проходят. Настоящая база — в `qa.md`.

### 7.5. Числовые `z-index` — не нарушение

20 совпадений в `frontend/src`. Каждое посмотрено: это локальные `z-[1]`…

шкалы `--z-*`. Править нечего.

## 20. Н1: верхний ряд категорий мессенджера разъезжается на телефоне

Жалоба владельца 05.10, настоящий телефон. Требование: один ряд, без
переноса, со своей прокруткой; вкладки не сжимаются и не меняют ширину от
счётчика; страница не двигается.

Начал с того, что названное уже стояло в коде: ряд — один
`flex … overflow-x-auto`, у вкладок `shrink-0`, у счётчика `tabular-nums` и
резерв места, у подписи — невидимая полужирная копия. То есть ни одна из
очевидных причин не подходила, и списать находку на «не воспроизвелось»
было нельзя: владелец заранее сказал мерить длинными подписями, счётчиками
из двух-трёх цифр и увеличенным шрифтом системы.

Условие «увеличенный шрифт» воспроизводится минимальным размером шрифта в
движке, как его задаёт настройка Android. Замер: ширины 320, 360, 390, 430
× шрифт обычный, 19 и 24 px — двенадцать замеров, учётка А, стенд здоров
(ответов 500 ноль, исключений ноль, баннер закрыт).

Нашлись **три** причины, и все три — число в пикселях там, где нужен запас.

### 20.1. У ленты была вторая ось прокрутки

Зону нажатия 44 px давал `TAP_TARGET_ROW_44` — псевдоэлемент
`position: absolute`, `h-11`, по центру кнопки высотой 32. Он вылезал за
кнопку на 6 px вниз. Лента объявлена `overflow-x: auto`, а когда одна ось
`auto`, вторая из `visible` тоже становится `auto` — то есть у ленты
заводилась вертикальная прокрутка.

| Шрифт | Высота ленты | Содержимое | Переполнение по вертикали |
| :-- | --: | --: | --: |
| обычный | 32 | 37 | **5** |
| минимум 19 px | 32 | 41 | **9** |
| минимум 24 px | 32 | 48 | **16** |

Одинаково на всех четырёх ширинах.

**Чего эта причина не объясняет.** Я проверил наклонный свайп настоящим
касанием (CDP, 18 px вбок и 6 px вверх за шаг): ряд по вертикали **не
уехал** ни на одной из четырёх ширин — Chromium на таком жесте залипает в
горизонтальную ось. Значит 5 px — настоящий дефект раскладки, но симптом
«разъезжается» объясняется не им, а двумя следующими. Записываю так, а не
«починил и симптом ушёл».

### 20.2. Жёсткая высота 32 ломается от увеличенного шрифта

При минимальном размере шрифта 24 px подпись занимает 36 px в кнопке
высотой 32 и вылезает из неё вместе с подчёркиванием активной вкладки.
Это видно глазами и это и есть «разъезжается».

### 20.3. Вкладка меняла ширину от счётчика

`min-w-[28px]` стоял с обещанием «место под „99+“ целиком». Обещание не
выполнялось **даже при обычном шрифте**:

| Шрифт | «99+» требует | Вкладка «Личные» | Прыжок |
| :-- | --: | :-- | --: |
| обычный | 30,1 px | 99,6 → 101,7 | 2,1 px |
| минимум 19 px | 46,5 px | 126,2 → 144,7 | 18,5 px |
| минимум 24 px | 55,5 px | 145,2 → 172,7 | 27,5 px |

Любое число в пикселях — догадка об одном размере шрифта, и человек с
увеличенным шрифтом системы её опрокидывает. Кружок при этом был зажат по
высоте на 18 px, когда цифры требовали 22 и 28.

### Правка

Высота 44 px задана самой кнопке (`minHeight`, не `height`) — так же, как
в `EntityTabs` (`h-11`), где этой беды нет именно поэтому; накладка убрана
за ненадобностью. У ленты явный `overflow-y: hidden` — ровно одна ось.
Место под счётчик держит невидимая копия «99+» в той же клетке сетки:
приём уже применён рядом, в `TabLabel`, для ширины полужирной подписи.
Высоты кружка и кнопки — нижними пределами.

### Проверено после правки

| Что | Было | Стало |
| :-- | :-- | :-- |
| Переполнение ленты по вертикали, 12 замеров | 5 / 9 / 16 | **0 на всех** |
| Ширина вкладки от счётчика «9» → «12» → «99+» | меняется на 2,1–27,5 px | **не меняется** |
| Высота кружка при шрифте 19 и 24 | 18 и 18 | 19 и 24 |
| Горизонтальная прокрутка страницы | 0 | 0 |
| Вид ряда на 360 и 1280, обычный и 24 px | — | один ряд, подчёркивание на месте |

### Побочный риск, который проверен и не подтвердился

`overflow-y: hidden` мог обрезать обводку фокуса на вкладке. Первый мой
вердикт был «риск есть» — и был ошибкой инструмента: он смотрел на запас
сверху и снизу (ноль) и не спросил про `outline-offset`, который всё и
решает. Правило в `styles.css` рисует кольцо внутрь (`outline-offset:
-2px`), обрезать нечего. Проверено снимком кнопки в фокусе с клавиатуры на
360 и 1280: кольцо видно со всех четырёх сторон.

### Сторож

`messenger-tabs-do-not-jump.test.ts`, пять утверждений, каждое доказано
откатом (`2 failed` у первого — он краснит и утверждение про 44, и
утверждение про жёсткие 32).

Отдельно: прежнее утверждение `toMatch(/TAP_TARGET_ROW_44/)` заменено на
требование настоящей высоты. Это строже — прежнее проходило и при кнопке
высотой 32. И оно едва не оказалось нестрогим само: `minHeight: 44` стоит
в файле ещё и у поля ввода, поэтому первый откат его не покраснил. Теперь
утверждение привязано к телу `tabButtonStyle`. Поймано откатом, а не
чтением.

### Что нашлось рядом и в Н1 не чинилось

У вкладок мессенджера есть `role="tab"`, но нет ни обхода по стрелкам, ни
`tabIndex` у невыбранных: в обход Tab попадают все четыре. Это тот же
дефект, что был у вкладок профиля и закрыт в сессии 4 переводом на
`EntityTabs`. Здесь перевести нельзя — четвёртый пункт ряда это меню
«Ещё», которого `EntityTabs` не умеет. Чинится в шаге 3 (мессенджер), не
расширяя правку Н1.

## 21. Н2: у видео в обзорах два набора настроек

Жалоба владельца 05.10: «при нажатии на видео дублируются элементы
управления качеством и скоростью; должен остаться один элемент настроек».

### Чтобы вообще измерить — пришлось завести видео

Обзоров на стенде было ноль (`select count(*) from videos` → 0). Завёл
один: файл в `storage/app/media/review_video/`, запись в `media` и запись
в `videos` от учётки А.

Две грабли по дороге, обе стоили бы ложного вывода:

1. **Назначение медиа берётся из пути.** `Media::getPurposeAttribute` —
   это второй сегмент `path`. Положил в `media/video/…` — прокси ответил
   403, потому что в списке публичных назначений есть `review_video`, а
   `video` нет. Не «права сломаны», а имя каталога.
2. **Эта сборка Chromium не умеет H.264.** Первый файл был `libx264`:
   `canPlayType('video/mp4; codecs="avc1.42E01E"')` возвращает пустую
   строку, `v.error.code = 4`, `readyState 0`. Проверка клавиатуры при
   этом показывала «пробел не сработал» — и это был бы ложный дефект.
   Перекодировал в VP9/WebM (`canPlayType` → `probably`), и пробел
   заработал. Правило «докажите, что инструмент работает» сработало ровно
   по назначению.

### Причина

У `<video>` стоит `controls`, то есть движок рисует своё меню, а в нём
**уже есть скорость воспроизведения**. Поверх него висела своя шестерёнка
`ReviewPlayerSettings` с той же скоростью.

Замер, учётка-подписчик, ширины 360 и 1280, родные элементы управления
достаты через CDP с `pierce` (без него теневое дерево движка не видно):

| Что | До правки | После |
| :-- | :-- | :-- |
| Своя кнопка «Настройки плеера» | 1, 36×36 | **0** |
| Родные `playback-speed-button`, `overflow-button` | есть | есть |
| **Наборов настроек** | **2** | **1** |

Отдельно: «Качество» в своей накладке выбора не предлагало **вовсе** —
подпись «Качество» и слово «Авто» текстом, без единого варианта. То есть
скорость дублировалась, а качество обещалось и не давалось.

### Правка

Убрана своя накладка: компонент удалён, использование со страницы снято,
подписи убраны из словаря. Родные элементы управления оставлены — они
работают с клавиатуры, читаются диктором и одинаковы на телефоне и на
компьютере; строить своё поверх них значит повторять за движком перемотку,
звук и полноэкранный режим.

Попутно ушло нарушение правила гидрации: накладка читала `localStorage` в
инициализаторе `useState` (`readReviewPlayerPrefs`), что `CLAUDE.md`
запрещает прямо.

### Проверено после правки

Подписчик, 360 и 1280, диалогов на странице ноль, ответов 500 ноль,
исключений ноль:

| Что | Результат |
| :-- | :-- |
| Наборов настроек | **1** (только родные) |
| Enter по «Смотреть» с клавиатуры | проигрыватель появляется |
| Видео в обходе фокуса | `tabIndex 0`, фокусируется |
| Пробел по видео | `paused false → true` — работает |

### Сторож

`reviews-player-single-settings.test.ts`, четыре утверждения, каждое
доказано откатом: вернуть файл компонента, вернуть использование, вернуть
ключи в словарь, убрать `controls` у видео — каждый откат краснит своё.

### Что нашлось попутно

**1. Учётка А — не подписчик**, вопреки записи в `screens.md`. По базе
активная подписка одна, у `ff-sub` (id 7). Запись в журнале поправлена.
На выводы сессии 4 это не влияет: там А нужна была именно без подписки.

**2. Окно «Нужна подписка» открывается на странице обзора само** и
перехватывает фокус: `focus()` на кнопку «Смотреть» откатывался на кнопку
«Оформить подписку» внутри окна. Из-за этого первая проверка клавиатуры
показывала «Enter не запускает проигрыватель» — это было про окно, а не
про проигрыватель. Законно ли, что при этом под окном отрисован рабочий
проигрыватель, **не проверял**: это вопрос доступа, он относится к шагу 4,
и ставлю его там, а не чиню заодно.

## 22. Н3: меню «Поделиться» в ленте не помещается на экране телефона

Жалоба владельца 05.10: «пост, развёрнутый стрелкой — блок „Поделиться“
сместился; кнопки над ним нажимаются, но не видны».

### Три ложных следа по дороге — и почему каждый был незамером

Записываю их, потому что каждый выглядел как находка.

**1. «После разворота все четыре кнопки панели провалили проверку».** Так
и печатала первая проверка: в центрах кнопок стояли `path`, `svg`,
`a.flex.min-w-0`. На деле карточка после разворота выросла с 227 до 572 px,
подвал уехал на y=993 при окне 844 — то есть **за нижний край экрана**, а
`elementFromPoint` вне видимой области возвращает `null`. Мой «чужой слой»
был пустотой. Проверка исправлена: каждую кнопку сперва подводим к экрану.
После этого негодных кнопок **ноль** — и до разворота, и после, на 360 и
1280.

**2. «Меню не открывается».** Программный `.click()` по кнопке меню не
открывал ничего: это меню, как и Radix, слушает `pointerdown`. Та же
грабля, что в сессии 4 с вкладкой «Ещё».

**3. «Слоёв 0».** Поиск меню по `[role="menu"]` ничего не находил, хотя на
снимке меню было открыто: роли у него нет вовсе. Нашлось поиском по
содержимому и ближайшему позиционированному предку.

Все три отвечали «не измерялось», а выглядели как «не воспроизвелось».
Разрешил их снимок экрана: на нём меню видно, и видно, что оно обрезано.

### Причина

Меню стояло `absolute bottom-full left-0 w-[260px]` — отсчёт от **левого
края своей кнопки**. Кнопка «Репост» третья в строке действий, её левый
край на 115 px, и меню занимало 115…375 при любой ширине экрана.

Замер, лента, настоящее касание, пять ширин:

| Ширина | Меню | За правым краем | Пункты |
| --: | :-- | --: | :-- |
| 320 | 115…375 | **55 px** | все три обрезаны |
| 360 | 115…375 | **15 px** | все три обрезаны |
| 390 | 115…375 | 0 | целиком |
| 430 | 115…375 | 0 | целиком |
| 1280 | 414…674 | 0 | целиком |

Горизонтальной прокрутки у страницы при этом **не появлялось** — поэтому
обычные ворота «ноль горизонтальной прокрутки на 320/360/390», которые
прошли 232 замера в промпте 00, этот дефект не ловили и поймать не могли.

### Чего причина не объясняет

«Кнопки над ним нажимаются, но не видны» я **не воспроизвёл**. Панель
действий лежит ниже меню, а не выше; выше меню — текст записи, и меню его
закрывает, как и положено открытому меню. Проверка владельца («у каждой
кнопки ненулевой размер и в её центре она сама») на исправленном замере
даёт ноль негодных кнопок до и после разворота. Записываю как есть и

### Правка

### Главный вывод: единого признака нет

Флага «демо» в схеме нет ни у одной таблицы — поиск по

столбца приложения. Признак у каждой таблицы свой:

| Таблица | Признак | На стенде |
| :-- | :-- | --: |
| `posts` | автор — `demo@modelizmclub.ru` или `admin@modelizmclub.ru` | 11 из 12 |
| `listings` | владелец — те же учётки | 10 из 10 |

| `videos` | загрузивший — те же учётки | 0 из 1 |
| `communities` | **`created_by` пуст** | 2 из 2 |

Сообщества выпадают из общего правила, и это важно: семя не ставит им
владельца вовсе. Признак «владелец — показательная учётка» их **не ловит**
— первый мой подсчёт дал по сообществам ноль, и это была ошибка признака,

Учётки семян на стенде: id 1 `demo@modelizmclub.ru` «Demo User» и id 2
`admin@modelizmclub.ru` «Admin User» (роль Владелец).

### Команда

`php artisan demo:content` — по образцу `CleanupSmokePostsCommand`,
который в проекте уже есть, а не своего покроя.

```bash
php artisan demo:content                     # перепись, ничего не меняет
php artisan demo:content --hide              # скрыть (обратимо)
php artisan demo:content --hide --dry-run    # что скрылось бы
php artisan demo:content --purge --dry-run   # что удалилось бы
php artisan demo:content --purge             # удалить (мягко)
```

Скрытие — **существующим механизмом**, тем же состоянием, которым
пользуется модерация, а не новым полем:

| Таблица | Как скрывается | Почему так |
| :-- | :-- | :-- |
| `posts` | `ContentStatus::Hidden` | значение уже есть в перечислении |
| `videos` | `'hidden'` | состояние строкой; публичная выборка смотрит `status = 'published'` |
| `listings` | `ListingStatus::Unpublished` | значения `hidden` в этом перечислении нет |
| `communities` | `CommunityStatus::Draft` | непубличное и обратимое |
| `channels` | `is_active = false` | состояния у канала нет вовсе |

`--hide` и `--purge` вместе отвергаются с ненулевым кодом.

### Выполнено на стенде

```
$ php artisan demo:content --hide
posts 11, listings 10, channels 7, videos 0, communities 2 — скрыто
Затронуто строк: 30.
```

Публичная выдача объявлений: **10 → 0**. В базе при этом записей 12,
объявлений 10, каналов 7, сообществ 2 — **всё на месте**, удалено ничего.

**Как вернуть:** состояния до скрытия были одинаковые (`published` у
записей и объявлений, `active` у сообществ, `is_active = true` у каналов),
поэтому возврат точный:

```sql
update posts set status='published' where status='hidden' and user_id in (1,2);
update listings set status='published' where status='unpublished' and user_id in (1,2);
update channels set is_active=true where owner_id in (1,2);
update communities set status='active' where created_by is null;
```

### На проде ничего не делалось

Граница сессии — не выкатывать и не трогать живые данные. Команда и
перепись готовы; на проде их запускает владелец, и начинать надо с
`php artisan demo:content` без флагов: числа там свои, и прежде чем что-то
скрывать, их надо увидеть.

### Сторож

`DemoContentCommandTest`, семь проверок, три отката: пробный прогон
начинает действовать (краснит **два** теста), скрытие перестаёт скрывать,
признак расширен на всех авторов.

**Один сторож из семи сначала был мёртвым.** «Пробный прогон удаления

## 25. Метка «Новые сообщения» пропадала при заходе по прямой ссылке

Шаг 3 задания: метка «Новые сообщения».

Сама метка работает верно. Замер, учётка А, три непрочитанных от Б:
одна метка, подпись «Новые сообщения», ниже неё **ровно три** сообщения,
первое из них — первое непрочитанное, метка в видимой области. На 360 и
1280.

Но только при **одном** из двух входов.

| Как вошли | Меток |
| :-- | --: |
| прямая ссылка `?chat=…` | **0** |
| переход внутри приложения (нажать диалог в списке) | 1 |

Ровно тот случай, про который `CLAUDE.md` предупреждает: «для маршрута —
ещё и оба входа: прямая загрузка и переход внутри приложения; они идут по
разным веткам». Под прямую ссылку попадают переход из уведомления,
присланная ссылка и обычная перезагрузка страницы, когда переписка открыта.

### Причина

Отметка о прочтении двигает курсор прочитанного на последнее сообщение, а
по этому курсору считается, где начинается непрочитанное. Отметка шла
**раньше** разбора границы — и стирала то, что граница должна была
показать.

Мест, где она отправлялась, было два, и оба срабатывали до загрузки
сообщений:

- `selectDialog` в эффекте синхронизации с `?chat=` — в тот же миг, когда
  диалог нашёлся в списке;
- `handleSelect` при нажатии на строку списка;
- плюс отдельный эффект `useEffect(() => markRead(activeId), [activeId])`.

При переходе внутри приложения это сходило с рук случайно: список диалогов
уже загружен, и эффект границы успевал прочитать прежний курсор в том же
проходе. Порядок был не задан, а совпал.

### Правка

Отметка уходит из одного места и ждёт, пока граница разобрана. Разбор
сообщает о себе состоянием `anchorResolvedFor`, а не только ref: от него
зависит отметка, и она должна уйти следующим проходом.

Запасной выход — если диалога нет в уже загруженном списке (удалён,
чужой), якорю взяться неоткуда, и отмечаем как раньше.

### Моя же правка сначала не работала — и показательно, почему

Первая попытка запасного выхода была записана как «диалога нет в списке →
отмечаем». Это срабатывало ровно в том окне, которое правка защищает: при
заходе по прямой ссылке список ещё пуст, диалог «не найден», отметка
уходит первой. Замер после правки дал те же **0 меток**, что и до неё.

Нашлось не чтением, а временной отладкой прямо в эффекте: она напечатала,
что курсор уже стоит на последнем сообщении (индекс 49 из 50) и
непрочитанных ноль. До этого я успел дважды ошибиться в догадке — думал на
клиентскую отметку из другого места, потом на сервер. Сервер проверен
отдельно: `GET /conversations/{uuid}/messages` курсор **не двигает**
(непрочитано 3 до и 3 после).

Условие исправлено на «список загружен **и** диалога в нём нет».

### Проверено после правки

| Вход | Меток | Ниже метки | Непрочитано |
| :-- | --: | --: | :-- |
| прямая ссылка `?chat=` | 1 | 3 | 3 → **0** |
| переход внутри приложения | 1 | 3 | 3 → **0** |

Счётчик гаснет на обоих входах — отметка отложена, а не отменена. Это
важнее самой границы: не гаснущий счётчик заметят все.

вернуть отметку в разбор адреса, вернуть её в выбор диалога, убрать

## 28. Шаг 4: счётчик реакций не двигался, отказ сохранения молчал, у закладки было выдуманное число

Три находки, и первые две — одна причина.

### 28.1. Реакция ставилась, а число не менялось

Замер 06.10, страница записи, учётка А. В базе после нажатия: реакция
есть, `reactions_count` = 1. На экране сердце закрашено. А в кнопке:

```html
<span class="tabular-nums" style="opacity: 0; transform: none;">0</span>
```

То есть числа на экране **нет ни старого, ни нового**: уходящий узел
застрял с нулевой непрозрачностью, приходящий не смонтировался.

**Причина не в счётчике.** Соседний `m.span` анимировал сердце тремя
кадрами `scale: [1, 1.35, 1]` с `type: "spring"`. framer-motion так не
умеет и бросает исключение:

```
Only two keyframes currently supported with spring and inertia animations.
Trying to animate 1,1.35,1.
```

Исключение рвало работу framer-motion, и `AnimatePresence` внутри
`ReducedMotionSwitch` не доводил смену числа. При этом в самом
`PostActions` стоит докблок, объясняющий, что `ReducedMotionSwitch`
заводился лечить ровно эту беду. Он её и лечит — пока ему не мешают.

`tween` с `times` даёт тот же отскок и допускает три кадра. Одна правка
сняла и исключение на странице, и застывший счётчик: после неё 0 → **1**,
`opacity: 1`, и это совпадает с базой.

Исключение, к слову, нарушало и общие ворота: «ноль исключений на
странице». Обход маршрутов в промпте 00 его не поймал, потому что оно
возникает только при нажатии, а обход только открывал страницы.

### 28.2. Отказ сохранения молчал

Запрос оборван: закладка на миг загоралась и гасла — **без единого слова**.
У реакции и у репоста рядом сообщение есть, у сохранения не было.

Ворота `check-empty-catch.sh` такое не ловят: обработчик не пустой, он
делает откат. Правило в `CLAUDE.md` смотрит не на пустоту, а на то, что
человек нажал и ждёт ответа. Теперь объявляется.

### 28.3. У закладки стояло число, которого не существует

Сервер его не отдаёт: в `stats` записи лежат просмотры, реакции,
комментарии и репосты, закладок там нет. Клиентский преобразователь
подставляет `saves: 0` в пяти местах. Значит условие `saves > 0`
выполнялось ровно в одном случае — сразу после своего нажатия, когда
оптимистичное обновление прибавляло единицу.

| Когда | Что показано |
| :-- | :-- |
| сразу после нажатия | «1» |
| после перезагрузки | пусто |

Человек видел «1» рядом с закладкой, что читается как «один человек
сохранил», а это было его собственное нажатие, исчезающее при обновлении.

Рядом, у просмотров, этот вывод в коде уже сделан: «ноль под каждой
карточкой — это не факт о записи, а сообщение о том, что счётчик не
работает». Здесь то же самое, только числа нет и на сервере. Число убрано,
закрашенная закладка осталась — `viewer.bookmarked` настоящее состояние.

### Проверено после правок: одинаковое состояние во всех списках

Действия на странице записи, затем три захода заново:

| Где | Реакция | Закладка |
| :-- | :-- | :-- |
| страница записи сразу | 1 / выделено | (пусто) / выделено |
| лента | 1 / выделено | (пусто) / выделено |
| профиль автора | 1 / выделено | (пусто) / выделено |
| страница записи заново | 1 / выделено | (пусто) / выделено |

В базе: реакций 1, закладок 1, счётчик 1. Исключений **ноль**.

Откат при отказе проверен обрывом запроса для обоих действий: состояние
возвращается, и оба отказа теперь объявляются.

## 29. Шаг 5: отбор каталога из адреса терялся молча, отказ обновления тоже

### 29.1. `/ads?category_id=…` не доезжал до запроса

Отбор проходит путь «идентификатор из адреса → имя раздела → обратно в
идентификатор». Средним звеном служит дерево каталога из
`/public/bootstrap`, и оно строится **не** из `listing_categories`
напрямую, а из «видимых зеркал» направлений
(`CategoryTaxonomyService::visibleMirrorIds`). Нет зеркал — дерево пустое —
имя не находится ни для какого идентификатора, и отбор молча исчезает.

Состояние стенда (замер 06.10): 30 направлений, у всех `in_listings`, **ни
у одного** нет `listing_category_id`; `listing_categories` в ответе
`bootstrap` — **ноль элементов**.

| Адрес | Запрос к API до правки | После |
| :-- | :-- | :-- |
| `/ads?q=Tamiya` | `?q=Tamiya&per_page=24&sort=new` | то же |
| `/ads?category_id=1` | **`?per_page=24&sort=new`** | `?category_id=1&…` |
| `/ads?category_id=999` | **`?per_page=24&sort=new`** | `?category_id=999&…`, выдача пуста |

API параметр понимает: `category_id=1` → одно объявление, `999` → ноль.
То есть ломался только путь от адреса до запроса.

Под эту же потерю попадали **крошки на странице объявления**: они ведут
ровно на такой адрес, и в коде рядом стоит комментарий «адрес каталога
понимает category_id/subcategory_id». Понимал маршрут, а запрос — нет.

**Правка.** Если дерево не знает раздела, идентификатор берётся прямо из
адреса: имена нужны панели для показа, а запросу достаточно числа.
Подстановка работает, только пока человек не выбрал раздел сам.

Попутно: `categoryId` и `subcategoryId` участвовали в запросе, но
отсутствовали в зависимостях `load`. Смена одного лишь адреса (переход по
крошке с раздела на раздел) ушла бы со старым идентификатором из
замкнутого окружения. Добавлены.

**Про прод.** Пусто ли дерево и там — проверить из контейнера нельзя.
Запрос для владельца:

```sql
select count(*) from post_categories where in_listings and listing_category_id is not null;
```

Ноль означает, что отбор каталога по разделам не работал и на проде, а
правка выше его чинит независимо от зеркал.

### 29.2. Неудачное обновление каталога ничего не говорило

Стояло:

```js
} catch {
  if (!refreshing) setLoadState("error");
}
```

`refreshing` истинно после первой успешной загрузки — значит **любой**
последующий отказ не оставлял следа. И состояние ошибки отрисовывалось
только при `!hasLoadedOnce`.

Замер: каталог открыт, запрос к `/listings` оборван, выбрана сортировка
«Сначала дешевле». На экране — прежняя выдача «Найдено: 1 объявление»,
сообщений ноль, кнопки «Повторить» нет. Человек читает старый список как
ответ на новый отбор.

**Правка.** Прежнюю выдачу не стираем — она настоящая, просто не та, о
которой просили, — но отказ объявляется: «Не удалось загрузить
объявления». Первая неудачная загрузка по-прежнему даёт состояние с
«Повторить». Догрузка следующей страницы записывает отказ через
`reportReadFailure` вместо голого `catch`.

### Измерять отказ пришлось дважды

Первый замер обрывал браузерные запросы и показывал, что страница
спокойно отрисовала список. Это был незамер: загрузчик маршрута работает
**на сервере**, и перехват браузерных запросов до него не достаёт. Настоящий
отказ получается только перезапросом из браузера — сменой сортировки. Со
второй попытки сортировка тоже не нашлась: это `<select>`, а я искал
кнопки.

### Что в шаге 5 прошло без правок

| Что | Результат |
| :-- | :-- |
| `?q=` в адресе | уходит в запрос и восстанавливается в поле поиска |
| Пустая выдача | «Найдено: 0 объявлений», «Сбросить фильтры», «Разместить объявление» |
| Избранное, обычный ход | «В избранное» → «В избранном», в базе 1 |
| Избранное, запрос оборван | откат + «Не удалось обновить избранное», в базе 0 |
| Избранное в разных местах | страница «В избранном», каталог и `/favorites` — «Убрать из избранного» |
