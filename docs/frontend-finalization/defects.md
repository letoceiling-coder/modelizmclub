## 8. D4 — состав нижней панели (единственный подтверждённый дефект)

Воспроизведено на стенде, `/feed`, гостем, ширины 320 и 360.

D4 требует пять пунктов: **Лента, Сообщества, Сообщения, Объявления,
Профиль**, а Друзья — «в профиле и меню».

Фактически панель рисует пять пунктов, но состав другой:

| Ширина | Пункты | Колонки |
| :-- | :-- | :-- |
| 320 | Лента · Сообщения · Объявления · Профиль · **Друзья** | 5 × 64 px |
| 360 | Лента · Сообщения · Объявления · Профиль · **Друзья** | 5 × 72 px |

То есть: **«Сообщества» отсутствует**, **«Друзья» присутствует**. Пять
получилось по совпадению — один нужный пункт пропал, один ненужный встал.

Почему пропали «Сообщества»: `src/components/layout/BottomNav.tsx:35`
отсеивает пункт по признаку `communitiesEnabled`, а
`FeatureFlagsSeeder.php:13` задаёт `feature.communities_enabled = false`.
На стенде признак выключен. **На проде он может быть включён — и тогда
панель покажет шесть пунктов**, то есть разойдётся с D4 ещё и числом.

«Друзья» не отсеиваются никогда: в `ALL_ITEMS` шесть записей, и
единственный фильтр — на `/communities`. Прочитан весь компонент, не
фрагмент.

Что при этом в порядке и портить не надо:

- зона нажатия 64×60 px при 320 и 72×60 при 360 — внутренняя норма 44×44
  соблюдена с запасом;
- подписи не обрезаны ни на одной ширине (`scrollWidth == clientWidth` у
  всех пунктов), то есть требование «на 320 px подписи не сталкиваются»
  выполнено;
- слой берётся из шкалы (`z-[var(--z-sticky)]`), безопасная зона учтена
  один раз (`padding-bottom: var(--safe-bottom)`).

Правка — шаг 3 промпта 01, вместе со сторожевым тестом на пять пунктов,
который требует гейт того же промпта. **В этой сессии не делалась**, и
проверка «а есть ли Друзья в профиле и меню» выполнена — её итог меняет
состав правки.

### Условие, без которого правку делать нельзя

D4 переносит Друзей «в профиль и меню». На телефоне выполнено только
первое:

| Вход в Друзей | Где | Видно на телефоне (< 768 px) |
| :-- | :-- | :-- |
| Нижняя панель | `BottomNav.tsx:28` | да — это и предлагается убрать |
| Профиль (свой) | `ProfileView.tsx:632`, `href={isOwn ? "/friends" : undefined}` | да |
| Боковая колонка | `Sidebar.tsx:70` | **нет** |
| Меню аватара | — | **нет, пункта не существует** |

`Sidebar.tsx:418` показывает колонку классом `w-16 md:flex xl:hidden`, то
есть от 768 px и шире; `BottomNav` — наоборот, `md:hidden`. На телефоне
панель остаётся единственной навигацией.

Меню аватара прочитано целиком: Админка, Профиль, Мои объявления, Сделки,
Кошелёк, Подписка, Приглашения. **Друзей там нет.**

Значит, если просто убрать пункт из панели, на телефоне останется один
путь — через свой профиль, в два нажатия вместо одного, а «и меню» из D4
не будет выполнено вовсе.

**Поэтому правка состоит из двух частей, и вторая обязательна:** убрать
«Друзей» из `BottomNav` **и** вернуть раздел в меню. Счётчик входящих заявок
(`useIncomingFriendRequestCount`) нужно перенести вместе с пунктом, иначе
человек перестанет видеть заявки.

## 9. Маршруты с параметрами: два дефекта

Обход дополнен 10 маршрутами с настоящими идентификаторами из базы стенда,
4 ширины = 40 загрузок. **Горизонтальной прокрутки нет ни на одной,
исключений нет ни одного.** Два замечания подтвердились с выдержкой 3,2 с.

### 9.1. `/post/{uuid}` — ни одного заголовка

Страница записи отвечает 200, содержимое настоящее, `<main>` один — но
**ни `<h1>`, ни `<h2>` на странице нет вовсе**.

```
адрес=/post/00000000-0000-4000-8000-000000000101
окно=«Сборка P-51 Mustang 1:48 — МоДелизМ»
main=1  h1=[]  h2=[]
сверху: К ленте · Demo User · 28 мин назад · Авиация · Сборка P-51 Mustang 1:48
```

Название записи выводится и даже попадает в заголовок окна, но разметкой
заголовка не является. Воспроизводится на всех четырёх ширинах, то есть это
не выдержка замера, а состояние страницы.

Это нарушение гейта 3.5.3 («ровно один `<h1>` на странице») на одной из
самых посещаемых страниц, и одновременно вопрос доступности: по заголовкам
такую страницу не обойти.

Правка — волна F4 (единая карточка записи, ТЗ 3.3): название записи должно
быть `<h1>` страницы.

### 9.2. Страница 404 без ориентира `<main>`

```
адрес=/rules/consent → HTTP 404
main=0  h1=["404"]  h2=["Страница не найдена"]
```

Заголовок есть и текст понятный — а `<main>` нет. Гейт 3.5.3 требует ровно
один; служебные страницы под это требование попадают так же, как
остальные, и шаг 4 промпта 06 их отдельно называет.

### 9.3. Две мои ошибки в этой же проверке — не дефекты

Чтобы следующая сессия не занесла их в дефекты:

- **`/ads/1`** отвечает «Объявление не найдено». Числовой `id=1` из таблицы
  `listings` этому маршруту не подходит — нужен другой идентификатор.
  Проверка неубедительна, маршрут надо перепроверить с верным значением,
  а не считать сломанным.
- **`/rules/consent`** отвечает 404 закономерно: `consent` — слуг из
  `legal_pages`, и живёт он под `/legal/`, а не под `/rules/`. `/legal/rules`
  и `/legal/privacy` прошли обход без замечаний. Дефект здесь только тот,
  что описан в §9.2 — отсутствующий `<main>` у самой страницы 404.

## 10. Счётчик заявок в друзья пропал с телефона — исправлено

Нашлось по ответу владельца 3: «проверь, что счётчик входящих заявок виден

колокольчика рядом) и у строки «Друзья» внутри шторки.

Замер после правки на 360: на кнопке «1», в шторке «Друзья 1»; у гостя ни

## 12. Вкладки при свайпе: не воспроизведено, но свойство добавлено

Настоящим касанием (`Input.dispatchTouchEvent` через CDP) на 360:

| :-- | :-- | :-- |
| Мессенджер | 8 → 163 из 163 | X=0 Y=0, не сдвинулась |
| Профиль | 0 → 290 из 557 | X=0 Y=0, не сдвинулась |

ровно симптом «вкладки вылетают». В эмуляции эта разница не видна, на
настоящем телефоне видна.

`ui/tabs`, вкладкам сущностей и вкладкам профиля. Прокрутку внутри ленты это
не меняет: после правки лента профиля прокручивается 0 → 296 из 557,
страница не двигается. Подтверждение самого симптома —
`BLOCKED: проверяет владелец`.

Карточки админки, крошки и сетки картинок с `overflow-x-auto` не трогал:
это не вкладки.

### 12.1. Два инструмента, которые мерили не то

Записано, чтобы следующая сессия не повторила и не завела ложный дефект.

**Мышиное протягивание не прокручивает контейнер.** Первый замер
протаскивал ленту мышью: у мессенджера прокрутка пошла, у профиля нет, и
профиль выглядел сломанным. На деле мышь вообще не прокручивает
`overflow-x-auto` — у мессенджера на жест отвечает своя обработка
(`drag-scroll-x` в `HorizontalScrollNav`), у профиля родное поведение,
которое отвечает на касание. Замер сравнивал разные механизмы.

**События касания, созданные в JS, не управляют родной прокруткой.** Второй
замер рассылал `TouchEvent` из `page.evaluate` — обе ленты не двинулись, и
теперь «сломанными» выглядели обе. Родная прокрутка идёт от настоящего
ввода, а не от событий, собранных в JS.

Годится только настоящий ввод: `Input.dispatchTouchEvent` через CDP. Прежде
чем записывать «не прокручивается», надо показать, что инструмент вообще
умеет прокручивать — на ленте, про которую это известно.

### 12.2. Вкладки профиля — не вкладки для доступности

На `/profile` при 360 весь перечень ролей на странице — `{"status": 1}`.
То есть у ленты из семи вкладок («Публикации», «Репосты», «Объявления»,
«Отзывы», «Сообщества», «Приглашённые», «Заблокированные») нет ни
`role="tablist"`, ни `role="tab"`: это кнопки в прокручиваемом `div`.
Клавиатурой и экранным диктором такая лента вкладками не читается.

Шаг 4 промпта 01 требует «один компонент» для вкладок. Профиль свою ленту
собирает сам, а не общим `ui/tabs`, который роли даёт. Это работа волны F1,

сессию не поместилась.

## 13. Переписку закрывает подписка, а не дружба — спорит с D2

Воспроизведено запросом и в интерфейсе.

D2: «„Написать“ проверяет дружбу, а не подписку. Подписчик пишет как
раньше.»

Фактически `app/Policies/ConversationPolicy.php`:

```php
public function create(User $user): bool
{
    return $this->isSubscriber($user);   // строка 28
}
```

и `send()` (строка 48) — тоже подписчик, кроме чата сделки.

Проба: А и Б — друзья, оба с подтверждённым телефоном, подписки нет.

```
POST /api/v1/conversations {"user_id":5}
→ 403 {"message":"Оформите подписку, чтобы начинать переписку.",
       "code":"subscription_required"}
```

То есть двое друзей без подписки переписываться не могут вовсе, а D2
говорит, что решать должна дружба.

**Не правил, и вот почему.** Это не вёрстка, а правило доступа, за которым
стоят деньги: подписка — то, за что платят. `CLAUDE.md` требует проверять
такие правки на стенде под всеми затронутыми состояниями, а менять их
вообще разрешено только «сверх решений раздела 2» — и формулировка D2
допускает два чтения: «так должно быть на сервере» и «так должна вести себя
кнопка „Написать“ в интерфейсе». Разница между ними — платная функция,
отданная бесплатно.

Вынесено владельцу в `MORNING.md` вопросом «да или нет».

Чтобы проверить сам мессенджер, А и Б на стенде получили подписку штатным
путём — выдачей администратора (`granted_by_admin_id`), как это делает
владелец в продукте. В остался без подписки: на нём проверяется отказ.

## 15. Правило переписки: сделано — `9cede1bb`

Расхождение из §13 закрыто решением владельца: переписку открывает дружба
ЛИБО подписка.

**Корень был не там, где казалось.** Клиент уже знал правило владельца: на
профиле «Написать» проверяет `is_friend` и открывает готовое окно
`FriendRequiredDialog` с текстом «Добавьте пользователя в друзья, чтобы
написать ему» — он лежал в проекте с тем самым заголовком, описанием и
кнопкой «Добавить», которые просил владелец. Сервер же требовал подписку
всегда. Друг без подписки проходил проверку клиента и получал 403, после
чего ему показывали окно подписки: просили заплатить за то, что по правилу
открыто.

| Что изменено | Где |
| :-- | :-- |
| Дружба ЛИБО подписка для `create` и `send` | `ConversationPolicy` |
| Получатель передаётся в политику | `StoreConversationController` |
| Код отказа пробрасывается любой, а не выбранный из списка | `AuthorizesSend` |
| Условие клиента приведено к серверному: дружба ЛИБО подписка | `ProfileView` |
| `friendship_required` открывает окно «Добавьте в друзья» | `ProfileView` |

**Трейт `AuthorizesSend` — отдельная находка.** Он пробрасывал наружу
только `subscription_required`, сравнивая код со строкой. Когда у политики
появился второй код, отказ по дружбе приехал клиенту пустым 403: окно не
открывалось, человек видел общий текст. Перечисление кодов в двух местах и
было той второй копией, которая расходится с первой; теперь решает только
политика.

**Дружбу спрашиваю у готового `FriendService::areFriends`.** Своего запроса
не завёл: он смотрит ту же таблицу, которую пишет при принятии заявки и
снимает при удалении из друзей. Поэтому «после удаления из друзей — отказ»
получается само, без отдельной проверки.

**Что не менялось:** участие в беседе, блокировки
(`UserService::assertCanInteract`), подтверждение телефона, чаты сделок.
Чаты направлений, сообществ и групп остались за подпиской: там собеседник не
один и взаимная дружба к ним не применима.

**Два существующих теста обновлены, а не откачены.** Они закрепляли код
`subscription_required` там, где теперь другая причина отказа. Сам отказ не
изменился — писать по-прежнему нельзя; изменилось то, что о нём сообщают, и
окно, которое от этого открывается.

**Семь проверок, каждая доказана откатом** (правило 3.2.5):

| Откат | Что краснеет |
| :-- | :-- |
| вернуть «только подписка» | друзья начинают, друзья отправляют, после удаления, заблокированный — **4** |
| отдать `create` всем | отказ не-другу — **1** |
| убрать подписчика из правила | «подписчик пишет не другу как раньше» — **1** |
| применить дружбу ко всем типам чатов | «подписка остаётся условием для чатов направлений» — **1** |

**Замеры в браузере** на 360 и 1280, учётки А (друг Б, без подписки), В (не
друг, без подписки), подписчик:

| Сценарий | 360 | 1280 |
| :-- | :-- | :-- |
| А → Б, друзья без подписки | переписка открылась | переписка открылась |
| А → В, не друзья без подписки | окно «Добавьте пользователя в друзья» | то же окно |
| подписчик → В, не друзья | переписка открылась | переписка открылась |

На 360 первый замер сценария А → Б сказал «кнопки нет» — это выдержка на

## 18. Поле ввода переписки — `1d7e8a4c`

Два требования ТЗ 3.7 и проверки M07, которых не было, **хотя намерение в
коде стояло**.

**Поле не росло.** У `textarea` были `rows={1}` и `maxHeight: 120`, но высоту
никто не считал: `maxHeight` оказался мёртвым намерением — поле оставалось в
одну строку и с первой же лишней прокручивалось внутри себя.

```
замер до правки, 360 и 1280: двенадцать строк текста → высота 24 px до и после
замер после правки:          24 → 120, дальше прокрутка внутри, за экран не выходит
```

Высота снимается с `scrollHeight` при сброшенной `height`: иначе
`scrollHeight` вернёт прежнюю высоту и поле не уменьшится, когда текст
стёрли.

**Enter отправлял во время композиции ввода.** Условие
`e.key === "Enter" && !e.shiftKey` истинно и посреди набора иероглифа: у
человека, набирающего китайский или японский, первое же подтверждение
символа отправляло недописанную строку. Добавлены `isComposing` и
`keyCode !== 229` — так о съеденном редактором ввода Enter сообщают браузеры,
где `isComposing` уже сброшен. Shift+Enter по-прежнему переносит строку.

Сторож на пять утверждений проверен откатом: снятие предела роста и снятие
проверки композиции валят по одному утверждению каждое.

## 7. Ложные находки этой сессии — и почему они возникли

Записано, чтобы следующая сессия не приняла их за дефекты и не «починила»
исправный код.

### 7.1. Семь страниц без `<h1>` и расхождение гидрации — моя сломанная база

Первый обход дал: пустой или отсутствующий `<h1>` на `/`, `/landing`,
`/how-to-use`, `/how-it-works`, `/payment`, `/refund`, `/rules/tariffs`;
расхождение гидрации React на `/landing` и `/channels`; по 3–6
исключений на страницу, одинаково в трёх прогонах подряд.

Выглядело убедительно: воспроизводимо, детерминированно, и расхождение
гидрации — ровно тот дефект, которому в `CLAUDE.md` отведён целый раздел.

Причина оказалась моя. Чтобы прогнать тесты так, как их гоняет CI, я
сменил пароль роли `modelizmclub` на `secret` — и не поправил
`backend/.env` стенда, где остался прежний. API начал отвечать 500 на
`select "value" from "system_settings" where "key" = 'branding.logo'`.
Сервер рисовал страницу без брендинга, браузер — с ним; отсюда и
расхождение гидрации, и пустой `<h1>` (его содержимое — название из
настроек брендинга).

После починки пароля и перезапуска API те же четыре страницы дают:

| Страница | `<h1>` | `pageerror` | `console.error` |
| :-- | :-- | --: | --: |
| `/` | «МоДелизМ» | **0** | **0** |
| `/channels` | «Каналы» | **0** | **0** |
| `/rules/tariffs` | «Тарифы и стоимость услуг» | **0** | **0** |
| `/how-to-use` | «Как пользоваться» | **0** | **0** |

Ни расхождения гидрации, ни пустых заголовков, ни единого исключения.

Урок для следующей сессии: **500 от API на стенде подделывает расхождение
гидрации**. Прежде чем искать причину в коде — проверить, что API отвечает
200. Один `curl` к `/api/v1/listings`.

### 7.2. `main=0` и `main=2` — снимок на середине перехода

Обход сообщил `main=0` на `/admin/design-system` и `main=2` на
`/settings` при 1280.

Ни то, ни другое не дефект. Гостя с `/admin/design-system` уводит на
`/login`, а `/settings` — на `/settings/account`; обход измерял страницу в
момент перехода. С выдержкой 2,5 с вместо 1,4 с на обеих ровно один
`<main>` и один `<h1>` («Войти», «Профиль и аккаунт»).

Отсюда же: **счёт `<h1>` в обходе при выдержке 1,4 с недостоверен** —
заголовок части страниц дорисовывается позже. Любое попадание `h1=0`
проверяется отдельно с выдержкой не меньше 2,5 с, прежде чем попасть в
этот файл.

### 7.3. `opacity:0` на проде — измерения не было

Отозвано, разобрано в `baseline.md`. Короче: `curl -s` при отказе
соединения молчит, `grep` получает пустой ввод, `wc -l` отвечает 0, и ноль
читается как «скрытых узлов нет». Сеть к проду закрыта — измерения не было.

### 7.4. Два красных теста ВТБ — мой `.env`, не база

Первый прогон `php artisan test` с `backend/.env` стенда дал 2 падения в
`SafeDealVtbHoldTest`. CI на том же коммите `dbb307a` зелёный (прогон 35,
`conclusion: success`).

Причина: CI гоняет `php artisan test --env=testing` с
`.env.testing.example`, а я прогнал с `.env` стенда, где ВТБ выключен.
С `--env=testing` оба теста проходят. Настоящая база — в `qa.md`.

### 7.5. Числовые `z-index` — не нарушение

20 совпадений в `frontend/src`. Каждое посмотрено: это локальные `z-[1]`…
`z-[3]` внутри своего `relative`-контейнера (`Lightbox`, `carousel`,
`CallScreen`, `CropSafeZoneOverlay`, `SimilarAds`). Запрет в `CLAUDE.md`
стоит на числовых слоях у **плавающих** элементов; плавающие берут слой из
шкалы `--z-*`. Править нечего.
