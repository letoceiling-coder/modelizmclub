### 2. Сердечко в `AdCard` не сохраняется никуда — и не показывается

**Поправка к первой редакции этого отчёта.** Я написал, что человек видит
пропажу избранного. Это неверно: сердечка на экране нет вовсе.

`frontend/src/components/AdCard.tsx:129` — кнопка под охраной:

```tsx
{!compact && (
  <m.button onClick={handleLike} …>
```

А оба вызова передают `compact`:

```
ProfileView.tsx:767          <AdCard ad={ad} state={cardState} compact />
SubcategoryRoomPage.tsx:1543 <AdCard key={a.id} ad={a} compact />
```

Третьего вызова нет — проверил `grep` по всему `src` (исключив `AdCardSkeleton`
и `MyAdCard`). Значит ветка с сердечком не отрисовывается никогда, и
пользовательского дефекта здесь нет.

Что остаётся — **мёртвая ветка с неработающей логикой внутри**:

```tsx
const [liked, setLiked] = useState<boolean>(false);   // :49
const handleLike = (e: React.MouseEvent) => {
  e.preventDefault();
  e.stopPropagation();
  setLiked((v) => !v);        // ни стора, ни сервера
  setLikeBump((n) => n + 1);
};
```

Начальное значение всегда `false`, запись никуда не идёт. Если кто-нибудь
отрисует `<AdCard>` без `compact` — а по сигнатуре это значение по умолчанию, —
он получит сердечко, которое загорается и ничего не сохраняет. Ловушка, а не
поломка.

Под тем же `!compact` лежит ещё 30 строк: значки доставки и счётчик
`<Heart size={12} /> {ad.likes}` (`:225–254`). Из 260 строк компонента 51 не
достигается ни одним вызовом, плюс обслуживающий их код — `liked`, `likeBump`,
`handleLike`, таблица `DELIVERY_ICON` (`:28–34`), импорты `Heart`, `Package`,
`Truck`, `BoxSelect`, `Store`.

**Настоящее дублирование рядом, и оно живое.** Логика переключения избранного
написана трижды, почти слово в слово, по 20 строк:

| Место | Что делает |
| --- | --- |
| `ads/CatalogCard.tsx:161` | оптимистичный `toggleFavoriteAd` → сервер → откат → тост |
| `routes/index.tsx:1072` | то же, подписи через `t()` |
| `routes/ads.$id.tsx:410` | то же плюс обновление `ad.likes` из ответа |

Три копии и одна сломанная не-копия в `AdCard`. Это то место, где стоит
вмешаться: вынести хук и подключить к нему все четыре.

### 6. Расхождение гидрации: время считается при отрисовке

`AdCard.tsx:16` объявляет свою `relativeTime()`, читающую `Date.now()`
(строка 20), и вызывает её в разметке — `AdCard.tsx:220`.

При этом в проекте для этого есть `components/TimeAgo.tsx`, написанный
именно против этой ошибки: `useHydrated()`, `suppressHydrationWarning`,
заглушка на первом кадре. `AdCard` его не использует.

Страницы профиля и комнаты подкатегории отдаются сервером (`ssr: false` нет
нигде). Сервер считает «2 ч назад» в момент запроса, браузер пересчитывает в
момент гидрации; на пересечении любого порога (`3600`, `86400`, `172800`,
`604800` секунд) строки расходятся — React бросает #418 и перерисовывает
страницу целиком. По `CLAUDE.md` это та же поломка, что держалась на 17
страницах из 21 до 14.09.

Заодно строки в `relativeTime` зашиты по-русски («недавно», «только что»,
«ч назад») — мимо i18next.

`AppFooter.tsx:75` — `© {new Date().getFullYear()} {siteName}`, подвал в
`AppLayout.tsx:178`, то есть на каждой странице с подвалом. Сервер живёт в
UTC, человек в Москве: 1 января с 00:00 до 03:00 МСК сервер отдаёт прошлый
год, браузер рисует новый. Три часа в году, зато на всех страницах сразу.

Проверил и **не** подтвердил по остальным 50 файлам со чтением текущего
времени: `PostCard.tsx:535`, `SubcategoryRoomPage.tsx:897` и прочие — внутри
обработчиков отправки (идентификатор оптимистичного сообщения), к разметке
первого кадра отношения не имеют.

### 7. Слои: числовой `z-index` у плавающих элементов

Шкала в `styles.css:132–141` кончается на `--z-call: 80`. Поверх неё:

| Место | Значение | Что это |
| --- | --- | --- |
| `admin/AdminContentSection.tsx:240` | `zIndex: 1000` | `position: fixed` окно предпросмотра |
| `admin/AdminReviewsPreviewModal.tsx:32` | `zIndex: 1000` | `position: fixed` окно предпросмотра |
| `admin/MediaManagerCard.tsx:464` | `zIndex: 200` | `position: fixed` окно выбора медиа |

Три окна стоят выше всей шкалы: выше тостов (60), выше гейта (70), выше
полноэкранного звонка (80).

Следствие, которое видно по коду: оба первых окна поднимают свои же тосты —
`AdminContentSection` при отказе шлёт `toast.error(statusUpdateFailed)` и
`deleteFailed`, `MediaManagerCard` — `uploadFailed`, `loadMediaFailed`,
`urlCopied`. Контейнер тостов прибит к `var(--z-toaster)` = 60 с `!important`
(`styles.css:815`). Администратор нажимает «удалить» в окне, удаление не
проходит, сообщение об отказе рисуется **под** окном.

Это следствие я **не замерял в браузере** и записываю как вероятное: оно
верно, если ни один предок окна не создаёт свой контекст наложения
(`transform`, `filter`, `opacity`, `contain`). Числа против шкалы — факт,
невидимый тост — требует живой проверки; это дешевле, чем рассуждать, и
правится всё равно одной заменой на `var(--z-modal)`.

Прочие `z-[2]`, `z-[3]`, `z-[10]` внутри `relative`-контейнеров (`Lightbox`,
`CallScreen`, `CropSafeZoneOverlay`, карусели) — локальное наложение внутри
своей карточки, под правило не попадают.

**Проверка есть, просто не политикой:**

- Записи — `PostService::update`/`delete` через `$user->can(…)`

**Самоадресованные** (`/users/me/*`, вход, выход, кошелёк, закладки,

запретом всё равно идёт последовательно — индекса нет вовсе.

**Нашёл один настоящий провал.** `post_reposts` — единственный индекс
`post_reposts_pkey(id)`. Ни `user_id`, ни `original_post_id`, ни

explain select original_post_id, count(*) from post_reposts

## Чего не измерял, и почему

Записываю отдельно, потому что пустая проверка и пройденная проверка должны
выглядеть по-разному.

**Боевая база — доступ получен 03.10, только чтение.** Сироты и рост
измерены, разделы 2a и 2b выше. Остаётся один пункт:

- *`EXPLAIN` на десяти частых запросах.* Пригодность индексов установил (см.
  раздел 1) — это то, что от объёмов не зависит. Сами планы не снимал: при
  59 пользователях и 328 записях последовательный просмотр честно дешевле
  любого индекса, и план на проде сегодня скажет не больше, чем на демо.
  Эту проверку надо повторить, когда появятся объёмы; `post_reposts` без
  индекса станет заметен первым.

**N+1 с логом запросов — не мерил.** Нужен засеянный контур и профилирование
на уровне запроса (`DB::listen` вокруг обращения к эндпоинту). Статически
нашёл смежное — `post_reposts` без индексов, — но это другая болезнь.
Делается прогоном нескольких функциональных тестов со счётчиком запросов на
отдельной тестовой базе; в этот заход не стал заводить, чтобы не столкнуться
схемой с соседними деревьями (их сейчас 45).

**Невидимый тост под окном админки** (п. 7 фронтенда) — следствие выведено
из чисел, в браузере не проверено. Числа против шкалы — факт; перекрытие
зависит от контекстов наложения у предков.

**307 приведений `as <Тип>`** — посчитаны, но не сверены с `docs/openapi`.
Именно там типы и врут, если врут.
