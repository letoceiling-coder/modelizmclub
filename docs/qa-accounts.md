# Тестовые учётки на проде

Три учётки под ручную проверку лестницы доступа. Заводить новые не нужно —
все три уже в нужных состояниях (кроме одной оговорки в конце).

Адреса одноразовые, пароль общий: `12345678`.

## Лестница доступа

`guest → registered → verified → subscriber` (`frontend/src/lib/gate/levels.ts`).
Отказ всегда ровно один — первая непройденная ступень, и окно ровно одно:

| Ступень | Чего не хватает | Какое окно |
| --- | --- | --- |
| `guest` | не вошёл | `auth` — «Войдите или зарегистрируйтесь» |
| `registered` | телефон не подтверждён | `verify` — «Подтвердите номер телефона» |
| `verified` | нет подписки | `paywall` — «Нужна подписка» |
| `subscriber` | — | окна нет |

«Подтвердите номер телефона», вторая — «Нужна подписка».

## Как подтверждали телефоны без СМС

Провайдер упирается в ограничение частоты и уже отклонял номера, а
эндпоинта подтверждения телефона в админке нет вовсе. Поэтому через
tinker, но **не записью в `phone_verified_at`**: колонку ставит
`PhoneVerificationService::verifyCode()`, и он же гасит код, проверяет
`assertPhoneAvailable` и при первом подтверждении зовёт
`FirstHundredService::tryGrant` и `ReferralService::onPhoneVerified`.
Прямая запись всё это пропускает.

Обходится только провайдер: в `phone_verification_codes` кладётся строка
ровно того же вида, что пишет `sendCode()`, и дальше зовётся `verifyCode()`
этим кодом.

```php
PhoneVerificationCode::create([
    'user_id' => $user->id, 'phone' => $phone,
    'code' => '424242', 'expires_at' => now()->addMinutes(30),
]);
app(PhoneVerificationService::class)->verifyCode($user, $phone, '424242');
```

Перед этим проверьте, что промо «Первые 100» выключено и раздающего пула
нет, иначе `tryGrant` выдаст подписку и вторая учётка перестанет показывать
окно подписки. На 06.09 промо выключено, занято 0 из 100, пула нет —
`is_first_hundred` у обеих учёток остался `false`.

Номера `+79000000002` и `+79000000003` — диапазон `+79000000xx` свободен.

## Открытый дефект: ручная выдача подписки в админке не даёт доступа

`AdminUserSubscriptionController` (`POST /api/v1/admin/users/{uuid}/subscription`,
`action=activate`) — то, что нажимает админ при ручной активации. Он создаёт
строку `user_subscriptions` со `status=active` и будущим `ends_at`, пишет
аудит и возвращает `is_active: true`.

Приложение эту подписку не видит. `User::hasActiveSubscription()` требует
сверх живой строки ещё одно из двух:

* оплаченный `Payment` с `metadata.plan_id` (`hasPaidSubscriptionPayment()`), либо
* промо-признак — `is_first_hundred` с `promo_pool_id` или покрытием
  `FirstHundredPromo::coversUser()`.

Ручная активация не делает ни того, ни другого. Замер на `hoxifoj625` 06.09:

```
hasUnexpiredSubscriptionRow: true      строка живёт до 2027-09-06
hasPaidSubscriptionPayment:  false     платежей у пользователя 0
hasActiveSubscription:       false     ← итог
```

`GET /users/me/subscription` отвечает `{"data":null}`, и на `/reviews`
учётка получает «Нужна подписка» — то есть ведёт себя как `verified`,
неотличимо от второй учётки.

Похоже, это следствие миграций `2026_08_21_095500_cancel_unpaid_active_subscriptions`
и `2026_08_21_112800_cancel_stub_unpaid_subscriptions`: неоплаченные
«активные» подписки тогда осознанно погасили, а кнопку в админке под новое
правило не привели.

Пока дефект не закрыт, третья учётка **не отличается от второй**, и
сценарий «подписчик не видит окон» ей не проверить.
