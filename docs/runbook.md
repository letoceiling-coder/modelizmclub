# Регламент эксплуатации

Что делать, когда что-то происходит. Всё измеренное помечено как
измеренное, оценки — как оценки.

Сейчас это держалось на памяти команды; здесь записано.

---

## Кто выкатывает и как

Выкатка — одна команда с машины разработчика:

```bash
ssh -p 2222 root@31.207.75.124 'nohup bash /root/deploy-remote.sh <полный-sha> >/dev/null 2>&1 &'
```

Копия скрипта лежит в репозитории: `deploy/scripts/deploy-remote.sh`.
До 25.09 её там не было — скрипт, которым выкатывается прод, жил вне
репозитория, и его нельзя было ни прочитать в ревью, ни откатить.

Что делает выкатка, по порядку:

1. дамп базы перед выкаткой;
2. `git merge --ff-only` на указанный SHA;
3. миграции — **только если** в коммитах есть файлы миграций;
4. пересборку кеша маршрутов — **только если** менялись файлы маршрутов;
5. перезагрузку php-fpm и рабочих очередей;
6. сборку и подмену фронта;
7. дымовую проверку, сверку схемы и карты доступа.

Журнал: `/tmp/deploy-<sha>.log` на сервере.

**Перед выкаткой обязательно** — проверить CI именно того коммита,
который выкатываете:

```bash
bash deploy/scripts/check-ci-status.sh "$(git rev-parse master)"
```

Ответов три, и путать их нельзя: `0` зелёный, `1` красный,
`2` — **неизвестно**. Неизвестно бывает, когда прогон ещё идёт или
спросить не удалось. Это не «всё хорошо».

Без `GH_TOKEN` в окружении GitHub даёт 60 запросов в час, и они
кончаются быстрее, чем кажется. Тогда ответ будет `2`, и выкатывать
вслепую нельзя.

**После выкатки** — убедиться, что код доехал:

```bash
ssh -p 2222 root@31.207.75.124 'cd /var/www/modelizmclub && git rev-parse --short HEAD'
```

Совпадение SHA не гарантирует содержимого, если между делом кто-то
откатил файл: 10.09 коммит с новым методом был в истории прода, а
метода в файле не было.

## Авария: порядок действий

### 1. Понять, что именно сломано

| Что видно | Куда смотреть |
| --- | --- |
| Сайт не открывается совсем | Жив ли сервер: `ping`, затем `systemctl status nginx` |
| Белая страница | `systemctl status modelizmclub-frontend` |
| 500 на всех страницах | `tail -100 backend/storage/logs/laravel.log` |
| Открывается, но без картинок | Ключи S3, см. перечень доступов |
| Не работают сообщения и звонки | `systemctl status modelizmclub-reverb` |
| Не уходят письма и уведомления | `systemctl status modelizmclub-worker` |

### 2. Если сломала выкатка — откатывать, а не чинить

Откат проверен на живом проде: переключение и возврат заняли **2
секунды**, ни один запрос не потерялся при опросе с шагом 2,3 секунды.

```bash
cd /var/www/modelizmclub
git log --oneline -5                  # найти предыдущий рабочий SHA
bash /root/deploy-remote.sh <предыдущий-sha>
```

Откат — это та же выкатка на прежний коммит. Она снова снимет дамп,
так что состояние до отката не потеряется.

**Миграции откат не отменяет.** Если выкатка применила миграцию, а
откат вернул прежний код, схема останется новой. Обычно это безвредно
(добавленная колонка старому коду не мешает), но если миграция что-то
удаляла — нужен разбор, а не второй откат.

### 3. Если сломаны данные — восстановление из дампа

```bash
bash deploy/scripts/restore-db.sh /root/backups/auto/daily/<файл>.dump
```

Скрипт **сначала снимает дамп текущего состояния** и требует набрать
подтверждение. `--yes` пропускает только вопрос, не защитный дамп.

**Замерено 26.09** на боевом сервере, восстановление суточного дампа в
отдельную базу:

| | |
| --- | --- |
| Размер дампа | 1,5 МБ |
| Время восстановления | **2 секунды** |
| Восстановлено | 141 таблица, 59 пользователей |

То есть простой при восстановлении определяется не самим
восстановлением, а решением: пока вы думаете, какой дамп брать,
проходит больше времени, чем занимает работа.

Дампы: суточные в `/root/backups/auto/daily/` (хранится 14), недельные
и снятые перед выкаткой — рядом. Копии выгружаются в S3, префикс
`backups/`; **оттуда ничего не удаляется**, так что старые копии там
есть, даже если локальные уже прокрутились.

Целостность дампа проверяется при создании: если `pg_restore -l` его не
читает, файл не сохраняется.

## Где смотреть ошибки

| Что | Где |
| --- | --- |
| Приложение | `backend/storage/logs/laravel.log` |
| Ошибки фронта в браузере | `storage/logs/csp-<дата>.log` |
| Выкатка | `/tmp/deploy-<sha>.log` |
| Дампы | `journalctl -u backup-db` |
| Место на диске | `journalctl -t disk-alert` |
| Очереди | `journalctl -u modelizmclub-worker` |
| Планировщик | `journalctl -u modelizmclub-scheduler` |
| Nginx | `/var/log/nginx/error.log` |

Сторожа, которые пишут сами:

- **Диск** — проверка каждые 15 минут, письмо на `info@modelizmclub.ru`
  при 80 % и отдельно при 90 %, по одному письму на порог.
- **Неудачный дамп** — письмо через `backup-db-failure@.service`.
- **Дымовая проверка** — выполняется после каждой выкатки, последняя
  строка печатает занятость диска и число тревог.

## Что проверять после перезагрузки сервера

Всё должно подняться само. Проверка, что так и есть:

```bash
systemctl is-enabled nginx php8.3-fpm postgresql redis-server \
  modelizmclub-frontend modelizmclub-worker modelizmclub-media-worker \
  modelizmclub-reverb modelizmclub-scheduler.timer backup-db.timer \
  disk-alert.timer
systemctl is-active  <тот же список>
```

Все должны ответить `enabled` и `active`. Проверено учением 22.09:
после перезагрузки все 15 единиц поднялись сами, простой около четырёх
минут.

Отдельно после перезагрузки:

```bash
bash deploy/scripts/smoke-check.sh
bash deploy/scripts/check-config-access.sh
```

Второй проверяет, читает ли php-fpm `.env` и собранный кеш. Если он
скажет `FAIL` на кеше — сайт уже отвечает 500, и чинить надо это, а не
идти дальше.

## Плановые работы

Порядок, проверенный 22.09:

1. Свежий дамп и выгрузка в S3.
2. **Три проверки до перезагрузки**, минута:
   - sshd поднимется сам и на том же порту: `systemctl is-enabled ssh`
     и `grep -E '^Port' /etc/ssh/sshd_config`;
   - правила брандмауэра переживут перезагрузку;
   - новое ядро установлено целиком, а не наполовину.
3. Перезагрузка.
4. Список проверок выше.
5. Сверить счётчики до и после: число пользователей, объявлений,
   записей. Расхождение означает, что что-то не поднялось.

Пятый пункт ценнее самих обновлений: он отвечает на вопрос, переживает
ли машина перезагрузку без человека.

## Контакты внешних сервисов

| Сервис | Зачем | Где искать |
| --- | --- | --- |
| Selectel | Хранилище медиа и копий базы | Кабинет заказчика |
| ВТБ, эквайринг | Приём платежей | Менеджер по договору |
| ВТБ, ОЭ | Выплаты продавцам | Отдельный менеджер, отдельный договор |
| СДЭК | Доставка | Кабинет и техподдержка |
| iqsms («СМС Дисконт») | Коды подтверждения | Кабинет |
| МТС Маркетолог | Запасной SMS-канал | Кабинет |
| Beget | Почта `info@modelizmclub.ru` | Панель хостинга |
| Хостинг сервера | Консоль машины, если SSH недоступен | Панель |

Логины в кабинеты знает заказчик; в репозитории их нет — см.
`deploy/docs/access-inventory.md`.

**Когда SSH не отвечает**, остаётся консоль в панели хостинга. Её стоит
проверить заранее, до того как она понадобится: пароль root для входа
через консоль — не тот же, что ключ SSH, и если его никто не знает,
консоль бесполезна.

## Чего в этом регламенте нет

- **Дежурства.** Кто отвечает ночью и в выходные — не решено.
- **Оповещения о падении сайта.** Сторожа есть только для диска и
  дампов. О том, что сайт не открывается, узнают от людей.
- **Проверки восстановления по расписанию.** Замер 26.09 разовый;
  регулярного учения «восстановить и убедиться» нет.
