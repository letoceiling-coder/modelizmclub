## Можно ли запускать

**Без платежей — да, после одной починки.** Чинить надо адрес пунктов выдачи
Яндекса: любой запрос к нему без фильтра съедает всю память обработчика и
убивает его. Это открыто гостю, то есть доступно кому угодно без входа.
Починка — три строки, она ниже. Остальные шесть находок запуску не мешают.

**С платежами — нет, и не из-за кода.** Приём денег я по вашему запрету не
трогал вовсе. Пока он не проверен живым платежом, запускать с деньгами нельзя.
Это проверка на один вечер, но её надо сделать.

**Отдельно, и это важнее любого дефекта.** Модерация записей включена, а
очередь никто не разбирает. Ваша собственная запись «Мы готовы запускаться!»
от 08.10 лежит невидимой со вчерашнего дня. При запуске это значит: человек
публикует — и не видит своей записи на сайте.

## Находки

### Д-01. Пункты выдачи Яндекса кладут обработчик сервера · **P1**

**Где.** `GET /api/v1/delivery/yandex/pickup-points`, открыт гостю без входа.

**Что сделал.** Открыл адрес без параметров — так, как его открыл бы кто
угодно.

**Чего ждал.** Либо список пунктов, либо отказ «укажите город» — так себя
ведёт соседний адрес СДЭК, он отвечает 422.

**Что вышло.** Пустой ответ 500. В журнале сервера:
`PHP Fatal error: Allowed memory size of 134217728 bytes exhausted in
Illuminate/Http/Client/Response.php on line 81`. Обработчик php-fpm умирает.

**Почему так.** Без фильтра по городу запрос уходит в настоящий Яндекс и
просит **все пункты выдачи по стране**. Ответ не помещается в 128 МБ. Хуже
того, код кладёт в ответ ещё и исходный объект каждого пункта целиком
(`'raw' => $point`) — то есть удваивает память.

**Чем это плохо для вас.** Три вещи сразу. Любой человек из интернета может
без входа убивать обработчики вашего сервера, повторяя один запрос. Каждый
такой запрос тратит квоту вашего ключа Яндекса. И доставка Яндекса, судя по
настройкам, включена на проде с настоящим ключом, но адрес узла не задан —
стоит решить, нужна ли она вам вообще.

**Ширина, роль, снимок.** Не зависит от ширины, воспроизводится гостем,
подтверждено журналом сервера `/var/log/nginx/error.log` за 09.10 06:41–06:45.

**Как починить.** Сделать город обязательным, как у СДЭК, и не возвращать
исходный объект:
```php
'geo_id' => ['required_without_all:latitude,longitude', 'integer'],
```
плюс убрать `'raw' => $point` из ответа. Починку я подготовил, она в PR.

### Д-02. Меню админки на телефоне не сворачивается · **P2**

**Где.** `/admin` на ширине 390, шторка меню.

**Чего ждал.** По вашему решению Ж4 — десять групп, все свёрнуты.

**Что вышло.** Шторка показывает **все 32 раздела подряд** одним длинным
списком: заголовки групп есть, но свернуть их нельзя. Снимок:
`evidence/defect-02-admin-menu-390.png`.

**Как есть на большом экране.** Там всё по решению: десять групп, все
свёрнуты, раскрытая остаётся раскрытой после перезагрузки. Проверено на 1280.

**Почему так.** Сворачивание сделано только для боковой колонки. Шторка
телефона рисует каждую группу целиком, не спрашивая о состоянии.

**Заодно.** Пункт 5 моего же листка `PHONE-CHECK.md` просит вас проверить на
телефоне «десять свёрнутых групп» — проверять там нечего, листок надо
поправить.

### Д-03. Поля ввода мельче 16 px на телефоне — три страницы · **P2**

**Где.** `/channels/new`, `/communities/new`, `/help` на ширинах 320 и 390.

**Что вышло.** Поля «Название канала», «Коротко о теме», адрес канала,
название и описание сообщества, почта и текст обращения в помощи — кегль
14 px.

**Чем плохо.** Сафари на айфоне приближает экран, когда человек ставит курсор
в поле мельче 16 px. Обратно экран сам не отъезжает — надо сводить пальцы.

**Почему так.** Общее поле сайта сделано правильно: `text-base md:text-sm` —
16 px на телефоне, 14 на большом экране. Но эти три страницы рисуют поля
своими руками и ставят 14 px на всех ширинах. Таких полей тринадцать, все в
`EntityRequestForm.tsx`, `communities.new.tsx` и `help.tsx`.

**Поправка к прежнему отчёту.** В `PHONE-CHECK.md` я написал «полей меньше
16 px нет ни одного». Это было неверно: тот обход не заходил на эти три
страницы.

### Д-04. Сервер обещает, что писать нельзя, и тут же принимает письмо · **P3**

**Где.** Ответ `GET /api/v1/conversations/{uuid}` у человека без
подтверждённого телефона: `can: {send: false}`. Сообщение при этом уходит с
кодом 201.

**Почему так.** Признаки `can` гасятся для всех, у кого телефон не
подтверждён, — правило верное, пока все действия были за этой стеной. Ваше
решение Ж3 вчера вынесло переписку из-за стены, а правило не пересмотрели.

**Насколько это видно людям.** Сегодня не видно: экран мессенджера этот
признак не читает, поле ввода показывает всем. Проверено на живом сайте.
Но любой следующий экран, который поверит `can`, спрячет поле ввода.

`{"error":"Only HTML requests are supported here"}`. Браузер так не ходит,
но поисковые и следящие службы — ходят, и для них это выглядит как авария.

При обрыве во время отправки **текста** показывается «Не удалось загрузить
файл или отправить запрос».
