### Подтверждённый дефект: лимит мест промокода обходится

Приёмка 27.09 назвала это открытым решением. **Воспроизведено этой
ночью** (временный тест, выкинут после):

```
промокод с max_usages = 1
  findValid для первого человека   → прошёл
  findValid для второго человека   → прошёл
  recordUsage ×2
  применений записано: 2 при max_usages = 1
```

Механизм виден в `PromocodeService::assertValid`:

```php
$totalUsages = $promocode->usages()->count();
if ($promocode->max_usages !== null && $totalUsages >= $promocode->max_usages) {
```

Обычный `count()` без блокировки строки и без ограничения в схеме. Двое
одновременно читают «осталось одно место» и оба проходят.

**Почему не починил этой ночью.** Починка не умещается в «минимальную
проверяемую правку», и причина не в сложности замка, а в том, что
применений промокода два, и у них разные последствия отказа:

| Путь | Где | Что будет, если отказать по лимиту |
| :-- | :-- | :-- |
| размещение объявления | `ListingService::create`, внутри `DB::transaction` | корректно: откатится всё, включая списание |
| оплата через провайдера | `PaymentFulfillmentService:104`, в обработке успешной оплаты | **деньги уже списаны** — отказ здесь означает, что человек заплатил и не получил скидку |

То есть замок в `recordUsage` закрыл бы первый путь и испортил второй:
место надо занимать не при записи применения, а при выдаче скидки, а это
уже решение о том, что делать с занятым и неоплаченным местом (возвращать
по тайм-ауту? держать до отмены платежа?). Это продуктовое решение, а не
опечатка, и принимать его в три сорок ночи без владельца я не стал —
правило 2.1.2 NIGHT-RUN.
