# Резервные копии базы под утёкшим ключом

Документ составлен 05.10.2026 по запросу владельца для разговора с юристом.
Всё ниже — наблюдения с боевого сервера, без изменений на нём.

---

## 1. Что произошло

12.09.2026 в переписку попали ключи объектного хранилища Selectel:
`AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`. Факт зафиксирован в
`deploy/docs/access-inventory.md` в тот же период. На 05.10 ключи **не
перевыпущены** и продолжают действовать.

## 2. Что открывает этот ключ

Ключ один на всё хранилище. Та же пара даёт доступ и к картинкам, и к
резервным копиям базы: проверено по `backend/config/filesystems.php` и
`deploy/scripts/backup-db-upload.php` — копии уходят через тот же диск `s3`,
с тем же `AWS_BUCKET`.

| | |
| --- | --- |
| Хранилище | Selectel S3, регион `ru-3` |
| Точка входа | `s3.ru-3.storage.selcloud.ru` |
| Контейнер | `knowledge-raw` |
| Права ключа | чтение, запись и **удаление** |

## 3. Что лежит в копиях

Полные дампы базы `modelizmclub`, то есть все данные площадки целиком:
учётные записи, адреса электронной почты, телефоны, профили, переписка,
объявления, сделки, платежи, реквизиты для выплат, журнал действий.

На 05.10 в базе 56 активных учётных записей и 3 заблокированных.

## 4. Как часто туда попадают новые копии

Ежедневно, автоматически, по таймеру `modelizmclub-scheduler`.

Из журнала резервного копирования на сервере:

```
2026-10-04T04:02:53 [daily] starting: db=modelizmclub commit=69f183e3
2026-10-04T04:02:54 [daily] dump ok: 1.6M, 1396 objects
2026-10-04T04:02:55 [daily] uploaded to s3://knowledge-raw/backups/daily/…
```

Локально хранится около месяца ежедневных копий (с 25.09 по 04.10 — по
одной в сутки, 1,5–1,6 МБ каждая). В хранилище — те же файлы в префиксе
`backups/daily/`, плюс `backups/pre-deploy/` перед каждой выкаткой.

**Значит с 12.09 по 05.10 в контейнер, ключ от которого известен
посторонним, ушло около двадцати трёх полных копий базы.** Каждая следующая
ночь добавляет ещё одну.

## 5. Были ли чужие обращения к копиям

**Ответить по журналам я не могу: журналов нет.**

Это не «обращений не было». Это «проверить нечем». Конкретно:

- на сервере не установлены `aws`, `s3cmd`, `rclone` — нечем спросить
  хранилище о его журналах;
- журналы доступа к контейнеру (access logging) в S3 — отдельная
  возможность, которую включают в кабинете провайдера. Включена ли она для
  `knowledge-raw`, с сервера не видно;
- если она не была включена заранее, записей о прошлых обращениях не
  существует вовсе — их не «потеряли», их не вели.

**Что нужно сделать в кабинете Selectel**, чтобы получить ответ:

1. Открыть контейнер `knowledge-raw` → раздел журналов или статистики.
2. Посмотреть, велись ли журналы доступа с 12.09.
3. Если велись — выгрузить записи по префиксу `backups/` за период с
   12.09.2026 по сегодня и искать обращения не с адреса боевого сервера
   (`31.207.75.124`).
4. Отдельно посмотреть счётчики исходящего трафика по контейнеру за тот же
   период: резкий скачок при неизменном числе посетителей сайта — косвенный
   признак выгрузки.

Пункт 4 стоит сделать, даже если журналов нет: трафик считают всегда.

## 6. Что это значит на практике

Пока ключ не отозван, исходить надо из того, что доступ к полным копиям
базы есть у всех, кто видел ту переписку. Доказать обратное нечем —
см. раздел 5.

Отзыв ключа прекращает доступ **вперёд**. Он не отменяет того, что было
доступно между 12.09 и днём отзыва.

## 7. Что сделать, в порядке важности

1. **Перевыпустить ключ и отозвать старый** в кабинете Selectel. Без
   второго шага первый бессмыслен.
2. **Проверить журналы и трафик** контейнера за период (раздел 5).
3. **Отделить копии базы от картинок**: отдельный контейнер и отдельный
   ключ, у приложения — только картинки, без права писать и удалять копии.
4. **Решить с юристом**, требует ли происшедшее уведомления
   пользователей и регулятора. Для этого и составлен этот документ.

Порядок важен: первый пункт останавливает утечку, остальные разбирают
последствия.
