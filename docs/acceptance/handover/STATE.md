# Промпт 02 — закрыт. Готово к выкатке

Четыре жалобы живого пользователя. У каждой нашлась причина в коде, и каждая
проверена на стенде — в браузере и запросами к серверу.

## Причина расхождения длины — одной фразой

**Код уходил в SMS числом, а числу ведущие нули не нужны.**

`sendTemplate(…, [(int) $code])` и `%d` в шаблоне. Код `001234` из базы
печатался как «1234». Проверено `php -r` на тех же значениях:

| В базе | Уезжало в SMS | Цифр |
| :-- | :-- | --: |
| `012345` | 12345 | 5 |
| `001234` | 1234 | **4** |
| `000123` | 123 | 3 |
| `123456` | 123456 | 6 |

Каждый десятый код начинается с нуля, каждый сотый — с двух. То есть один
человек из десяти получал код короче, чем требует форма, и подтвердить номер
не мог вовсе.

**Оговорка, без которой вывод был бы нечестным.** В боевой базе 23 кода, и
ни один не начинается с нуля — то есть у вашего пользователя сработала не
эта половина, а вторая (ниже). Но механизм настоящий, он в коде, и ждать,
когда он выстрелит на живом человеке, незачем.

## Вторая половина той же жалобы: поле кода исчезало

Поле ввода кода стояло под условием `{smsSent && …}`, где `smsSent` —
состояние компонента. Человек нажимал «Отправить SMS», уходил читать
сообщение, возвращался на страницу — и поля не было: состояние умерло вместе
с прежним рендером. Оставалось нажать «Отправить» ещё раз, то есть отменить
только что полученный код и получить новый. Круг без выхода.

**Видно по боевой базе.** Учётка `#1285` (зарегистрировалась 09.10 в 11:36)
запросила код в 11:37 и ещё раз в 11:49, и у обоих кодов `attempts = 0`.
Человек ни разу не отправил код на проверку — ему было некуда его вписать.
Оба SMS при этом ушли: в журнале сервера `SMS sent via iqsms` на оба.

## Часть А — длина кода (решение З1)

Шестёрка была записана **шесть раз в бэкенде и три раза в интерфейсе**, а
настройка `sms.verification.code_length` существовала и не использовалась ни
разу: `grep` по бэкенду давал одну строку — саму настройку.

Теперь из неё строится всё: генератор, проверка сервиса, проверка формы
запроса, текст отказа, ответ на запрос кода и по нему — поле ввода.

| Что | Было | Стало |
| :-- | :-- | :-- |
| Генерация | `str_pad(…, 6, …)` | длина из настройки |
| Проверка на сервере | `/^\d{6}$/` | по той же настройке |
| Проверка формы запроса | `size:6` | по той же настройке |
| Текст отказа | «Код должен состоять из 6 цифр» | «Код состоит из N цифр» |
| Ответ на запрос кода | не сообщал длину | `code_length` и `max_attempts` |
| Поле ввода (3 файла) | `maxLength={6}`, `slice(0, 6)`, `length !== 6` | один компонент `SmsCodeInput` по длине с сервера |

Код уходит строкой, пять шаблонов с кодом переведены с `%d` на `%s` — текст
не меняется, нули доезжают.

**Поле кода стало одним компонентом** `SmsCodeInput`: цифровая клавиатура,
`autocomplete="one-time-code"` (без него нет ни подсказки из SMS, ни
автоподстановки WebOTP в Chrome на Android), вставка кода целиком с очисткой
от текста уведомления, автоотправка на последней цифре, подсказка «Код из N
цифр». И поле стоит **всегда**, а не только после отправки в этом же заходе.

Защита на месте и проверена: срок жизни кода, предел попыток, новый код
отменяет прежний, повтор по таймеру от сервера.

## Часть Б — где требуется телефон (решение З2)

Посредник `verified` требовал почту **и** телефон одним именем, поэтому снять
телефон значило снять заодно почту. Разделён на два:

- `verified.email` — там, где стоял прежний, **134 маршрута**;
- `verified.phone` — **четыре маршрута**, и список закрыт сторожем:

| Метод | Маршрут | Почему |
| :-- | :-- | :-- |
| POST | `api/v1/listings` | публикация объявления |
| POST | `api/v1/listings/{uuid}/publish` | публикация из черновика |
| POST | `api/v1/wallet/withdraw` | вывод средств |
| PUT | `api/v1/account/payout-requisites` | куда уходят деньги — часть вывода |

Имя `verified` убрано нарочно: оставь синонимом — и требование вернётся с
первым же новым маршрутом.

**Таблица «где требовался телефон» до и после** — в `phone-required.md`
прошлого выпуска; здесь важен итог: из 134 мест осталось 4, и ни одно из них
не в матрице админки — матрица отвечает на вопрос «нужен ли вход», а не
«нужен ли телефон», и значения `verified` в ней нет вовсе.

В интерфейсе опустели оба списка: страниц, закрытых без телефона, — ноль
(были `/friends` и `/ads/new`); действий — ноль (были `ads.safe_deal` и
`ads.call_seller`, оба сервером больше не закрыты).

**Флаги `can.*` подвинулись вместе со стеной.** Оставить их строгими значило
бы повторить ошибку 07.09 зеркально: сервер пускает, а флаг говорит «нельзя»,
и человек без телефона не видит кнопки, которую ему разрешили.

**Лестница доступа перестала знать про телефон.** Это нашлось уже в браузере,
а не в коде: учётка без номера открывала `/reviews` (тир `subscription`) и
получала окно «Подтвердите номер» вместо окна подписки — подтверждение
номера доступа к обзорам всё равно не давало. То же на `/deals`. Теперь
вошедший сразу стоит на ступени `verified`, а два действия с телефоном
спрашивают его сами.

## Часть В — окно подтверждения (решение З3)

ответ**. У фонового запроса нет прерванного действия, и подтверждение номера
не даёт человеку ничего, кроме закрытого окна.

Закрытое окно помнится до конца захода (`sessionStorage`, обе операции в
try/catch, с запасом в памяти процесса — в приватном окне хранилище бросает
исключение). Нажатие открывает окно и после отказа: З3 запрещает возвращаться
**само**, а не открываться по просьбе.

Плашка про телефон снята с ленты и подписки, где телефон не нужен ни для
чего, и говорит теперь настоящую причину — «Подтвердите телефон, чтобы
размещать объявления». Тексты в трёх местах перестали обещать, что без
телефона закрыт весь сервис.
