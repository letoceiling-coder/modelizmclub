## §2.4 Матрица доступа

Самый разошедшийся раздел. Библия описывает права одной колонкой
`users.role`; строка про переименование `admin` → `owner` в ней уже есть
(19.09), но всё остальное появилось позже.

**Чего в библии нет:**

- **карта разделов** — у каждого раздела админки своя минимальная роль
  (`App\Support\AdminAccess::SECTIONS`), и состав правится из админки
  (`admin.role_access`), а не только константами;
- **права галочкой поверх роли** (25.09): владелец выдаёт отдельному
  сотруднику раздел, которого роль не даёт. Таблица
  `admin_permission_grants`, 27 выдаваемых ключей;
- **порог администраторов на направление** — по умолчанию 10, правится
  из админки;
- **сводка открыта модератору** (30.09). До этого раздел показывался ему
  в меню, а маршрут отвечал 403.

## §3.9 Billing — разошёлся сильно

**Чего нет в библии:**

- **оплата баллами.** `pay_with` теперь принимает `points` наравне с
  `gateway` и `wallet`; появилась ручка `GET /bonus-points` (остаток,
  история, цены). Подписка баллами не оплачивается — сервер отклоняет
  прямо;
- **статус платежа `abandoned`** (30.09) — брошенная форма, не отказ.
  Библия знает три статуса, теперь их четыре, и это меняет любую выборку
  «не `paid` значит неудача»;
- **диагностика отказа** — колонки `failure_code`, `failure_message`,
  `failure_stage`, `failed_at`, `form_opened_at`, `decided_by`;
- **воронка оплат** — `GET /admin/payments/funnel`;
- **отметка «дошёл до формы»** — `POST /payments/{uuid}/form-opened`.

## §3.10 и §5 Безопасная сделка — расхождение про деньги

**Комиссию платит покупатель** (27.09). Библия описывает прежнюю схему,
где комиссия вычиталась из выплаты продавцу. Отличие берётся из строки
(`safe_deals.fee_payer`), а не из даты: сделки до 27.09 живут по старому
правилу, и оба правила действуют одновременно.

план, а не факт. Три места уже чинили по этой причине: письмо о сделке,
сводка бухгалтерии, выгрузка реестра.

## §7 Тесты на сервере — раздел стал опасным примером

Раздел библии стоит пометить: прогон на боевом сервере допустим **только**
через `run-backend-tests.sh`, и никогда напрямую `phpunit`.

## Защита от прогона тестов по боевому окружению

Разобрано и закрыто 13.09 коммитом `38675ea8`, в тот же день, когда
случилось. Из его разбора:

> прогон phpunit на боевом сервере отправил запросы в iqsms с рабочими
> доступами из `.env.testing`: `phpunit.xml` драйвер SMS не задавал, а
> клиент для всего, кроме mts, — iqsms. Тот же прогон от root создал
> дневной `csp-*.log` с владельцем root, и отчёты CSP отвечали 500.

Что стоит сейчас — **проверено запуском 30.09**, а не чтением:

| Попытка | Ответ |
| --- | --- |
| `APP_ENV=production … phpunit` | `Tests must run with APP_ENV=testing, got: production` |
| `DB_DATABASE=modelizmclub … phpunit` | `Tests must use an isolated database named modelizmclub_test*` |
| `IQSMS_LOGIN=… phpunit` | `Tests must not see real SMS credentials` |

Проверка стоит в `refreshApplication()`, то есть **до первой миграции** —
иначе база была бы уже вычищена к моменту отказа. Все **212** тестовых
классов наследуют защищённый `Tests\TestCase`; Pest в проекте нет, обойти
защиту нечем.

**Кто именно запускал 13.09 — не восстановить.** Проверено три источника:

- `/root/.bash_history` — 1032 байта, оборван перезагрузкой 22.09;
- `auth.log.2.gz` (покрывает 13.09) — 24 вызова `php` через `sudo`, все
  `artisan tinker` с диагностикой, ни одного `phpunit`;
- `laravel.log.12.gz` (покрывает 13.09) — ни упоминаний SMS, ни следов
  тестового прогона.

Причина структурная: `sudo` пишет в журнал только то, что шло через него.
Root в своей оболочке не оставляет записи вовсе. Имя не появится.
