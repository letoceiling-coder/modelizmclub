## 1. Задача

1. Пользователь **не ждёт** нарезку и сжатие: превью сразу, публикация не блокируется джобой.
2. На сайте — **лёгкие файлы** (карточка, лента, галерея), не оригинал 3–10 МБ.
3. **Качество на экране не должно визуально падать** (детали модели, надписи на декалях, текстура).
4. Если после стандартного сжатия файл **всё ещё тяжёлый** — автоматический второй проход, без участия пользователя и модератора.
5. Основной формат показа — **WebP**; JPEG только как запасной.

---

## 2. Как не потерять качество (важно)

Телефон уже отдаёт **lossy JPEG**. Повторное «lossless WebP» с такого JPEG **не возвращает** исходник и часто **не легче**, чем оптимизированный JPEG.

Для витрины «не терять качество» значит:

- на карточке / в галерее картинка **неотличима от оригинала при обычном просмотре** (100% масштаб экрана, Retina);
- **не** бит-в-бит архив.

Это достигается так:

| Правило | Зачем |
|---------|--------|
| Оригинал на S3 **не перезаписывать** | всегда можно пересобрать варианты |
| Уменьшать сторону **только до размера показа × 2** | 640 px на карточке достаточно для Retina ~320 CSS px |
| WebP **lossy с высоким качеством**, не lossless | lossless для фото почти не выигрывает в весе |
| Пол качества (`q_min`) | автосжатие не давит файл до «мыла» |
| Если после `q_min` файл всё ещё тяжёлый | **качество побеждает вес** (вариант A) или мягко уменьшается только вариант, не оригинал (вариант B) |

Не предлагаем: PNG для фото, WebP lossless как основной путь, качество 0.92 как сейчас в редакторе (жирный файл без выигрыша на экране).

## 3. Общее для обоих вариантов (не обсуждается)

Это база. Оба варианта A и B её используют.

```
Выбор фото → сразу blob-превью
     → POST /media кладёт оригинал в S3
     → status=ready, url оригинала сразу
     → в Redis: ProcessMediaVariantsJob
     → пользователь идёт дальше по форме
```

- Загрузка фото **в фоне при выборе**, не в момент «Опубликовать».
- Джоба **не** внутри HTTP-запроса. `url` не бывает `null` из-за нарезки.
- Варианты: **thumb 320 / card 640 / medium 1080 / large 1600** (длинная сторона).
- Кодирование: **WebP основной + JPEG fallback**.
- Прокси: `/api/v1/media/{uuid}` — оригинал; `/api/v1/media/{uuid}/card.webp` — вариант, **если файла ещё нет — отдать оригинал, не 404**.
- Фронт: `variants` если есть, иначе `url`. Поллинг не нужен.
- Не трогать: SVG, иконки, видео, PDF.
- Отсекать кадры **> 40 мегапикселей**.
- Timeout джобы: **120 с** (у `queue:work` сейчас дефолт 60 с).
- Старые фото — отдельная команда бэкфилла, не в upload.

Потолки веса **после** ресайза (типичная фотография модели). Автопроход включается, если файл **выше** потолка.

| Вариант | Потолок WebP | Потолок JPEG |
|---------|--------------|--------------|
| thumb 320 | 40 КБ | 55 КБ |
| card 640 | 80 КБ | 110 КБ |
| medium 1080 | 180 КБ | 250 КБ |
| large 1600 | 350 КБ | 480 КБ |

## 4. Автосжатие, если файл остался тяжёлым

Одинаковый каркас в A и B. Разница — стартовое качество, минимальное качество и что делать, если потолок всё равно превышен.

```
1. Ресайз до целевой стороны (без увеличения маленьких фото)
2. Стереть GPS/EXIF, применить ориентацию
3. Закодировать WebP при q_start
4. Пока size > потолок И q > q_min:
      q = q − 4
      перекодировать этот же кадр заново (не поверх уже битого)
5. JPEG fallback тем же алгоритмом
6. Если WebP тяжелее JPEG при том же кадре — в srcset оставить JPEG
7. Если после q_min всё ещё > потолка → правило варианта (A или B)
```

Перекодировать **всегда с ресайзнутого растра**, не с уже сжатого WebP (иначе артефакты копятся).

## 5. Вариант A — очередь + WebP на GD (рекомендуем)

**Суть:** всё на текущем стеке (GD, Redis worker). Качество высокое и стабильное. Автосжатие есть, но ниже безопасного порога не опускаемся.

| Параметр | Значение |
|----------|----------|
| Кодер | PHP GD `imagewebp` / `imagejpeg` (уже на проде) |
| `q_start` | **84** |
| `q_min` | **76** |
| Шаг | −4 |
| Если всё ещё тяжелее потолка | **оставить файл как есть**, записать в лог `media_heavy` |
| Новые пакеты / Imagick | нет |
| Оценка | 3–5 рабочих дней |

**Почему качество держится.** q 84 на 640–1600 px для фото модели визуально равен исходному 12 Мп JPEG на экране. Автопроход до 76 трогает только «шумные» ночные/ISO-кадры, где вес раздувается. Ниже 76 не идём — лучше редкая карточка 120 КБ, чем мыло на декалях.

**Плюсы**

- Не ждёт пользователь; не нужен новый сервис.
- WebP реально легче JPEG на тех же пикселях.
- Автоматика без ручной модерации.
- Откат: оригинал на месте, варианты можно пересобрать.

**Минусы**

- GD слабее `cwebp` / Imagick: на сложной текстуре файл может быть на 10–20% тяжелее, чем в варианте B, при том же q.
- Редкие кадры превысят потолок и останутся тяжёлыми (это сознательно).

**Когда выбирать:** утвердить как основной путь и внедрять.

## 6. Вариант B — качество прежде веса, кодер сильнее

**Суть:** тот же UX и те же размеры, но кодирование качественнее. Автосжатие умнее: сначала лучший кодер, и только в крайнем случае чуть меньшая сторона **варианта** (оригинал не трогаем).

| Параметр | Значение |
|----------|----------|
| Кодер | Imagick или `cwebp` (поставить на VPS) |
| `q_start` | **88** |
| `q_min` | **80** |
| method WebP | 4–6 (медленнее, лучше сжатие при том же q) |
| Если всё ещё тяжелее потолка | уменьшить сторону варианта на **10%** (например 640→576), снова q_start; **один** такой круг |
| Если и после этого тяжело | оставить, лог `media_heavy` |
| Новые пакеты | `php-imagick` и/или `webp` (libwebp) |
| Оценка | 6–9 рабочих дней + ops |

**Почему качество держится.** Старт выше (88), пол выше (80). Лишний вес сначала съедает кодер, не качество. Уменьшение стороны на 10% только у производного файла: на карточке 320 CSS px это всё ещё запас под Retina.

**Плюсы**

- Лучшая пара «вес / вид» на сложных фото.
- Потолки веса соблюдаются чаще, чем в A.
- Тот же контракт для фронта (`variants` + fallback на оригинал).

**Минусы**

- Imagick сейчас **нет** на проде; нужен apt + проверка worker memory.
- Джоба дольше (method 6); держать timeout 120 с и, при необходимости, очередь `media`.
- Больше точек отказа (расширение PHP).

**Когда выбирать:** если после пилота A на 20–30 реальных фото лотов видно мыло или карточки систематически > 150 КБ.

## 7. Сравнение для утверждения

| Критерий | A — GD + потолок | B — Imagick/cwebp |
|----------|------------------|-------------------|
| Ожидание у пользователя | нет | нет |
| WebP | да | да |
| Визуальное качество витрины | высокое (q 84–76) | максимальное из двух (q 88–80) |
| Автосжатие тяжёлых | да, стоп на q 76 | да, стоп на q 80 + один −10% стороны |
| Если всё равно тяжело | качество > вес | качество > вес после одного круга |
| Риск «мыла» | низкий | ниже |
| Срок | короче | дольше |
| Зависимости | только то, что есть | Imagick/cwebp |
| Оригинал | не трогаем | не трогаем |

Оба варианта **не** делают то, что было в `PLAN-FRONT-INTEGRATION.md`: не держат медиа `pending`, пока джоба не закончит. Иначе форма и `<img>` ждут нарезку.

## 8. Что сознательно не берём

| Идея | Почему нет |
|------|------------|
| Сжимать в том же HTTP, что upload | пользователь ждёт 1–3 с на каждое фото |
| Lossless WebP как основной | для фото с телефона почти нет выигрыша в весе |
| Давить q до 50, пока не влезет в 40 КБ | потеря деталей модели |
| Отдавать на сайт только оригинал, «браузер сам» | карточка 80 px качает 8 МБ |
| imgproxy «на лету» вместо джобы | отдельный сервис; первый хит медленный; спорные файлы (dispute) сложнее закрыть |
| Стирать оригинал после нарезки | нельзя починить качество и пересобрать |

Клиентский потолок 2560 px **не конкурирует** с A/B: он только ускоряет саму заливку. Имеет смысл добавить **после** утверждения A или B, тем же этапом или следующим.

---

## 9. Критерии приёмки (после внедрения выбранного)

- Выбор 10 фото в визарде: превью сразу, кнопка публикации не крутится на нарезке.
- Карточка каталога запрашивает **card WebP ≤ 80 КБ** в типичном случае (не ISO-шум).
- Галерея объявления — **large**, не оригинал 4000 px.
- Safari/старый браузер без WebP получает JPEG.
- Пока джоба не закончила, картинка **видна** (оригинал), без дырки и без спиннера «оптимизация».
- На 5 контрольных фото моделей (светлая декаль, мелкий текст, тёмный фон) нет видимого мыла рядом с оригиналом на экране 100%.
- Файл в логе `media_heavy` можно открыть и при необходимости пересобрать с оригинала.

---

## 10. Предложение

Утвердить **вариант A**. Заложить в конфиг `q_start` / `q_min` / потолки КБ, чтобы переход на B был сменой кодера, а не переписыванием пайплайна.

После двух недель на проде: если доля `media_heavy` > 10% карточек или есть жалобы на качество — рассмотреть B.
