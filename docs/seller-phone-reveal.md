# «Позвонить продавцу»: раскрытие номера и переход на АТС

## Как устроено сейчас

1. **Карточка и список номера не содержат.** `ListingResource` отдаёт только
   `phone_available` — номер есть, продавец его показывает, объявление
   опубликовано. Автору дополнительно приходит `show_phone` (его выбор).
   Номер в разметке и в ответе списка собирают за один проход и дальше
   обзванивают, поэтому в HTML страницы его нет до нажатия.
2. **Номер — отдельным запросом по нажатию:**
   `POST /api/v1/listings/{uuid}/reveal-phone` → `{ phone, expires_at }`,
   `Cache-Control: no-store`. Маршрут за `auth:sanctum` и `verified`: гостю
   фронтенд открывает окно входа, вошедшему без подтверждённого телефона —
   окно подтверждения. После входа действие повторяется: в той же вкладке
   замыканием гейта, после входа по ссылке — `listing.reveal_phone` в
   `frontend/src/lib/gate/resumable.ts`.
3. **Выбор продавца** — `listings.show_phone`, по умолчанию `true`.
   Меняется в мастере подачи (вместе с объявлением) и на странице объявления
   у владельца: `PUT /api/v1/listings/{uuid}/phone-visibility` — отдельно,
   потому что любой `PATCH` опубликованного объявления возвращает его на
   модерацию.
4. **Журнал** — таблица `listing_phone_reveals`: объявление, покупатель,
   продавец, провайдер, IP, User-Agent, время. Отдельная таблица, а не
   `audit_logs`: журнал аудита — действия сотрудников в админке («История
   изменений»), а раскрытий на порядки больше и их ищут по продавцу и по
   покупателю, когда приходит жалоба на обзвон. Ссылки при удалении
   объявления или учётки обнуляются, запись остаётся.
5. **Частота** — `SellerPhoneRevealService`, считает по журналу разные
   объявления за последний час:
   - 20 на учётку (`PER_ACCOUNT_PER_HOUR`);
   - 30 с одного IP по всем учёткам (`PER_ADDRESS_PER_HOUR`) — выше лимита
     учётки, потому что за одним внешним адресом бывает несколько человек.

   Повторное раскрытие того же объявления лимит не тратит. Сверх лимита —
   429 «Слишком много номеров за час. Попробуйте позже.»

## Точка замены: `ContactNumberProvider`

Весь путь номера проходит через один интерфейс:

```
backend/app/Modules/Listing/Contracts/ContactNumberProvider.php
```

| метод | что отвечает |
|---|---|
| `name()` | имя в журнале: `profile` |
| `canProvide(Listing)` | есть ли что выдать — зовётся на каждую карточку списка, без внешних запросов |
| `numberFor(Listing, User $viewer)` | номер для этого покупателя по этому объявлению: `ContactNumber(phone, expiresAt)` |

Сейчас привязан `ProfilePhoneNumberProvider`: настоящий номер из профиля
продавца, только подтверждённый по SMS. Привязка — в
`backend/app/Providers/AppServiceProvider.php`.

## Что менять при переходе на АТС

1. Написать `PbxPhoneNumberProvider implements ContactNumberProvider`:
   - `name()` → `pbx`;
   - `canProvide()` — как сейчас: у продавца есть подтверждённый номер (АТС
     переадресует на него), без обращения к АТС;
   - `numberFor()` — запросить у АТС подменный номер для пары «покупатель —
     объявление», вернуть `new ContactNumber($virtual, $expiresAt)`.
2. Заменить привязку в `AppServiceProvider` на новый класс.
3. Если подменному номеру нужен срок — он уже уходит клиенту в
   `expires_at`; показать его в `SellerCallButton` при желании.

Не меняются: маршрут и ответ API, `SellerPhoneRevealService` (лимиты,
журнал, проверка `show_phone`), ресурс объявления, фронтенд (кнопка,
возобновление после входа, переключатель продавца). В журнале у новых
записей появится `provider = pbx`, старые останутся `profile`.

Если АТС может отказать (нет свободных номеров, недоступна) —
`numberFor()` бросает исключение; ответ 5xx клиент покажет как «Не удалось
получить номер», запись в журнал при этом не пишется (журнал пишется после
получения номера).
