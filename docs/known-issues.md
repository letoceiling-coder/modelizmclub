## ~~`deploy-neeklo-frontend.sh` does not `git pull`~~ — закрыто 10.09.2026

**Починено.** В скрипт добавлен тот же блок, что был у бэкендового
`deploy-neeklo.sh`: переключение на ветку `NEEKLO_GIT_BRANCH` (по умолчанию
`neeklo`) и `git pull`. Переменная общая у обоих скриптов — иначе два
скрипта одного стенда собирали бы разный код.

**Почему это чинили, а не выбросили.** Стенд жив: `neeklo.modelizmclub.ru`
отвечает 200, каталог `/var/www/modelizmclub-neeklo` на месте. Проверено
10.09.

Ниже — как было записано 13.07.


**Found:** 2026-07-13, while deploying a hotfix for a production crash on `/feed`.

`deploy/scripts/deploy-neeklo-frontend.sh` builds and restarts the frontend
from whatever is *currently checked out* on the server — it never runs
`git pull`. Only `deploy/scripts/deploy-neeklo.sh` (the backend script) pulls.

Consequence: running the frontend-only deploy script after pushing new
frontend commits silently rebuilds the **old** code. The build succeeds,
the service restarts, everything reports "OK" — but the live site doesn't
change. This is easy to miss because there is no error; the deployed
JS chunk hashes just don't change.

**What happened concretely:** a hotfix commit was pushed, the frontend
deploy script was run, it reported success, but the site kept crashing
with the exact same error and the exact same JS chunk hash as before the
fix. Only checking `git log -1` on the server (and comparing asset
filenames) revealed the script had built stale code.

**Suggested fix:** add a `git pull origin <branch>` step to
`deploy-neeklo-frontend.sh` (mirroring what `deploy-neeklo.sh` already
does), or document clearly that the backend script must always run first
even for frontend-only changes.

**Workaround until fixed:** always run `git -C /var/www/modelizmclub-neeklo
pull origin neeklo` manually before invoking
`deploy-neeklo-frontend.sh`, and verify by diffing `git log -1` before/after
or checking that the built asset hash for a known-changed file actually
changed.

## ~~`GET /users/me` answers 500~~ — закрыто 10.09.2026

**Чем подтверждено.** Замер на проде 10.09, без токена:

```
users/me                → 401
users/me/listings       → 401
wallet                  → 401
users/zzz-no-such-user  → 404
```

То есть и сам маршрут отвечает отказом вместо ошибки, и catch-all перестал
глотать несопоставленные пути: несуществующий слуг даёт 404, а не 500.
Записанная ниже причина при этом остаётся верной как урок — неограниченный
`{slug}` в конце префикса опасен сам по себе, и сметать его стоит в других
модулях тоже.

Ниже — как было записано 03.09.


**Found:** 2026-09-03, while writing the post-deploy smoke check
(`deploy/scripts/smoke-check.sh`). The check picked `/users/me` as its
"authenticated route" probe and failed on the first run against production.

```
GET https://api.modelizmclub.ru/api/v1/users/me   (no token)
→ 500 {"message":"Server Error"}
```

Every other protected route behaves correctly:

```
users/me/listings         401
me/entity-requests        401
wallet                    401
account/payment-methods   401
```

**Cause.** There is no `GET users/me` route at all — `backend/app/Modules/User/routes/api.php`
declares `me/stats`, `me/settings`, `me/interests`, … under `auth:sanctum` and
`PATCH me` under `auth:sanctum,verified`, but no bare `GET me`. The request
therefore falls through to the public catch-all on line 63:

```php
Route::get('{slug}', ShowProfileController::class);
```

which treats `me` as a profile slug, finds no such user, and throws instead of
returning 404.

**Why this is worth a task of its own.** The bug is not the missing route —
it is that an unauthenticated catch-all sits at the end of the `users` prefix
and absorbs every path that did not match something explicit. Any future typo,
renamed route or client calling a path that no longer exists lands in
`ShowProfileController` and surfaces as a 500. `{slug}` has no `where()`
constraint, unlike the `{id}` routes above it which are guarded with
`->whereNumber('id')`. The same shape may exist under other prefixes.

Worth checking as part of the F3 routing audit:
- constrain `{slug}` (a slug pattern, or an explicit exclusion list of reserved
  words like `me`), so unmatched paths 404 instead of reaching a controller;
- make `ShowProfileController` return 404 for a missing profile rather than
  throwing;
- sweep the other module route files for unconstrained catch-alls.

**Not fixed** — recorded deliberately. The smoke check probes
`users/me/listings` instead, so the deploy gate does not depend on this bug
being resolved first.

Это разные таблицы с разными последовательностями, и совпадут их номера или
нет — зависит от того, сколько строк успело появиться в каждой к этому месту

если номера совпадут, «сервис перевёл один идентификатор в другой» нельзя
отличить от «сервис вернул то же число». Но выполняется оно по случайности,
а не по построению.

**Сегодня не сработало.** Два падения, которые я на это списал, оказались
гонкой двух прогонов за одну тестовую базу (см. ниже). После её устранения

соседнем тесте.

**Закрыто в тот же день.** Случайность кончилась через несколько часов после
этой записи: пять тестов страницы тарифов добавили категорий объявлений,
последовательности сравнялись, и оба утверждения упали — при том, что файл по

## Шапка профиля не сводится с шапкой сообщества и канала

**Проверено:** 09.09.2026, при правке шапок сущностей.

`EntityHeader` — одна на сообщества и каналы. Профиль в неё не сводится, и
вот чем он отличается по существу, а не по оформлению:

| | EntityHeader | Профиль |
| --- | --- | --- |
| Обложка | только показывает | загрузка и кадрирование на месте, соотношение 3.5, вывод 1400×400 |
| Аватар | только показывает | своё меню «сменить / удалить», кадрирование |
| Заглушка обложки | градиент из имени | ровная заливка акцентом |
| Бейджи | слот от страницы | Pro, «первая сотня», статус телефона со ссылкой в настройки |
| Мета | одна строка caption | город, рейтинг, отзывы, сделки — с переходами по клику |

Свести их значило бы завести в `EntityHeader` флаги `editable`,
`onCoverChange`, `onAvatarChange`, `stats` — ровно то, от чего предостерегает
его собственная докстрока: «Флагов вида `isChannel` внутри нет — как только
такой понадобится, компоненты надо разводить обратно».

**Что при этом стоит знать:** кольцо-отбивка вокруг аватара, которого не
хватало сообществу и каналу, **в профиле уже было** —
`border: 4px solid var(--background)`. То есть приём в коде существовал, и
шапка сущности просто им не пользовалась. Разошлись не подходы, а две
реализации одного и того же.

**Если сводить всё же решим** — правильный порядок такой: сначала вынести
редактируемую обложку и редактируемый аватар в отдельные компоненты
(`EditableCover`, `EditableAvatar`), которые профиль передаёт слотами
`coverOverlay` и вместо `avatarUrl`. Тогда `EntityHeader` останется без
флагов, а профиль получит те же отступы и то же кольцо. Это отдельная ветка,
не правка отступов.

## Десять категорий без `path` и четыре с `depth`, спорящим с `parent_id`

**Измерено:** 09.09.2026, боевым прогоном `categories:flatten` на проде.

Команда приводит деревья к двум уровням и после записи сверяет результат
независимым запросом. Первый прогон дал 8 несошедшихся строк в направлениях
и 2 в каталоге — и ни одной из тех двух на дерево, которые команда писала.
Обе правленые строки легли верно; «путь есть, но не сходится с `parent_id`»
— ноль в обоих деревьях.

У всех десяти `path` не заполнен вовсе:

| Дерево | Строки |
| --- | --- |
| `post_categories` | #120 roboty, #121 gumanoid, #124 channels, #132 vodoemy, #133 prikormka-i-snasti, #134 dlya-rybalki, #137 akvarobot, #138 kotello |
| `listing_categories` | #98 escrow-smoke, #99 escrow-e2e |

Две последние — мусор от смоук-тестов эскроу, их можно просто убрать.

**Что важнее пустого пути.** Четыре строки — #121, #132, #133, #134 — имеют
`parent_id`, но `depth = 0`. Это ровно болезнь «ил 6»: дерево по `parent_id`
считает их подкатегориями, дерево по `depth` — корневыми направлениями.
«ил 6» из-за неё стоял в правой панели рядом с «Авиацией»; эти четыре стоят
там же сейчас — «Гуманоид» под «Роботами», «Водоёмы» и «Прикормка и снасти»
под «Рыбалкой», «Для рыбалки» под «Кораблями».

**Почему не починено вместе с «ил 6».** Починка «ил 6» была однозначной:
`path` называл родителя, и оставалось согласовать с ним `parent_id` и
`depth`. Здесь `path` пуст, и выбирать не из чего — вопрос «эти четыре
подкатегории или направления» решают не данные, а тот, кто заводил их
руками. Заполнить `path` по `parent_id` механически можно, но это тихо
утвердит один из двух ответов.

**Что решить:** чем должны быть эти четыре — подкатегориями своих родителей
или самостоятельными направлениями. После ответа правка на пять минут:
`categories:flatten` уже умеет приводить `depth` и `path` в согласие с
`parent_id`, надо лишь снять неоднозначность.

Проверка их не скрывает: она печатает каждую строку по номеру и слугу и
не валит прогон — расхождение настоящее, но не той правки, которая его
нашла.

нигде, уязвимость недостижима, и её можно ждать до перехода спокойно.

дешёвый и отбивает то, чему в адресе не место, независимо от версии.

## «Нравится» в первые секунды страницы записи считает от устаревшего состояния

**Измерено:** 11.09.2026, живой прод, 1440, учётка с подпиской — на тестовой
записи отметка у неё уже стояла. Найдено при проверке `fix/like-verify-gate`,
но эта ветка ни при чём: механизм старше, правка трогает только видимость
кнопки и ступень, которую она просит.

**Что произошло.** Клик через ~5 с после загрузки страницы. Сервер не
изменился — отметка стоит, реакций 1; интерфейс на миг прибавил единицу.
Второй клик отметку снял — реакций 0. Три повтора на 1440 и прогоны на 375
прошли чисто: это окно, а не постоянная поломка. Отметку учётке вернул.

**Механизм.**

- Серверная отрисовка анонимна: токен лежит в `localStorage`, загрузчику
  маршрута его не достать. В первом кадре у записи всегда `isLiked: false`.
- `routes/post.$uuid.tsx` помечает серверные данные просроченными
  (`initialDataUpdatedAt = 0`), и react-query дозапрашивает запись с токеном.
  `PostCard` сверяется со снимком сервера и подменяет состояние на настоящее —
  правка от 07.09.
- Пока ответа нет, `doLike` считает `next = !liked` от устаревшего `false` и
  отправляет «поставить» — `POST /posts/{uuid}/react`. Отметка уже стоит,
  сервер ничего не меняет; когда ответ приходит, интерфейс поправляется.
  Следующий клик уходит как «снять».

Ширина окна — время ответа `GET /posts/{uuid}` с токеном. В том прогоне он
не успел за ~5 с; мои замеры идут с задержкой ~500 мс до сервера.

**Насколько плохо.** Немного: человек видит «не отмечено» и жмёт, чтобы
отметить, — а отметка и так стоит, намерение совпадает с итогом. Остаются
лишняя единица, мигнувшая на счётчике, лишний запрос и путаница при двойном
клике. «Сохранить» и «Репост» берут состояние из того же снимка — у них,
скорее всего, то же окно. Не проверялось.

**Как чинить**, один из двух вариантов:

- пока запрос записи с токеном не вернулся, кнопки действий зрителя стоят
  с `aria-busy`, а клик ждёт ответа и выполняется по настоящему состоянию;
- действие отправлять не как «поставить» или «снять» по локальному флагу, а
  брать из ответа сервера, чем кончилось (`reacted`, число), и сверять
  интерфейс по нему.

## Прямая загрузка `/communities` и `/channels` вошедшим сдвигает секции

**Измерено:** 11.09.2026, сборка `feat/layout-rails-rule`, демо выключено,
учётка с подпиской, прямая загрузка страницы, 5 с наблюдателя `layout-shift`.

| страница | 1440 | 375 | источник |
| --- | --- | --- | --- |
| `/communities` | 0,0634 | **0,2013** | секция «Рекомендованные» y223 → 526 |
| `/channels` | 0,0375 | 0,0002 | две секции списка, +151 |

Это загрузка, а не переход. Переходы починены в той же ветке: у
`/communities` возврат больше не рисует закешированный анонимный ответ
(`gcTime: 0`), замер пар — ноль.

**Механизм** — тот же, что у «Нравится» выше. Серверная отрисовка анонимна:
токен в `localStorage`, загрузчику его не достать. Роли в ответе пусты, и
все сообщества попадают в «Рекомендованные». Компонент дозапрашивает список
с токеном, сверху вставляются «Мои» и «Подписки», и «Рекомендованные» уезжают
вниз на их высоту.

**Почему не в этой ветке.** Сервер не знает, вошёл ли зритель, а первый кадр
на клиенте обязан совпасть с серверным. Нужна одна из правок ниже, и обе
шире раскладки.

**Как чинить**, один из двух вариантов:

- при токене сразу после гидрации заменять список скелетоном до ответа с
  ролями: строки уходят, скелетон и секции вставляются, а вставка сдвигом не
  считается. Цена — список на мгновение пропадает;
- переносить признак входа в cookie, чтобы загрузчик на сервере шёл с
  правами зрителя. Решает то же и для «Нравится», но это правка авторизации —
  отдельная задача с проверкой на всех ступенях.

Δh −84. Ровно половина: блок центрируется по вертикали в контейнере с
`minHeight: min(88vh, 760px)`, поэтому потеря 84 px высоты двигает его верх
на 42.

**Что именно перетекает.** Не заголовок — у `h1` высота не менялась ни разу
(43 px до и после). Опрос детей блока по кадрам показал пятый узел, ряд
счётчиков `mt-12 flex flex-wrap gap-x-10 gap-y-4`
([routes/index.tsx:584](../frontend/src/routes/index.tsx)): **152 → 68 px** в
тот самый кадр, когда `document.fonts` доложил загрузку IBM Plex.

| время | IBM Plex | высота ряда счётчиков |
| --- | --- | --- |
| 2764 мс | нет | 152 |
| 2862 мс | да | 68 |

Подписи под числами набраны `var(--font-mono)` — это `"IBM Plex Mono",
monospace` (`styles.css:35`). Запасной `monospace` шире, подписи в верхнем
регистре с `letter-spacing: 0.08em` не помещаются, `flex-wrap` переносит ряд
на две строки. Приезжает IBM Plex Mono — ряд складывается в одну.

Добавка 0,0022 у вошедшего — отдельный, более поздний сдвиг (~4 с): шапка
меняет гостевую кнопку на пользовательское меню, когда приезжает сессия.

**Как чинить**, по возрастанию цены:

- зарезервировать высоту ряда счётчиков (`min-h-[...]` под две строки на
  узких ширинах и под одну на широких) — сдвига не будет ни в одну сторону;
- выровнять метрики запасного шрифта: `@font-face` с `size-adjust` и
  `ascent-override` под IBM Plex Mono, чтобы подстановка не меняла ширину;
- предзагрузить IBM Plex Mono (`<link rel=preload>`) — уменьшает окно, но не
  закрывает его: на медленной сети подмена всё равно случится.

Первое — самое дешёвое и точное, остальные лечат весь сайт сразу, но шире
этой записи. Ср. `/categories`, где такой же перетёк закрыли 11.09 приведением
строк к одной высоте.

## Вынести чанк из главного не значит перестать его качать

_Проверено дважды: звонки и словарь. Оба раза главный чанк уменьшался, а байт у посетителя становилось больше._

**Измерено:** 12.09.2026, прод и сборка. Попытка откачена (`a6ab384c` → откат).

Звонковый стек — `lib/calls.ts` плюс три экрана — лежал в главном чанке и
качался на каждой странице, хотя звонок начинается действием из мессенджера.
Вынос выглядел очевидным и был сделан тремя приёмами сразу:

- динамический `import("@/lib/calls")` в `lib/realtime/hub.ts`;
- `React.lazy` для `CallScreen`, `GroupCallScreen`, `GroupCallInviteDialog`;
- правило `manualChunks` в `vite.config.ts`, отправляющее `lib/calls.ts`
  в чанк `calls`.

**Главный чанк действительно уменьшился: 289 → 212 КБ (brotli).** И это ничего
не дало: суммарный JS на `/feed` вырос с 403 до 412 КБ, на `/ads/{uuid}` — с
377 до 387, оценки остались 70 и 92 (медиана из 5).

**Почему.** Вынесенные 80 КБ по-прежнему приезжают на первом экране, потому
что в HTML стоит `<link rel="modulepreload" href="/assets/calls-*.js">`.
Предзагрузку формирует **манифест серверной отрисовки TanStack Start**, а не
сборщик: манифест перечисляет всё, что достижимо из графа отрисованных
модулей, и `React.lazy` внутри `Suspense` из этого графа не выпадает.

Три вещи, которые пробовали и которые не помогают:

| Приём | Что вышло |
|---|---|
| `build.modulePreload: false` в Vite | ноль изменений: 38 `modulepreload` как было — настройка управляет подсказками сборщика, к манифесту SSR отношения не имеет |
| `React.lazy` + `Suspense` в `__root` | чанк остаётся в графе отрисовки, `modulepreload` сохраняется |
| Монтирование после гидрации (`CallHost` с `useEffect`) | тоже сохраняется: манифест собирается по графу, а не по тому, что отрисовалось в первом кадре |

Ещё одна ловушка по дороге: если затянуть в `manualChunks` не только
`lib/calls.ts`, но и `components/calls/*`, вместе с ними приедет LiveKit и
чанк вырастет до 2 МБ — выигрыш превращается в проигрыш.

**Проверено второй раз, на другом модуле.** 12.09 тем же способом выносили
словарь: `pages.settings`, `pages.adsNew`, `pages.messenger`,
`pages.onboarding` — 25 КБ — в `locales/ru-deferred.ts`, импортируемый четырьмя
файлами маршрутов, плюс правило `manualChunks`. Главный чанк снова честно
уменьшился, 289 → 283 КБ. Сумма байт на странице, наоборот, выросла:

| | `/feed` | `/settings` |
| --- | --- | --- |
| до выноса | 356 КБ, 37 файлов | 304 КБ, 5 файлов |
| после | **359 КБ, 38 файлов** | 306 КБ, 6 файлов |

Тот же манифест перечислил новый чанк на каждой странице, включая ленту, где
ни один модуль на словарь не ссылается. Плюс лишний файл — плюс лишний запрос.

По дороге всплыло отдельное: **`beforeLoad` при первой загрузке отрабатывает
только на сервере.** Первая попытка досылала словарь оттуда — серверная
разметка выходила правильной, а сразу после гидрации на экране появлялись
точечные пути вместо подписей (настройки, создание объявления, мессенджер,
знакомство). Если словарь всё же делить, привязывать его надо статическим
импортом к файлу маршрута, а не загрузкой из `beforeLoad`.

**Что это значит для следующей попытки.** Резать главный чанк имеет смысл
только там, где вынесенное перестаёт попадать в манифест первого экрана: то
есть модуль не должен быть достижим из графа отрисовки корня и страницы.
Условное монтирование по событию («звонок появился») это даёт, отложенное —
нет. Пока такой переделки нет, вынос ради размера главного чанка меняет
номер файла, а не число байт у посетителя — и добавляет запрос.
