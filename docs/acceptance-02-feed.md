### 2. «Сохранённое» показывает не все сохранённые записи

Серверного списка закладок не существует. В маршрутах есть только
`POST` и `DELETE /posts/{uuid}/bookmark` — поставить и снять. Списка
`GET` нет вовсе.

Вкладка фильтрует то, что уже загружено:

```js
// frontend/src/routes/feed.tsx:364
if (filter === "saved") return visiblePosts.filter((p) => p.isSaved);
```

То есть запись, сохранённая полгода назад, во вкладке не появится, пока
человек не долистает до неё в общей ленте. А запись, ушедшая из ленты
(снятая с публикации, скрытая правилом каналов), не появится никогда.

Сейчас в ленте 154 записи по 20 на страницу — первый экран покажет
сохранённое из первых двадцати. Комментарий в коде это признаёт:
«saved is a viewer flag, not a server filter».

Приоритет — **до открытия**, потому что вкладка обещает то, чего не
делает. Оценка: полдня — список закладок на сервере.

### 3. Неизвестное значение фильтра обходит ограничение на записи каналов

Замер, гость и подписчик дают одно и то же:

| `filter=` | Записей всего |
| --- | --- |
| `all` | 154 |
| `category` | 154 |
| `following` | 154 |
| `scheduled` | 0 |
| `subscriptions` (нет такого) | **194** |
| `saved` (нет такого) | **194** |
| `чтоугодно` | **194** |

Причина в `FeedService::list`. Ограничение, прячущее из ленты записи
авторских и экспертных каналов, применяется **только** к известным
значениям:

```php
if (in_array($filter, ['all', 'category'], true) && empty($filters['author_id'])) {
    // в ленту попадают только официальные и проверенные каналы
}
```

Любое другое значение проваливается мимо — и лента отдаёт сорок записей,
которым полагалось остаться на странице канала.

Утечки личного здесь нет: все эти записи опубликованы и открыты на
странице канала. Нарушается не тайна, а правило показа. Интерфейс шлёт
только правильные значения (`all`, `following`, `scheduled`,
`category`), так что через кнопки это не воспроизводится — только
запросом.

Приоритет — **после запуска**. Оценка: полчаса — свести неизвестное
значение к `all`.

## Что проверено и в порядке

**Запись сообщества не видна в ленте.** Собрал все 154 записи через API:
записей с `community` — **ноль**. Запись канала в ленте видна — одна, и
это официальный канал, как и задаётся правилом `FEED_KINDS`.

**Пять вкладок на месте** и видны гостю: Все, Подписки, Направления,
Сохранённое, Запланированные.

**Счётчик просмотров не накручивается.** `PostService::recordView`:
считается только опубликованная запись, свои просмотры автора не
считаются вовсе, а повтор гасится ключом `pv:<запись>:<зритель>:<день>`
со сроком до конца суток. У записей каналов то же самое сделано
уникальным индексом `(channel_post_id, viewer_key, viewed_on)` — надёжнее,
потому что переживает чистку кеша. У обычных записей дедупликация живёт в
кеше: его чистка обнулит счёт за день, и повтор засчитается второй раз.

**Планировщик отложенных записей жив.** `posts:publish-scheduled`
выполняется каждую минуту. Отдельно: записей со `scheduled_at` на проде
**ноль** — отложенная публикация в бою ни разу не использовалась. Это не
дефект, но и не проверено.

**Ошибок в консоли нет** (кроме предупреждений из находки 4).
Горизонтальной прокрутки на `/feed` нет.

## Что не проверено и почему

**Требует видимой панели браузера.** Панель сейчас скрыта, и хотя
наблюдатели в ней отвечают (проверил своим `IntersectionObserver`), лента
в таком состоянии отрисовывает мало карточек, а ленивые изображения не
загружаются. Мерить поведение в этих условиях — значит мерить состояние
панели, а не сервиса. Не проверены: сетка по каждому варианту
фотографий, просмотрщик (стрелки, счётчик «6 / 9», Esc, клик вне),
подгрузка комментариев без скачков, «Показать ещё», бесконечная
подгрузка.

**Требует публикации, а её не было по вашему указанию:** публикация
записи с текстом и с фотографиями, публикация видео, отложенный выход по
расписанию, репост со своим текстом и его уход на модерацию, рост
счётчика реакции.

## Чуть не записал ложную находку

`crontab -l | grep -c schedule:run` на проде даёт **0** — ни у `root`, ни
у `www-data`, ни у `deploy`. Отсюда напрашивался вывод, что планировщик не
работает вовсе, а значит не идут ни напоминания о мероприятиях, ни
авто-выплата по сделкам.

Это неправда. Планировщик запускается systemd-таймером
`modelizmclub-scheduler.timer`, и на момент проверки он отработал 58
секунд назад. Cron на этой машине к нему отношения не имеет.

Записываю, потому что это пятый случай за цикл, когда отсутствие в одном
месте едва не выдали за отсутствие вообще. Проверка стоила одной команды,
ложная находка стоила бы вам ночи.
